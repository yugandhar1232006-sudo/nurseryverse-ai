# 12. Plant Digital Twin (7H)

## Scope

7H is the frontend for Module 7's Plant Digital Twin engine: a per-plant, event-projected read model rather than a resource with its own writes. There is no "create a twin" or "edit a twin" anywhere in this phase -- a twin is created and updated internally by `DigitalTwinEventHandler` reacting to `domain_events` rows produced by every other module (registration, growth/health/watering/fertilizer/environmental recording, status transitions, moves, sales, AI predictions, and so on). The UI surfaces this projection: the current snapshot, its version history, a raw domain-event feed, and an on-demand replay-consistency check.

`DigitalTwinTab` is nested inside the Plant Profile (`/plants/[id]`, 7G) as one more top-level tab, not a separate route -- a twin only makes sense in the context of the one plant it belongs to, and 7G's page already owns the plant-identity chrome (header, permission gating, other tabs) a twin view would otherwise have to duplicate.

## Data layer

- `lib/api/digital-twin.ts` -- typed wrappers for every `/plants/{id}/digital-twin/*` read route plus the cross-plant `/digital-twins` listing: `getCurrentTwin`, `getTwinTimeline`, `getVersionHistory`, `getVersion`, `compareVersions`, `getSnapshotByDate`, `getEventHistory`, `verifyTwinConsistency`, `listDigitalTwins`. Every function is a `GET` -- there is no `POST`/`PATCH`/`DELETE` anywhere in this file, matching `digital_twin_service.py`'s own docstring: "entirely read-only; the only way to change a twin is to record an event elsewhere in the system."
- `TwinSnapshot` is hand-written, not generated: the Pydantic schema types `DigitalTwinResponse.snapshot` as a plain `dict`, so the generated OpenAPI client sees it as `Record<string, never>`. The real nested shape (`identity`, `lifecycle_state`, `operational_status`, `growth_stage`, `current_location`, `counts`, `latest`, `ownership`, `sold_at`/`deceased_at`/`deceased_reason`/`archived_at`/`archived_reason`) was reconstructed from `digital_twin_service.py`'s module docstring and cross-checked against its own `_on_*` projector methods (e.g. `_create_twin`, `_on_growth_recorded`, `_on_plant_sold`, `_on_ai_prediction_generated`) rather than guessed, then applied with an `as unknown as Record<string, never>` cast wherever a real value needs to cross the generated type boundary -- the same established pattern as `AtRiskPlantResponse.result` (7D) and `DomainEventResponse.payload` (this phase).
- `lib/digital-twin/queries.ts` -- `twinKeys` factory + `useCurrentTwinQuery`, `useTwinTimelineQuery`, `useVersionHistoryQuery`, `useEventHistoryQuery` (all list-shaped, auto-fetched), plus `useVersionQuery`/`useVersionCompareQuery` (on-demand, `enabled: false` until a version/pair is actually selected in the Versions panel).
- `lib/digital-twin/mutations.ts` -- `useVerifyTwinConsistencyMutation`. Consistency verification is a real `GET` server-side, but it's modeled as a TanStack `useMutation` on the frontend rather than a `useQuery`, because it's a diagnostic action the user explicitly triggers ("Verify now"), not data the page should silently refetch on mount or on a background interval -- the same reasoning 7B used for triggering a fresh permission check on demand.

## Permission model

Module 7 mints no dedicated `digital_twin:*` permission code anywhere in the seed data. `digital_twin_service.py`'s docstring is explicit: every route reuses `plants:read`. The frontend follows suit -- `DigitalTwinTab` is not independently `PermissionGate`d; it inherits the Plant Profile page's existing `plants:read` gate, the same as the Overview/Movement/Images/Timeline tabs from 7G. A user who can open a plant's profile at all can see its full twin, including cross-branch/cross-org internals the twin API is permitted to expose (there is nothing in the twin's own scope narrower than "can this user see this plant").

## Snapshot-shape by-example, not by-guess

Because `TwinSnapshot` isn't in the generated client, every field the UI renders was verified against a concrete projector method rather than assumed from the field name. Two examples worth recording: `latest.ai_prediction` is a small summary dict (`prediction_id`, `prediction_type`, `model_version`, `confidence`, `generated_at`) written by `_on_ai_prediction_generated`, not the full prediction record -- `TwinOverview` deliberately renders it as a one-line "latest prediction" fact with an explicit note that the *full* AI prediction history lives in 7L's `GET /plants/{id}/ai-predictions`, rather than implying this is a complete AI history view. `counts` is an integer-per-event-type dict that only grows, never per-field-updated -- `TwinOverview` filters it to non-zero entries before rendering, since a freshly registered plant would otherwise show a wall of "0" rows for record types that haven't happened yet.

## Versions vs. Timeline vs. Events -- three views of the same underlying data, deliberately not merged

All three panels are backed by overlapping backend concepts (`domain_events` rows and the `digital_twin_versions` table both key off the same event stream), but they answer different questions and were kept as separate panels rather than one mega-list:

- **Timeline** (`TwinTimelinePanel`) -- "what happened to this plant, twin-version by twin-version" -- a simple newest-first list of `version` + `event_type` + `occurred_at`, using the shared `RecordEntryList` scaffold since `DigitalTwinVersionResponse` has a real `id`.
- **Versions** (`VersionHistoryPanel`) -- the same list, but built for inspection: checkbox-select up to two versions (FIFO eviction past two), "View snapshot" opens the full raw JSON for one version, "Compare" calls `compareVersions` and shows `changed_keys` plus both snapshots side by side. This is the only panel that calls a `POST`-shaped-in-purpose-but-actually-`GET` comparison route.
- **Events** (`EventHistoryPanel`) -- the raw `domain_events` feed itself (`event_type`, `aggregate_type`, `actor_user_id`, `sequence`, `occurred_at`), with each row's full JSON `payload` behind a `<details>`/`<summary>` disclosure. This is strictly lower-level than Timeline/Versions -- an event doesn't necessarily produce a new twin version by itself in every case documented in the projector, so the raw event count and the version count are not guaranteed to match, and the UI doesn't claim they do.

## Route-registration-order dependency inherited from the backend

`digital_twin.py`'s `GET /plants/{id}/digital-twin/versions/compare` must be registered before `GET /plants/{id}/digital-twin/versions/{version}` server-side, or FastAPI would try to parse the literal string `"compare"` as the `{version}: int` path parameter and fail. `test/msw/digital-twin-handlers.ts` mirrors this exact ordering (`/versions/compare` before `/versions/:version`) even though MSW's own path-matching doesn't strictly require it, so the test fixture stays an honest model of the real route table rather than something that happens to pass by accident.

## UI states

Real loading skeletons, real empty states (a plant with only a `plant.registered` event still renders a valid twin with all-zero counts, not an error), real error states with retry on every panel, and a real "Verify now" action that shows either a genuine "Consistent as of version N" result or a genuine "Replay diverged on: ..." result without hiding a real inconsistency -- the point of the check is to surface drift, so the UI does not soften or suppress a `consistent: false` response.

## Real defect found and fixed this phase

**Nested `Tabs` producing two same-named `role="tab"` elements simultaneously.** 7H is the first phase to nest a `Tabs` component inside another `Tabs`' `TabsContent` (Digital Twin's own Overview/Timeline/Versions/Events tabs, inside the Plant Profile's own top-level tabs). Radix's `Tabs` only unmounts `TabsContent`, not `TabsList`/`TabsTrigger` -- so once the outer "Digital Twin" tab is selected, both the outer page's own top-level "Timeline" tab (7G) and the inner "Timeline" sub-tab exist in the DOM at once as `<button role="tab">Timeline</button>`, and an unscoped `getByRole("tab", { name: "Timeline" })` throws "found multiple elements." Fixed by giving the inner `TabsList` an `aria-label="Digital Twin views"` and scoping every test query for an inner tab through `within(screen.getByRole("tablist", { name: "Digital Twin views" }))`. This is now the established pattern for any future nested-tabs UI in this app -- documented here since 7H is where it was first needed.

## Known Limitations

- The Inventory Timeline concept floated during 7H's planning turned out to be structurally inapplicable: the bulk `inventory` table has no `plant_id` join in the general case (only one Module 8 exception, an optional `StockMovement.plant_id`), so there is no "this plant's inventory movement history" view here distinct from what `counts.inventory_movements`/`latest.inventory_movement` already summarize.
- `TwinOverview` shows only `latest.ai_prediction`, a one-fact summary -- the full `GET /plants/{id}/ai-predictions` history list is explicitly deferred to 7L (AI Experience), not duplicated here.
- `verifyTwinConsistency` is a potentially expensive full-replay operation server-side (`digital_twin_service.py` describes it as replaying every event for the plant from scratch); the UI calls it only on explicit user action ("Verify now"), never automatically on tab mount or on an interval.
- The cross-plant `GET /digital-twins` listing route is wrapped in the data layer (`listDigitalTwins`) but has no dedicated screen in 7H -- there is no product requirement for a standalone "all twins" browser distinct from `/plants` (7G's list already serves that purpose with richer plant-specific filtering), so the wrapper exists for completeness and potential reuse in 7N (Reports & Analytics) rather than being surfaced here.
