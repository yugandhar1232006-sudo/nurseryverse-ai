# 13. Inventory (7I)

## Scope

7I is the frontend for Module 8's Inventory & Stock Management bounded context: bulk-stock lines (pots, soil, fertilizer, tools, or an optionally species-tagged batch of unindividuated plant material) tracked by quantity rather than as individually-registered `Plant` rows (that's 7G). It covers three surfaces: the `/inventory` list (Stock/Locations/Reports tabs) and `/inventory/[id]` line detail (Movements/Reservations tabs). It deliberately does **not** cover 7G's per-plant records, 7J's Sales/CRM (deferred: a sale's `reference_sale_id`/`plant_id` linkage on `SellStockDialog` and `fulfill_reservation` stay null pending 7J's real Sales Order resource), or 7L's AI Experience.

`InventoryLocation` is a sub-branch physical hierarchy (Zone/Greenhouse/Outdoor Area/Rack/Bench/Section), always nested under a specific `branch_id` -- there is no org-wide "all locations" listing route server-side, so `LocationsPanel` always starts from a branch picker rather than a flat cross-branch table.

## Data layer

- `lib/api/inventory.ts` -- typed wrappers for every Module 8 route across its three path roots (`/inventory-locations`, `/inventory`, `/stock-reservations`) plus the new `/units` reference route (see Real defect below): `listUnits`, `createInventoryLocation`/`listInventoryLocations`/`deactivateInventoryLocation`, `createInventoryLine`/`listInventory`/`getInventoryLine`, `receiveStock`/`transferStock`/`reserveStock`/`adjustStock`/`markDamaged`/`disposeStock`/`sellStock`/`archiveInventoryLine`, `getLineMovements`/`getLineReservations`, `releaseReservation`/`fulfillReservation`, and the six reporting routes (`getInventorySummary`, `getLowStockReport`, `getStockValuation`, `getWasteReport`, `getTransferReport`, `getMovementHistory`, `getReservationReport`).
- `lib/inventory/queries.ts` -- `inventoryKeys` factory + 13 query hooks. `useInventoryLocationsQuery` is `enabled: false` until a real `branchId` is supplied (`GET /inventory-locations` requires `branch_id` server-side, same shape of constraint as 7H's on-demand version-compare query).
- `lib/inventory/mutations.ts` -- 13 mutation hooks. Every action mutation (`receive`/`transfer`/`reserve`/`adjust`/`damage`/`dispose`/`sell`/`archive`/`release`/`fulfill`) invalidates both the line detail and its movements query on success, plus reservations where relevant, and surfaces failure via `toast.apiError` -- consistent with the pattern established across 7F-7H.
- `lib/validation/inventory.ts` -- 10 Zod schemas, following the established numeric-field pattern (`z.string()` + `.refine()`, converted to `number | null` explicitly at submit -- never `z.coerce.number()`).

## Permission model

`inventory:read` gates every GET (the whole `/inventory` page and `/inventory/[id]` detail route). `inventory:write` gates the normal operational flows: create line, receive, transfer, reserve, sell, create/deactivate location, release a reservation. `inventory:adjust` gates the quantity-correcting/write-off actions: adjust, mark damaged, dispose, archive, and fulfilling a reservation (fulfillment converts a hold into a real departure of stock, not merely releasing a hold). This mirrors `inventory.py`'s own route-level permission declarations exactly -- no permission logic is re-derived or duplicated client-side beyond `PermissionGate`-wrapping each corresponding button.

## Single write-path awareness in the UI

The backend's `InventoryService._apply_change()` is the sole place `quantity`/`reserved_quantity`/`damaged_quantity`/`disposed_quantity` are ever written, always paired with exactly one immutable `StockMovement` row. The frontend reflects this by treating `MovementsTab` (`GET /inventory/{id}/movements`) as the authoritative, complete audit trail for a line -- every one of the eight mutating actions (receive/transfer/reserve/adjust/damage/dispose/sell/archive) is expected to produce exactly one new row there, and the tab reuses 7G's `RecordEntryList` scaffold since `StockMovementResponse` has a real `id`. `ReservationsTab` is separate and unpaginated (`list[StockReservationResponse]`, not a `Page_*_` shape), the same pattern 7G's `MovementTab` already established for a non-paginated sub-resource list.

## UI states

Real loading skeletons, real empty states distinguishing "no inventory yet" from "no matches" (Stock tab, same as 7G's plant list), a real "no locations yet" empty state per branch, low-stock and archived badges driven entirely by real response fields (`quantity <= low_stock_threshold`, `archived_at !== null`) rather than a separate flag, and real error+retry on every query. `AdjustStockDialog` and friends deliberately do **not** validate quantity bounds client-side -- an adjustment that would take quantity below zero is a real `InsufficientStockError` (modeled server-side as a `ConflictError` with `context={"reason": "insufficient_stock"}`), surfaced as a 409 via `toast.apiError`, with the dialog staying open rather than silently closing, so the user sees the rejection and can correct the value.

## Real defects found and fixed this phase

**1. Missing `GET /units` backend route (backend gap, fixed in `apps/api`).** `CreateInventoryLineRequest.unit_id` had no route for the frontend to discover valid unit ids, unlike `category_id` which already had `GET /plant-categories` (built in 7F). Both `Unit` and `PlantCategory` are global, system-seeded reference tables (migration `0002_seed_system_metadata.py`), never mutated through the API. Hardcoding the seeded UUIDs client-side was considered and rejected -- even though they're deterministic and real for this exact codebase, doing so would violate the "hit the real backend, no static/mock data" mandate, and there was no precedent anywhere else in the frontend for hardcoding backend-seeded UUIDs (roles, for comparison, are referenced by stable `code` strings, not raw UUIDs). Fixed by adding a full `UnitRepository`/`SqlAlchemyUnitRepository`/`FakeUnitRepository`/`UnitResponse`/`GET /units` route stack, mirroring the existing `PlantCategoryRepository` stack exactly, and adding `unit_repo` to `InventoryLocationService`'s constructor (not `InventoryService`'s, which has more call sites across other modules and was judged riskier to touch). Verified with a new unit test, 3 new integration tests, and a full backend regression run (684 unit tests + all 22 integration files) showing zero regressions.

**2. `LocationsPanel`'s auto-select-first-branch logic silently no-opped after a tab switch (frontend, this file).** The initial implementation used a "sync on reference change" render-body pattern -- `useState(branchesQuery.data)` compared against the live `branchesQuery.data` on every render, auto-selecting the first branch only when a *change* was detected -- modeled on the codebase's existing `ArchivePlantDialog.syncedOpen` precedent. That precedent doesn't actually apply here: `branchesQuery` uses a `staleTime` of 60s and a shared `QueryClient`, so if the Stock tab's `InventoryList` (which also calls `useBranchesQuery()`) had already fetched and cached branches before the user switched to the Locations tab, `LocationsPanel` would mount with `branchesQuery.data` *already populated on its very first render* -- meaning the "did the reference just change" check was already satisfied before the sync state even initialized, so the auto-select branch of the `if` never ran, and the branch `<Select>` was stuck on its "Select a branch" placeholder with no way to trigger the location list without the user manually re-selecting a branch. Found via a real test failure in `inventory.test.tsx`'s Locations panel test (switching from Stock to Locations after Stock's own branches fetch had already resolved). Root cause: the "sync on reference change" pattern is only correct when the *first* render is guaranteed to see `undefined`/no-data; it is not a general substitute for "initialize once data becomes available." Fixed by removing the indirection entirely -- the component now does `if (branchId === null && branchesQuery.data && branchesQuery.data.length > 0) setBranchId(branchesQuery.data[0].id)` directly in the render body, guarded solely by `branchId === null`, which is idempotent (once set, the condition itself becomes false, so it can't loop) and correct regardless of whether the query resolves synchronously-from-cache or asynchronously. Regression coverage added as part of the same `inventory.test.tsx` Locations panel test; full suite re-run afterward confirmed no other component relying on the same "sync on reference change" idiom (`ArchivePlantDialog`'s actual use case -- syncing a dialog's `open` prop, which genuinely does start `undefined`-then-defined on every mount -- remains correct and was not touched).

## Known Limitations

- `SellStockDialog`'s `reference_sale_id` and `fulfill_reservation`'s `reference_sale_id`/`plant_id` are deliberately submitted as `null` -- there is no real Sales Order resource yet to link to until 7J exists. Once 7J ships, both should be revisited to offer a real sales-order picker instead of an always-null field.
- `CreateLocationDialog` does not expose `parent_location_id` -- nesting locations under each other is real, validated backend behavior (`create_location` checks the parent belongs to the same branch), but no product requirement called for a nested-location picker in this initial build.
- There is no org-wide "all locations" listing route server-side, so `LocationsPanel` always starts from a branch picker (auto-selecting the caller's first accessible branch) rather than a flat cross-branch table.
- `InventoryList`'s branch/category filters are a user-chosen narrowing on top of whatever `inventory:read` already scopes server-side, not a client-side authorization boundary of their own.
