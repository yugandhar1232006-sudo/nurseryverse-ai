# 16. AI Experience (7L)

## Scope

7L is the frontend for Module 10's AI Platform -- the six real prediction modules (Disease Detection, Growth, Survival, Water Recommendation, Revenue Forecast, and the Recommendation Engine) plus the AI Assistant. It covers three genuinely separate surfaces, all built against the exact 13 routes confirmed to exist by direct `grep` against `lib/api/generated/schema.d.ts` (never assumed from the UX pages' own prose, several of which cite routes the real backend does not have -- see Known Limitations): a new "AI Predictions" tab on the existing `/plants/[id]` page (PG-26 + PG-28, on-demand growth/survival/water/disease-scan triggers plus full per-plant history); the real `/ai-center` implementation (PG-31/32/33, replacing 7C's `ComingSoon` placeholder) with Survival Risk, Revenue Forecast, and Recommendations tabs; and the AI Assistant, a persistent header overlay (FR-9.1-9.4) rather than a page, per `nav-config.ts`'s own docstring that Notifications and AI Assistant are "deliberately NOT" sidebar destinations.

## Data layer

- `lib/api/ai-predictions.ts` -- wraps all ten prediction/recommendation routes: `POST /ai/disease-detection/scan`, `GET /plants/{id}/ai-predictions`, `POST /plants/{id}/ai-predictions/{growth,survival,water}`, `GET /ai/predictions/survival-risk`, `GET+POST /ai/predictions/revenue-forecast`, `GET /ai/recommendations`, `POST /ai/recommendations/refresh`. Its docstring explicitly lists three routes cited by `docs/ux/09-page-inventory.md` that do not exist in the real backend -- `GET /ai/predictions/growth-summary`, `GET /ai/predictions/summary`, `POST /ai/recommendations/{id}/dismiss` -- confirmed absent via direct schema inspection, not silently worked around.
- `lib/api/ai-assistant.ts` -- wraps `POST /ai/assistant/message`, `POST /ai/assistant/actions/{id}/confirm`, `GET /ai/assistant/conversations/{id}`.
- Two hand-written result interfaces, `SurvivalPredictionResult` and `RevenueForecastResult` (in `lib/api/ai-predictions.ts`), and one for the Assistant, `ProposedAction` (in `lib/api/ai-assistant.ts`) -- the same established `Record<string, never>`-cast pattern as `TwinSnapshot`/`PassportContent`, but this time read directly from each inference module's own `predict()`/`postprocess()` source (`apps/api/app/ai/survival_prediction/inference.py`, `.../revenue_forecast/inference.py`) and `AssistantConversationService.send_message`'s message-construction code, not guessed. The other three prediction types' `result` shapes are deliberately left opaque -- see `ai-predictions-tab.tsx`'s docstring for why hand-writing all five was judged out of scope.
- `lib/ai-predictions/queries.ts` + `mutations.ts`, `lib/ai-assistant/queries.ts` + `mutations.ts` -- query-key-factory hooks mirroring every prior phase's pattern.
- `lib/validation/ai.ts` -- Zod schemas for the disease-scan URL field and the assistant message field, following the established `z.string()` pattern.
- `store/assistant-store.ts` -- a new, small persisted store holding only the current `conversationId`. This exists because Module 10's real API has no "list my conversations" route at all -- a caller can only ever fetch a conversation it already knows the id of, and ownership is enforced as a 404, not a 403 (`AssistantConversationService`'s own documented choice, to avoid confirming a conversation exists). The persisted id is the only way this frontend can reopen "my last conversation" after a reload; if it ever 404s (stale, deleted, or a different account sharing the browser), `AssistantPanel` clears it and falls back to a real empty state rather than surfacing a raw error.
- `store/ui-store.ts` (edited, additive) -- one new `assistantPanelOpen` flag + setter, following `notificationCenterOpen`'s exact precedent (shared state so any future second trigger point opens the same panel instance, not a duplicate).

## Permission model

`ai_predictions:read` gates the AI Predictions tab's visibility and every history/list read. `ai_predictions:run` gates every on-demand trigger -- growth/survival/water prediction, the disease-detection scan, and the revenue-forecast/recommendations-refresh actions -- all five confirmed via direct route inspection to share this exact one permission (see the real vs. documented discrepancy below). `ai_assistant:use` gates the Assistant panel's trigger and message-sending; `ai_assistant:confirm_write` is checked in addition, only for the Confirm button specifically (Cancel needs only `ai_assistant:use`, matching `ai_assistant.py`'s own reasoning: discarding a proposal is strictly less capable than confirming one).

## Real doc-vs-code discrepancies found and documented (not treated as defects to "fix" by matching the wrong doc)

- **PG-28's stated permission requirement is wrong.** `docs/ux/09-page-inventory.md` says AI Disease Detection Scan needs `disease:write, ai_predictions:run`. The real route (`run_disease_detection` in `ai_predictions.py`) only ever checks `ai_predictions:run`, a single permission, via `_authorize_plant`. The frontend gates the "Scan for disease" button on `ai_predictions:run` alone, matching the real route.
- **Three routes PG-07/31/33 describe do not exist**: `GET /ai/predictions/growth-summary`, `GET /ai/predictions/summary`, `POST /ai/recommendations/{id}/dismiss`. Verified absent via `grep` against the generated OpenAPI schema. No dismiss/snooze button was built for the Recommendation Feed, and no growth-summary widget was built -- building either would mean either silently doing nothing on click or calling a URL that 404s, both of which the kickoff's "no fake functionality" rule prohibits.

## UI states

Real loading skeletons, real empty states distinct from a populated list (e.g. "No AI predictions yet," "No revenue forecast yet," "No survival predictions yet"), real error+retry on every query. The Revenue Forecast panel distinguishes a genuine `insufficient_data` result (fewer than 7 real days of sales history) from `seasonal_naive` (a real, renderable 14-day chart) -- never a fabricated flat line when there isn't enough history. The Recommendations panel's Refresh button is disabled with explanatory copy when the page's branch-scope selector is on "All branches," since the real route's `branch_id` is a required, not optional, query parameter.

**One real defect found and fixed while writing test fixtures (not an application defect -- a fixture-authoring mistake, caught before it could mask a real bug):** the shared `makePrediction()` fixture's default `result` field is shaped for its most common caller (survival predictions). Fixed by explicitly passing `result: makeRevenueForecastResult() as unknown as Record<string, never>` at both the GET and POST revenue-forecast handler call sites, with an inline comment explaining why the default couldn't be trusted here.

Full regression after 7L: **30 test files, 195 tests, all passing, zero regressions** against every carried-over 7A-7K test. Verified with `vitest run --no-file-parallelism --pool=forks`, batched into six groups of four-to-six files.

## Known Limitations

- **No org-wide "AI prediction accuracy" or growth-summary widget on `/ai-center`**, because no such route exists server-side (`GET /ai/predictions/growth-summary`, `GET /ai/predictions/summary`) -- the closest real equivalent, a pre-aggregated accuracy ratio, already exists as 7D's Dashboard "AI" tab (`GET /dashboards/ai`, a different Module 12 rollup, not duplicated here).
- **No dismiss/snooze control on the Recommendation Feed**, because `ai_predictions.py` has no route for it -- only list and refresh. A recommendation's real `status` (new/dismissed/acted_upon) is shown as a read-only badge, since the backend does transition it via other paths (e.g. the Assistant's tool-call layer, per Module 10's own design), just not through a route this frontend can call directly.
- **`SurvivalRiskPanel` links each row to `/plants/{id}` using the raw plant id as the link text**, not a resolved plant label, because the raw `GET /ai/predictions/survival-risk` response only carries `plant_id` -- no batch id-to-label resolution route exists. 7D's Dashboard "AI" tab (`AtRiskPlantResponse`) does bundle a label, but that's a different, already-built Module 12 surface with a different response shape; duplicating its query here to backfill labels onto Module 10's raw rows was judged out of scope.
- **`AIPredictionResponse.result` is hand-typed for only two of five prediction types** (Survival, Revenue Forecast) -- Disease Detection, Growth, and Water Recommendation results are shown only via their shared `confidence`/`explanation`/`model_version` fields, not their own structured payload. A future pass could extend the same hand-written-interface pattern to the remaining three if a richer per-type display is wanted.
- **No file-upload UI for disease detection scans** -- `RunDiseaseDetectionRequest.image_url` expects an already-hosted URL, matching this backend's real (lack of a) binary upload endpoint; the same honest URL-registration pattern 7G's Images tab already established, not a new gap this phase introduced.
