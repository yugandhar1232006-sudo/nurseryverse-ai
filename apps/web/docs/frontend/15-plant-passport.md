# 15. Plant Passport (7K)

## Scope

7K is the frontend for Module 9's Plant Passport bounded context (`passport.py`'s two routers). It covers two genuinely separate surfaces sharing one backend module: an **internal, authenticated** surface -- a new "Passport" tab added to the existing `/plants/[id]` page (7G) that lists a plant's real passport version history and generates new versions -- and a **public, unauthenticated** surface -- `/passport/[token]`, a standalone route outside the authenticated app shell entirely, which is what a customer's phone actually opens when they scan the physical QR tag attached to a plant. It deliberately does not cover 7L's AI Experience, even though `ai_care_recommendations` appears inside a passport's frozen snapshot -- that field is always `[]` until Module 10's AI platform is wired into passport generation, and 7L owns the actual AI prediction/recommendation UI.

## Data layer

- `lib/api/passport.ts` -- internal, authenticated wrapper around `POST /plants/{plant_id}/passports` (generate) and `GET /plants/{plant_id}/passports` (list versions for one plant). Deliberately does **not** wrap the org-wide `GET /passports` or `GET /passports/reports/summary` routes -- see Scope decision below.
- `lib/api/public-passport.ts` -- public, unauthenticated wrapper around `GET /public/passport/{token}` and `GET /public/qr/{token}`. Reuses the same `apiClient`/`unwrap` helpers as every authenticated module: confirmed safe by reading `lib/api/client.ts` in full -- the 401-driven token-refresh retry only ever triggers on a literal 401 response, and these public routes only ever return 404 per their own declared `_PUBLIC_ERROR_RESPONSES`, so there is no risk of an unauthenticated visitor's request accidentally trying to refresh a token that doesn't exist. `PassportContent` and `QrScanContent` are hand-written interfaces (not generated) matching the backend's `dict[str, Any]` snapshot/live-data shapes exactly, cast via `as unknown as PassportContent` -- the same established `Record<string, never>`-cast pattern `TwinSnapshot` uses in `lib/api/digital-twin.ts`.
- **Real defect found and fixed here: wrong path prefix.** `passport.py`'s own module docstring claims `public_router` is "mounted with no shared prefix," but the actual generated `schema.d.ts` registers both public routes under `/api/v1/public/...`. Writing `apiClient.GET("/public/passport/{token}", ...)` failed `tsc --noEmit` with `TS2345: Argument of type '"/public/passport/{token}"' is not assignable to parameter of type 'PathsWithMethod<paths, "get">'`. Verified the real registered paths via direct `grep` against `schema.d.ts` before fixing, rather than guessing -- corrected both calls to the `/api/v1/public/...` form. Had this shipped unfixed, the public passport page would have 404'd for every real customer scan in production while every mocked test still passed (MSW handlers were written against the same, correct `/api/v1/...` path from the start).
- `lib/passport/queries.ts` + `mutations.ts` -- `passportKeys` factory, `usePlantPassportsQuery(plantId)`, `useGeneratePassportMutation(plantId)` (invalidates the plant's passport list on success).
- `lib/public-passport/queries.ts` -- `publicPassportKeys` factory, `usePublicPassportQuery(token)`, `useQrScanQuery(token)`. The QR scan query is deliberately configured with `staleTime: Infinity` and `refetchOnWindowFocus/refetchOnMount/refetchOnReconnect: false` -- `scan()` on the backend logs a real `QRScanEvent` as a side effect of being called, so refetching on every window focus or remount would inflate real scan-analytics counts with phantom scans that no customer actually performed.

## Permission model

`passport:read` gates the internal list route and the Passport tab's visibility on `/plants/[id]` (via `PermissionGate`, matching the exact pattern every other tab on that page already uses). `passport:generate` gates the "Generate passport" button and its dialog. `GET /passports/reports/summary` uses `reports:read`, not `passport:read`, per that route's own backend declaration -- not surfaced in this phase regardless (see Scope decision below). The public routes require no permission and no authentication at all -- there is no `PermissionGate` anywhere on `/passport/[token]`, by design.

## Scope decision: no standalone `/passports` list page

The backend exposes an org-wide `GET /passports` (list across all plants) and `GET /passports/reports/summary`, but this phase does not surface either as a page or sidebar nav item. Two UX documents were checked before deciding this, not assumed: `docs/ux/04-navigation-architecture.md` has zero mention of Passport as a primary nav destination anywhere in its full navigation tree, and `docs/ux/15-plant-passport-workflow.md` explicitly states "All versions remain retrievable from the plant's Digital Twin (PG-22) for audit purposes" -- meaning the UX spec's own intended integration point is per-plant, not a global list. `lib/navigation/nav-config.ts`'s docstring separately warns against inventing sidebar items not called for in the UX spec, citing the established precedent of Invoices/Suppliers being deliberately excluded from nav despite having seeded permissions and no corresponding backend route file. Given both, the internal half of 7K was built as an addition to the existing `/plants/[id]` page rather than a new route -- justified as "genuinely required" under the kickoff's "do not modify completed phases unless genuinely required" rule, since generating a passport requires a plant-scoped entry point (`POST /plants/{plant_id}/passports`) and skipping this would leave staff with no UI to generate a passport at all. The edit to `app/(app)/plants/[id]/page.tsx` was additive only: one import, one `TabsTrigger`, one `TabsContent`, both permission-gated identically to the page's other tabs -- no other line was touched.

## Scope decision: one public URL, two data sources

`passport_service.py`'s `qr_payload_url()` returns exactly one URL per plant (`{frontend_base_url}/passport/{public_token}`) -- the single URL physically encoded in the QR tag a customer scans. That one URL needs to serve two different kinds of data: the frozen `content_snapshot` from `GET /public/passport/{token}` (factual, point-in-time, matches `15-plant-passport-workflow.md`'s explicit "not a live dashboard... no AI predictions" framing) and the live "what does this plant need right now" data from `GET /public/qr/{token}` (health/water/fertilizer schedule computed at scan time, which is also what triggers the real scan-analytics side effect). Rather than inventing a second URL the physical tag doesn't encode, `/passport/[token]` renders both: the frozen certificate as the primary content, with a separately-badged "Live" **Current care status** section sourced from the QR scan endpoint underneath it. If the live QR-scan read fails for any reason, the certificate section still renders on its own -- a live-data hiccup does not hide an otherwise-successful certificate page.

## Route boundary

There is no `middleware.ts` in this app (confirmed absent). Auth gating happens entirely client-side in `app/(app)/layout.tsx`, which redirects to `/login` whenever `useSession()` resolves to unauthenticated. `/passport/[token]` cannot live under that route group -- doing so would redirect every real customer scan straight to a login page. A third route group, `app/(passport)/`, was created with its own minimal layout that uses a plain `<span>` for branding rather than a `<Link>` back into the authenticated app, deliberately, so a customer scanning a tag is never invited into the staff application.

## UI states

Internal tab: real loading skeleton, real empty state ("No passport generated yet") distinct from a populated list, real error+retry, version rows sorted newest-first with "Latest" and "Expired" badges computed from real `expires_at` data (never assumed), "Copy public link" (clipboard) and "View public page" (real anchor, `asChild` on `Button`) per row. Public page: real loading skeleton; a single unified not-found `ErrorState` for both an invalid and an expired token (`GET /public/passport/{token}` returns the same generic 404 for either case server-side, so the frontend does not fabricate a distinction the backend doesn't make); certificate sections (Origin, Nursery, Care guide, Health history, Purchase) each conditionally rendered only when their underlying data is present -- Purchase is `null` for any plant not yet sold, and is simply omitted rather than shown empty; AI recommendations section rendered only when non-empty (never a placeholder implying AI content exists when it's always `[]` pre-Module-10).

## Real defects found and fixed this phase

**1. Wrong public-route path prefix in `lib/api/public-passport.ts`** -- see Data layer above. Root cause: trusted a backend docstring's claim over the actual generated OpenAPI schema; fixed by verifying against `schema.d.ts` directly and correcting both `apiClient.GET(...)` calls to the real `/api/v1/public/...` paths. Caught by `tsc --noEmit`, not by a passing-but-wrong test (the MSW handlers had already been written against the correct path independently).
**2. `react-hooks/set-state-in-effect` ESLint error in `passport-tab.tsx`'s `GeneratePassportDialog`.** The dialog originally reset its one local `expiresAt` field via a raw `React.useEffect(() => { if (open) setExpiresAt(""); }, [open])`. ESLint's `set-state-in-effect` rule correctly flags this as a real error, not a stylistic warning, because `setExpiresAt` is a recognized `useState` setter (unlike, e.g., `form.reset()` calls elsewhere in the codebase which the rule doesn't flag). Fixed using the established render-body "adjusting state" pattern from this codebase's precedent set (`ArchivePlantDialog`'s `syncedOpen` guard), specifically the bare open/closed-transition variant rather than the content-signature variant `create-return-dialog.tsx` uses -- the content-signature variant exists to handle a field whose reset value depends on async query data that might arrive after the dialog opens, which doesn't apply here since `expiresAt` always resets to the same empty string regardless of any query state. A code comment at the call site explains why this variant, not the other, is correct.

## Known Limitations

- **No org-wide `/passports` list or `/passports/reports/summary` report page**, despite both backend routes existing -- a deliberate scope decision per the UX-doc citations above, not an oversight. A future phase could add this as a genuine standalone destination if product direction calls for one; today's UX spec does not.
- **`ai_care_recommendations` is always `[]` in every passport's frozen snapshot** until Module 10's AI platform is wired into passport generation server-side -- the frontend's conditional rendering (never showing an empty/placeholder AI section) is a direct, honest reflection of current backend behavior, not a frontend gap to fix later.
- **The public page merges two data sources onto one URL by design**, not as a routing shortcut -- see the Scope decision above. A future iteration could split "certificate" and "live status" into distinct sub-routes if a product need for linking to just one half ever arises, but the physical QR tag only ever encodes the one combined URL today.
- **No UI for revoking or explicitly expiring a passport version early.** The backend accepts an optional `expires_at` at generation time, and the internal tab surfaces whether a version has already expired, but there is no route to update `expires_at` after the fact -- generating a fresh version is the only way to supersede an existing one.
