# 14. Sales & CRM (7J)

## Scope

7J is the frontend for Module 9's Sales, Customer/CRM, Invoicing, and Returns/Refunds bounded contexts. It covers two top-level areas: `/customers` (list + `/customers/[id]` profile with Overview/Purchase History/Contacts/Addresses/Tags/Notes/Communications tabs) and `/sales` (a six-tab hub -- Quotations/Orders/Sales/Returns/Refunds/Reports -- plus four detail routes: `/sales/quotations/[id]`, `/sales/orders/[id]`, `/sales/[id]`, `/sales/returns/[id]`). It deliberately does **not** cover the Plant Passport routes that live in the same backend file set (`passport.py`'s `router`/`public_router`) -- those are cleanly separable and deferred entirely to 7K, nor 7L's AI Experience, which has its own separate prediction/recommendation surfaces.

## Data layer

- `lib/api/customers.ts` / `lib/api/sales.ts` -- typed wrappers for every Module 9 Customer/CRM route and every Sales/Quotation/SalesOrder/Invoice/Payment/Return/Refund route respectively, split into two files because `customers.py` and `sales.py` are two separate route files server-side. Money fields (`unit_price`, `*_amount`, `amount`) are typed `string` in every `*Response` schema (a pre-rounded 2-decimal Decimal, quantized `ROUND_HALF_UP` server-side) and `number | string` in every `*Request` schema -- the frontend never re-derives a total from `tax_rate` client-side, since the rate itself isn't persisted anywhere past Quotation/SalesOrder creation, only the resulting dollar `tax_amount`.
- `lib/validation/customers.ts` / `lib/validation/sales.ts` -- Zod schemas following the established `z.string()` + `.refine()` numeric-field pattern (never `z.coerce.number()`), converted to `number | null` explicitly at submit.
- `lib/customers/queries.ts` + `mutations.ts`, `lib/sales/queries.ts` + `mutations.ts` -- query-key-factory-based hooks mirroring 7I's `lib/inventory/queries.ts` pattern exactly.

## Permission model

`customers:read`/`customers:write` gate every Customer/CRM route. `sales:read` gates Quotation/SalesOrder/Sale/Return GETs; `sales:write` gates the normal create/status-change/confirm/cancel/checkout/approve/reject flows; `sales:void` gates completing a return specifically (the inventory-restocking, irreversible step -- heavier than `sales:write`, matching `sales.py`'s own route declaration). `invoices:read`/`invoices:write` are a separate permission pair gating Invoice/Payment/Refund GETs and writes, independent of `sales:*` -- a role can read Sales but not Invoices, or vice versa.

## Business rules reflected in the UI

- **State machines, enforced only server-side, surfaced as real 409s client-side.** Quotation: `DRAFT->{SENT,REJECTED,EXPIRED}`, `SENT->{ACCEPTED,REJECTED,EXPIRED,DRAFT}`, with `ACCEPTED/REJECTED/EXPIRED/CONVERTED` terminal for the generic status-change route (`ACCEPTED->CONVERTED` only via the separate `/convert` endpoint). Sales Order: `DRAFT->CONFIRMED->PROCESSING->FULFILLED`, or `->CANCELLED` from any non-terminal state. Return: `REQUESTED->{APPROVED,REJECTED}`, `APPROVED->COMPLETED` only. Every header component (`QuotationHeader`, `SalesOrderHeader`, `ReturnHeader`) only renders the buttons that are legal from the record's current status, but an illegal transition attempted anyway (e.g. a stale page after another user already acted) surfaces the real `invalid_status_transition` 409 via `toast.apiError` rather than being silently prevented twice.
- **`insufficient_stock` is a real, expected 409**, not just a defensive edge case -- Sales Order `confirm` reserves bulk-stock inventory per line through Module 8's real `InventoryService`, and `checkout` fulfills/sells every line, so either action can genuinely fail if stock changed between confirm-time and checkout-time. Reuses the exact same discriminated-context `ConflictError` shape 7I's Adjust/Sell dialogs already handle, not reinvented.
- **Checkout is idempotent server-side.** If `order.sale_id` is already set, a repeat checkout call returns the order unchanged rather than erroring -- `SalesOrderHeader`'s Checkout button is disabled during `isPending` to avoid firing a redundant request anyway, but a genuine double-click race is safe either way.
- **`Invoice.amount_paid`/`payment_status` are derived live** (sum of `Payment` rows vs. `total_amount`), never stored columns -- `InvoicePanel` always reads them straight off the `GET /invoices/{id}` response rather than computing a running total client-side, so a page reload or a payment recorded from elsewhere is always reflected correctly.
- **Refunds have no real payment-gateway integration.** `POST /refunds` creates a refund `PENDING` then immediately flips it to `COMPLETED` synchronously -- there's no webhook wait, and `CreateRefundDialog`'s copy says so explicitly rather than implying a real settlement step exists.

## UI states

Real loading skeletons, real empty states (e.g. "No quotations yet", "No returns yet", distinguishing "no customers yet" from "no matches" the same way 7F/7I's lists do), and real error+retry on every query, consistent with every prior phase. `RecordPaymentDialog`'s "Record payment" button is hidden once `invoice.status === "void"` or the remaining balance is `<= 0`, computed from the real response rather than a separate flag.

## Real defects found and fixed this phase

**1. `LineItemsFieldArray`'s section heading used `FormLabel` outside a `FormField`/`FormItem` context, throwing at render time (frontend, `components/sales/line-items-field-array.tsx`).** The repeatable line-item builder's "Line items" section header was written as `<FormLabel>Line items</FormLabel>`, reusing the same primitive as every per-field label elsewhere in the file. `FormLabel` internally calls `useFormField()`, which requires both a `FormFieldContext` (from an ancestor `<FormField>`) and a `FormItemContext` (from an ancestor `<FormItem>`) -- neither exists for a section-level heading that isn't bound to one specific RHF field, so it threw `"useFormField must be used within <FormField>"` the instant either `CreateQuotationDialog` or `CreateSalesOrderDialog` was actually opened and rendered. This was invisible to every validation step run before tests actually exercised the dialog: `tsc --noEmit` type-checks fine (the prop types line up), `eslint` has no rule for "this component requires a specific ancestor context," and `next build`'s static generation never mounts a closed dialog's contents. It was caught by the very first Vitest test that clicked "New quotation" and asserted the dialog's contents -- a concrete demonstration of why component tests that actually render interactive UI (not just typecheck/lint/build) are necessary before calling a phase complete. Root cause: reusing a context-bound primitive (`FormLabel`) for a non-field-bound purpose (a section heading). Fixed by importing and using the plain `Label` primitive (`components/ui/label.tsx`, which has no context requirement) instead, with an inline comment at the call site explaining why. Regression coverage: both of `sales.test.tsx`'s quotation-creation and sales-order-creation tests open the affected dialog and interact with a line item, so this exact defect class cannot silently return without failing those tests.
**2. `useCreateReturnMutation` had no `onError` handler, a silent-failure gap (frontend, `lib/sales/mutations.ts`).** Caught proactively while reviewing the mutation (not via a failing test): `CreateReturnDialog` manages its own local selection state rather than an RHF form (the set of returnable items is bounded to the sale's own items, not freely repeatable, so `useFieldArray` didn't fit), and therefore never calls `useApiFormErrors`'s `handleApiError`. Without an `onError` on the mutation itself, a real 422 from the backend (e.g. a requested return quantity exceeding the original sale item's quantity) would fail with zero user-visible feedback -- the dialog would just sit there having silently done nothing. Fixed by adding `onError: (error) => toast.apiError(error)` directly to the mutation, with a docstring comment explaining why this mutation's own `onError` is the *only* place such an error can surface for this particular dialog.

## Known Limitations

- **Line-item builders (`CreateQuotationDialog`, `CreateSalesOrderDialog`) only build inventory-linked (bulk-stock) lines in this initial build.** `LineItemRequest` also supports a `plant_id`-linked line (selling one specific, individually-registered `Plant` record from 7G), but the shared `LineItemsFieldArray` component only exposes an inventory picker. A future pass should add a toggle between "bulk stock" and "specific plant" per line.
- **`SaleResponse` has no `invoice_id` field** -- only `SalesOrderResponse` does, and there is no `GET /invoices` list route or a way to look up an invoice by `sale_id`. This means the Invoice/Payment UI (`InvoicePanel`) is only reachable from the Sales Order detail page that generated it (`/sales/orders/[id]`), never from the completed Sale's own detail page (`/sales/[id]`) -- documented in that page's own code comment, not a bug to work around.
- **`SalesOrder.payment_status` is never updated by `POST /invoices/{id}/payments`** -- that route doesn't pass a `sales_order` into `record_payment()`. Only the Invoice's own derived `payment_status` reflects real payment state; `SalesOrderResponse.payment_status` will silently stay `unpaid` after payments are recorded via this API path. This is real backend behavior being disclosed, not something the frontend can or should work around client-side.
- **`CreateReturnDialog` uses local component state instead of an RHF form**, since the set of returnable line items is fixed to the sale's own items (bounded, one checkbox row per item) rather than a freely add/remove-able list -- `useFieldArray` didn't fit this shape.
- **No delete/edit routes for customer contacts, addresses, or notes.** `customer_service.py` has `delete_contact`/`delete_address`/`delete_note` service methods, but no route exposes any of them, so those three tabs are deliberately add-and-list only. Tags are the one exception (`DELETE /customers/{id}/tags/{tag}` is a real route), which `TagsTab` uses.
- **`RefundsList` has no detail page** -- a refund has no sub-items or lifecycle actions beyond its one-shot synchronous creation, so there was nothing a detail route would add beyond what the list row already shows.
- **`CreateRefundDialog` exposes `return_id`/`invoice_id`/`sale_id` as three independent, optional free-text id fields** rather than a single typed picker, since the backend enforces no FK-level "exactly one of these three" constraint -- a general-purpose dialog was chosen over assuming every caller arrives from one specific linked record.
