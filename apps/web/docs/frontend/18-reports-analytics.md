# 18. Reports & Analytics (7N)

## Scope

7N is the real `/reports` route (replacing 7C's `ComingSoon` placeholder), covering the two genuinely distinct real workflows Module 12's `reports.py` supports beyond dashboards: on-demand Report Catalog/Generate/Status/History/Download, and Scheduled Reports CRUD. Dashboards and Analytics (`/dashboards/*`, `/analytics/*`) are **not** part of this phase's UI work -- those 19 routes were already built as 7D's `/` (home) route, confirmed by reading `components/dashboards/dashboard-content.tsx` directly rather than assuming from the phase name. `lib/api/reports.ts` already wrapped every dashboard/analytics/report/scheduled-report route as part of 7D's own data-layer work (all three route groups live in the same backend file), so this phase only adds the three wrapper functions 7D's scope didn't need (`getCustomerAnalytics`, `getScheduledReport`, `runDueScheduledReports`) and builds the UI for the report-generation and scheduling routes 7D never touched.

## Data layer

- `lib/api/reports.ts` (extended) -- added `getCustomerAnalytics` (`GET /analytics/customer-analytics`, same `CustomerDashboardResponse` shape as `/dashboards/customer` -- a distinct real route, not a duplicate call), `getScheduledReport` (`GET /reports/scheduled/{id}`), and `runDueScheduledReports` (`POST /reports/scheduled/run-due`). Also exported `ReportFormat`/`ReportStatus`/`ReportScheduleFrequency`, previously referenced only inline. `runDueScheduledReports`'s docstring documents why this manual trigger is real and not redundant: Module 14's Celery beat already sweeps due scheduled reports automatically, but the real route exists as an operator-facing "run now" action independent of the beat schedule.
- `lib/reports/queries.ts` (new) -- `reportKeys` factory; `useReportCatalogQuery` (10-minute `staleTime`, the catalog is effectively static); `useReportHistoryQuery` and `useReportStatusQuery`, both with a `refetchInterval` that is a *function of the last fetched data* -- polling only continues while at least one visible report is `pending`/`processing`, and stops on its own once every report has settled into `complete`/`failed`. This is necessary because `POST /reports` (verified against `apps/api/app/api/routes/reports.py` directly) returns `202 Accepted` immediately and hands generation to FastAPI `BackgroundTasks`, not Celery -- there is no webhook, SSE, or other push channel back to the frontend, so polling the list is the only way to observe progress.
- `lib/reports/mutations.ts` (new) -- `useCreateReportMutation`, the four Scheduled Reports CRUD mutations (`create`/`update`/`pause`/`resume`/`delete`), and `useRunDueScheduledReportsMutation`. Each invalidates `reportKeys.all` on success; the form-backed ones (create report, create/update schedule) intentionally omit an `onError` handler so the RHF `useApiFormErrors` pattern at the call site can map 422s to fields, following every prior phase's established split between "mutation owns success side-effects" and "the form owns error mapping."
- `lib/validation/reports.ts` -- `generateReportSchema` and `scheduledReportSchema`. **Scope decision, not an oversight**: the real `ReportFilters` schema has nine fields (`species_id`, `category_id`, `customer_id`, `customer_type`, `status`, `category`, `prediction_type`, `low_stock_only`, plus `date_from`/`date_to`), each meaningful only for a subset of the 18 real `ReportType` values (e.g. `low_stock_only` only means something for an Inventory report). Building 18 distinct per-type filter forms was judged out of scope for this pass; both dialogs expose only branch scope and `date_from`/`date_to`, the two filters meaningful for every report type. See Known Limitations.

## UI

- `components/reports/report-history-panel.tsx` -- Report Catalog (a card grid sourced directly from the real `GET /reports/catalog` response, never a hand-typed label list, so titles always match the backend's actual `ReportType` set) plus Report History (`RecordEntryList` of `ReportResponse`, status badge, download link shown only once `status === "complete"` and `download_url` is non-null). Every catalog card and the top-level "Generate report" button are gated on `reports:export`; the catalog and history lists themselves need only `reports:read`.
- `components/reports/generate-report-dialog.tsx` -- `POST /reports`. Report-type options come from the same real catalog data (title as the label, `report_type` as the value), so the dropdown can never drift from what the backend actually accepts.
- `components/reports/scheduled-reports-panel.tsx` + `scheduled-report-dialog.tsx` -- Scheduled Reports CRUD (`RecordEntryList` of `ScheduledReportResponse`, Pause/Resume/Delete row actions, "New schedule" dialog for `POST /reports/scheduled`) plus the real "Run due reports now" button for `POST /reports/scheduled/run-due`. All writes gated on `reports:export`.
- `components/reports/reports-content.tsx` -- two-tab container (`Reports`, `Scheduled`) wired into `app/(app)/reports/page.tsx`, replacing the `ComingSoon` placeholder inside the existing `PermissionGate permission="reports:read"` wrapper (unchanged from 7C).

## Testing

**Vitest/RTL (written, executed, passing):** `components/reports/__tests__/reports.test.tsx`, 7 tests -- permission-denied page without `reports:read`; real catalog + history rendered with Generate/export controls hidden for a `reports:read`-only role; a `processing` report shown without a download link alongside a `complete` report with a real download `href`; generating a real report through the dialog and asserting the real `report_type`/`format` POST body; listing real scheduled reports and pausing one through the real mutation; creating a real scheduled report through the dialog; running due scheduled reports now through the real mutation.

New fixtures/handlers: `test/fixtures/reports.ts`, `test/msw/reports-handlers.ts` (registered in `test/msw/server.ts` adjacent to `dashboardHandlers`, since both wrap the same backend route file but own disjoint path prefixes -- no shadowing risk, same reasoning as `aiHandlers`' placement in 7L).

**One real test-authoring mistake found and fixed while writing this suite (not an application defect):** the first draft asserted a `pending`-status report showed the label "Generating…", but `pending` and `processing` are two distinct real `ReportStatus` values with two distinct labels in `report-history-panel.tsx` (`"Pending"` vs `"Generating…"`) -- the test's fixture used the wrong status for the assertion it made. Fixed by using `processing` where the "Generating…" label was actually being exercised, rather than loosening the component's real per-status labels to make the wrong fixture pass.

Full regression after 7N: **36 test files, 231 tests, all passing, zero regressions** against every carried-over 7A-7M test. Verified with `vitest run --no-file-parallelism --pool=forks`, batched into six groups of five-to-six files.

`npx tsc --noEmit`: 0 errors. `npx eslint` across every 7N file: 0 errors. `npx next build`: succeeds; `/reports` builds correctly.

**Playwright E2E (written, collected, not executed):** `e2e/reports.spec.ts`, 2 tests -- generating a real report and watching it move from pending to complete in history with a real download link (exercising the actual async `BackgroundTasks` generation path end-to-end); creating a real scheduled report and pausing it. Collected via `npx playwright test --list` (2 tests confirmed, parses cleanly). ## Known Limitations

- **Generate/schedule dialogs expose only branch scope and a date range**, not the other seven real `ReportFilters` fields -- a deliberate, disclosed UX scope decision (see `lib/validation/reports.ts`'s docstring), not a gap in what the backend supports. A future pass could add per-report-type conditional filter fields.
- **Scheduled report editing (`PATCH /reports/scheduled/{id}`) has a real wrapper function (`updateScheduledReport`) and mutation (`useUpdateScheduledReportMutation`) but no dedicated edit UI** -- only create, pause, resume, and delete are exposed as actions in this pass, matching what the real Report History cards and catalog make immediately actionable; the update route exists and is data-layer-ready for a future edit dialog.
- **The "Run due reports now" button has no per-item feedback** beyond a toast with the real `executed_count` -- it doesn't highlight which specific scheduled reports it ran, since `RunDueResponse.results` isn't rendered individually in this pass.
