# Frontend Architecture — Phase 7A (Foundation)

Covers `apps/web`: stack, directory layout, and the decisions made building the foundation that every later Phase 7 sub-phase (7B–7Q) builds on. Phase 6 (Backend) is complete and approved; nothing here duplicates its business logic or bypasses its AuthorizationService/PermissionService — the frontend calls the real API and renders what it returns.

## Stack

Next.js 16 (App Router, Turbopack), React 19, TypeScript (strict), Tailwind CSS v4, hand-built shadcn/ui-style components (Radix UI primitives + `class-variance-authority` + `tailwind-merge`), TanStack Query v5 (server state), Zustand v5 (client/UI state), React Hook Form + Zod, `openapi-fetch` against types generated by `openapi-typescript`, Recharts, Framer Motion, `next-themes`, `sonner`.

This is the stack specified in Phase 4's frontend architecture doc — no substitution.

## Why no shadcn CLI

`npx shadcn@latest init` was attempted first. Its current version's `-b` flag means "component library" (`base|radix|aria`), not "base color" as in older CLI versions, and its interactive theme-preset selector (Nova/Vega/Maia/…) has no non-interactive flag in this CLI version, so it can't run unattended in this environment. The primitives in `components/ui/` were hand-built directly from the same underlying pieces the CLI would have used (Radix primitives + `cva` + `cn()`), wired to this project's own design tokens instead of shadcn's defaults. Functionally equivalent output, full control over the token wiring.

```
  components/

  lib/

    auth/                 # Permission-aware UI utilities (see 05-permission-aware-ui.md).
    forms/                # RHF ↔ backend-validation-error bridge.
    toast.ts              # sonner wrapper, ApiError-aware.
    utils.ts              # cn() classname helper.
  providers/
    query-provider.tsx    # TanStack QueryClientProvider (client/server split, per-request client on the server).
    theme-provider.tsx    # next-themes wrapper.
  store/
    session-store.ts       # Auth session (tokens + Me snapshot), in-memory only.

```

## Design tokens

`app/globals.css` transcribes every token in `docs/design/06-design-tokens.md` into Tailwind v4's CSS-first `@theme` format (no `tailwind.config.js` in v4 — theme values are custom properties, and Tailwind generates utilities from their names automatically). Two things worth knowing:

- **Spacing/icon-size tokens are not redefined.** The design doc's scale (4/8/12/16/24/32/48/64/96px, 16/20/24/32px) is exactly Tailwind's own default 4px-based scale — `space-4` already is `p-4`/`gap-4`. Redefining them would just be a second name for the same value.
- **Z-index tokens are named, not left as bare numbers**: `z-sticky` (10), `z-dropdown` (20), `z-overlay-scrim` (30), `z-overlay` (40), `z-toast` (50), `z-tooltip` (60) — verbatim from the design doc's own Z-Index Tokens table. Component code reads `z-overlay-scrim` rather than a bare `z-30` whose meaning has to be looked up.
- **Light/dark mode** uses `next-themes`'s `.dark` class strategy (`@custom-variant dark (&:where(.dark, .dark *))`), with the surface/text/border tokens defined per-mode in `:root`/`.dark` and mapped into shadcn-style generic names (`background`, `foreground`, `card`, `border`, etc.) via a second `@theme inline` block, so primitives never reference a domain-specific token directly.
- **Fonts are self-hosted**, not loaded via `next/font/google`. `next/font/google` requires a live fetch to `fonts.googleapis.com` at build time; some CI/sandboxed network policies block that (this build hit exactly that in the agent sandbox), and self-hosting avoids sending every visitor's first request to a third-party CDN regardless. `@fontsource-variable/inter`'s static `.woff2` is loaded via `next/font/local`, which still gets Next's font optimizations (self-hosted asset serving, automatic fallback-metric CSS to prevent layout shift).
