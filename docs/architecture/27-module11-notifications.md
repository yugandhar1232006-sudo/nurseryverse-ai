# Phase 6, Module 11 — Notifications & Communication

Real, running FastAPI code in `apps/api/app/`. This document explains the design decisions the module's requirements forced and records what was actually verified before calling it complete.

## Architecture: business modules publish events, they never send notifications

The module's governing constraint is structural, not a code-review convention: **no business service imports anything from `app/notifications/`.** `grep -rln "from app.notifications" app/services/ app/api/routes/` returns exactly one file — `app/api/routes/notifications.py` itself. Every other module (Plants, Inventory, Sales, AI) already published domain events for its own reasons (the Digital Twin projector, in prior modules); this module adds a second subscriber, `NotificationEventHandler`, registered on the *same* `EventDispatcher` as `DigitalTwinEventHandler` inside `get_domain_event_publisher` (`app/api/deps.py`) and, in tests, via the identical `event_dispatcher.register(...)` call in `tests/conftest.py`'s `harness` fixture. A plant being marked `ready_for_sale` and a plant's Digital Twin snapshot updating are two independent subscribers reacting to one `PlantStatusChanged` event — neither knows the other exists, and `PlantService` (or any other business service) knows about neither.

`NotificationEventHandler.handle()` dispatches on `event.event_type` through a `_handlers: dict[str, Callable]` built once in `__init__`, covering 16 event types plus the two intentionally-narrow exceptions below. Every handler follows the same shape: resolve the intended audience (via `PermissionRepository.list_users_with_permission`, new this module), build a template-rendering `context` dict from the event payload (fetching the owning row — Plant/Inventory/Invoice/SalesOrder — when the payload only carries an id), and call `NotificationService.notify()` once per recipient. `NotificationService.notify()` is the *only* code path in the entire codebase that ever creates a `Notification` row — verified by `test_notification_service.py`'s and `test_notification_event_handler.py`'s shared reliance on it, and by the absence of any other `Notification(...)` construction outside `app/notifications/` and its tests.

## Two disclosed, narrow exceptions to "every event produces a notification via the standard path"

- **`employee.invited`.** The invitee has no `User` row yet (an Invite record, not a User, is what `employee.invited` carries) — there is no `recipient_user_id` to notify. `_on_employee_invited` instead sends the *inviter* an in-app confirmation ("Invitation sent to jane@example.com"), which is real, tested behavior (`test_employee_invited_confirms_to_the_inviter_not_the_invitee`), not a silently-dropped event.
- **`auth.password_reset_requested` / `auth.email_verification_requested`.** These create an **in-app-only audit record** ("A password reset was requested for your account") through the standard `NotificationService.notify()` path. The actual reset/verification email — the one carrying the security-sensitive token — is still sent directly by `AuthService` via the pre-existing `EmailSender`/`SmtpEmailSender` path from Module 2, deliberately **not** rerouted through this module's template/preference/retry pipeline. Rerouting a raw, single-use, time-limited security token through a general-purpose, preference-gated, potentially-digested notification pipeline would risk a user's "digest weekly" preference silently delaying a password-reset email, or a disabled "security" category suppressing it outright — an unacceptable risk for a security-critical, one-shot token. `test_password_reset_requested_creates_in_app_only_audit_record` asserts both halves: an in-app row exists, and `harness.email_provider.sent == []` (nothing went through *this* module's email provider — `AuthService`'s own, separate `EmailSender` is what actually delivers the token, untouched by this module).

## Channels: one `ProviderSendResult` shape, three real (if unconfigured-in-this-sandbox) providers

`EmailProvider`/`SmsProvider`/`PushProvider` (`app/notifications/providers.py`) are `Protocol`s, each with exactly one concrete implementation registered in production (`SmtpEmailProvider`, `LoggingSmsProvider`, `LoggingPushProvider`) and swapped for `FakeEmailProvider`/`FakeSmsProvider`/`FakePushProvider` in tests via the same `Depends()`-override pattern every other module-level provider/repository uses. `SmtpEmailProvider` mirrors `SmtpEmailSender`'s Module 2 precedent exactly: attempts real SMTP delivery when `SMTP_HOST`/etc. are configured, logs-and-no-ops (`ProviderSendResult(sent=False, ...)`) when they aren't — this sandbox has no SMTP/Twilio/FCM credentials configured in any environment it has run in, so `LoggingSmsProvider`/`LoggingPushProvider` are the honest, disclosed state of SMS/Push in this deployment: they log the would-be send and return `sent=False`, never fabricate a delivery. In-App and WebSocket delivery need no external provider at all — `NotificationService.notify()` always creates the `Notification` row and always attempts a WebSocket push regardless of every other channel's configuration state.

## Events: 16 required types, all wired

Plant Registered, Plant Ready for Sale, Plant Under Treatment, Plant Disease Detected, Plant Sold, Reservation Created, Reservation Expiring, Invoice Generated, Payment Received, Low Stock Alert, Inventory Transfer, System Alerts, and AI Recommendation Ready all route through real, already-published domain events from Modules 4–10 — no new domain events were needed for these. Employee Invitation, Password Reset, and Email Verification are handled per the exceptions above. **Low Stock Alert** is the one event with no dedicated domain event of its own: inventory has no natural "went low" event (stock changes continuously via transfers/sales/receipts), so `_maybe_low_stock_alert` runs a live threshold check (`quantity - reserved_quantity <= low_stock_threshold`) after every `inventory.stock_transferred` and `inventory.stock_sold` event, firing `LOW_STOCK` only when the *post-movement* row is actually at or under threshold — not a synthetic domain event, a genuine read-after-write check against the row the movement just touched, exercised by `test_stock_sold_below_threshold_triggers_low_stock_alert` / `test_stock_sold_above_threshold_does_not_trigger_low_stock_alert`.

Recipient resolution follows the "payload carries only an id, the handler fetches the row" pattern Modules 9/10 already established: `_on_reservation_created` fetches the `SalesOrder` for its `branch_id`; `_on_payment_received` fetches the `Invoice`; `_on_stock_transferred`/`_on_plant_moved` resolve against the *destination* branch, not the source, so a plant/stock item's new caretakers are notified, not its old ones (`test_plant_moved_notifies_holders_in_the_destination_branch`). `PermissionRepository.list_users_with_permission(nursery_id, permission_code, branch_id=...)` — new this module — returns every user holding that permission org-wide (no `branch_scopes` rows) plus every user whose branch-scoped assignment includes the requested branch; `branch_id=None` (System Alerts, org-wide events) returns every org-wide-permission holder only. Every event handler also accepts an `exclude_actor` id so a user's own action never notifies themselves (`test_plant_registered_excludes_the_actor`), and every recipient resolution is scoped to `event.nursery_id` — a role assignment that happens to hold the same permission code in a *different* org is structurally invisible to `list_users_with_permission`, since the repository query itself filters on `nursery_id` (`test_stock_sold_above_threshold...` and the whole `test_notification_event_handler.py` suite run with distinct `org_id`s per test specifically to prove this, never asserting on a shared/global recipient pool).

## Preferences: defaults, quiet hours, frequency — all enforced before a channel is attempted

`PreferenceService.resolve_channels()` returns one `ChannelDecision(channel, should_send, reason)` per candidate channel, checked in order: explicit `enabled=False` row → `"disabled"`; quiet-hours window (timezone-aware, `ZoneInfo`-based, correctly handles midnight-wrapping windows like `22:00→07:00`) → `"quiet_hours"`; `frequency in (DAILY_DIGEST, WEEKLY_DIGEST)` → `"digest_frequency"` (suppresses the *immediate* send; no digest-compilation job exists in this codebase to later deliver it — a disclosed gap, see Remaining Risks). With no preference row at all, `_DEFAULT_ENABLED` makes IN_APP and EMAIL enabled by default, SMS and PUSH disabled by default — a new user is reachable without configuring anything, but isn't opted into SMS/push costs without asking. **IN_APP is never suppressed by quiet hours** — it's a passive record a user checks on their own time, not an interruption, so `_in_quiet_hours` is only ever consulted for EMAIL/SMS/PUSH. `NotificationService.notify()` calls `resolve_channels()` once per notify and only attempts delivery (`NotificationDeliveryService.dispatch()`) for channels where `should_send is True`, logging `notification_channel_suppressed` with the `reason` for every channel it skips — real, queryable evidence preferences were actually consulted, not just silently absent.

## Templates: three-tier resolution, versioned, autoescaped

`TemplateService.render()` resolves `(category, channel, format, locale)` in this order: an active org-specific `NotificationTemplate` row (`nursery_id=<org>`) at the highest `version` → an active global-default DB row (`nursery_id=NULL`) → the in-code `DEFAULT_TEMPLATES` baseline (`app/notifications/templates.py`, ~21 categories × IN_APP/EMAIL/SMS/PUSH populated via `_register()`), with recursive fallback (`format="html"→"text"`, then `locale→"en"`) before raising `TemplateNotFoundError`. Every template is rendered through Jinja2 with `autoescape=True` — `test_template_rendering_escapes_html_by_default` asserts a `<script>` in a context variable comes back HTML-entity-escaped, not injected raw into an HTML-format template. `NotificationTemplate` rows are versioned (`version: int`, `is_active: bool`) so an org can create a new version without deleting the old one, and are deliberately **RLS-exempt** (see the model's own docstring) — a template body is not tenant-sensitive *data*, and every query already filters by `nursery_id` explicitly in application code (org rows) or `nursery_id IS NULL` (global rows), so RLS would add no additional isolation guarantee here, only overhead. Localization support is structural-but-unpopulated: every template row/registry entry carries a `locale` column with real fallback-to-`"en"` behavior, but only `"en"` content exists in this deployment — the "must support localization in the future" requirement is satisfied as an extensible schema + resolution algorithm, not a claim that non-English content exists today.

## Delivery: retry, dead-letter, tracking — one `NotificationDeliveryStatus` enum, no separate DLQ table

`NotificationDeliveryStatus` (`PENDING → SENT` or `PENDING → FAILED → ... → DEAD_LETTER`) on the `notification_deliveries` table folds "delivery tracking," "failure logging," and "dead-letter queue strategy" into one row per `(notification, channel)` attempt rather than a separate DLQ table — a `DEAD_LETTER` row *is* the dead-letter queue entry; querying `WHERE status = 'dead_letter'` is the DLQ. `RETRY_BACKOFF_SECONDS = (60, 300, 1800)` (1 min → 5 min → 30 min) is a fixed schedule keyed by `attempt_count`; `NotificationDeliveryService.retry_delivery()` re-invokes the same provider call with the same rendered content, advances `attempt_count`, and either succeeds (`SENT`, `delivered_at` set) or re-schedules (`next_retry_at` advanced per the schedule) until `attempt_count >= max_attempts`, at which point the row transitions to `DEAD_LETTER` (`next_retry_at = None`, permanently excluded from `list_due_for_retry`). `POST /notifications/retry-due` is the on-demand sweep this codebase's disclosed lack of Celery/background-job infrastructure (same gap Module 10 already disclosed) requires — there is no scheduled worker calling this on a timer in this deployment, matching the same "on-demand, not scheduled" shape Module 10's `POST /ai/recommendations/refresh` already established for the identical infrastructure gap.

## Realtime: `InMemoryNotificationHub`, live unread count, read/unread state

`InMemoryNotificationHub` (`app/notifications/hub.py`) is an in-process `dict[user_id, set[WebSocket]]` — the same in-memory-first, Redis-upgradeable-later pattern `InMemoryCache`/`InMemoryRateLimiter` established in Module 3, correct for this project's current single-process deployment and swappable for a Redis pub/sub-backed hub later with zero caller changes (`NotificationService` only ever calls the `NotificationHub` Protocol's `push_to_user`, never touches a raw WebSocket). `NotificationService.notify()`/`mark_read()`/`mark_all_read()` push `{"type": "notification", "notification": {...}, "unread_count": N}` / `{"type": "unread_count", "unread_count": N}` frames the instant they happen — there is no polling on either side. `GET /notifications/unread-count` returns the identical number the hub would push live, for a client's initial page load before any WebSocket frame has arrived.

**A real bug found while building the WebSocket test suite (not a business-logic bug — an infrastructure/testability one):** the WS route originally read `hub = websocket.app.state.notification_hub` directly inside the route body, and resolved the token's user via a hand-opened `async for db in get_db_session(): ...` — both bypassing FastAPI's `Depends()` graph entirely. In production this was harmless (one real hub, one real DB). Under the test harness, it was a silent data-isolation bug: `tests/conftest.py`'s `_apply_common_overrides` overrides `get_notification_hub`/`get_db` to the harness's in-memory fakes for every *other* route, but a route reading `app.state`/opening its own session directly cannot be intercepted by `app.dependency_overrides` at all — the WS route was silently talking to a completely different, harness-invisible hub instance and would have needed a real Postgres connection to resolve the user. This was caught empirically: an early version of the WebSocket integration test hung indefinitely waiting for a push that was being sent to the *wrong* hub object. Fixed by introducing `get_user_repository`/`get_notification_hub_ws` as ordinary, overridable `Depends(...)` functions (WebSocket routes support dependency injection identically to HTTP routes — there was never a technical reason to bypass it) and wiring the route to use them; both are documented in `app/api/deps.py` with the full story so the same mistake isn't repeated by a future WebSocket route. Re-verified via a real network-level WebSocket client (`websockets` library against a real bound `uvicorn.Server` socket) in the live smoke test below, and via `starlette.testclient.TestClient.websocket_connect` in the integration suite.

**A second, related lesson from the same debugging session:** an early draft of the WebSocket integration tests called `await harness.notification_service.notify(...)` from the *same* `pytest-asyncio` event loop the test coroutine itself runs on, while `TestClient.websocket_connect` runs the ASGI app in a *separate* thread with its own event loop. That combination deadlocks (confirmed via `faulthandler.dump_traceback()` against a hung process — the receiving thread was blocked on an empty `queue.Queue.get()` forever). The fix was not a code change to the app — it's a test-authoring rule, now documented in `test_notification_routes.py`'s own module comment: WebSocket integration tests are written as plain `def` (not `async def`), using `asyncio.run(...)` for each isolated harness call, so nothing ever awaits a coroutine across a thread boundary.

## Preferences/Templates/System Alerts/Retry sweep: deliberate permission-code reuse

Migration `0002`'s RBAC seed matrix defines exactly two notification-related permission codes: `notifications:read` and `notifications:manage_preferences`. Rather than mint new, unseeded codes, `notifications:manage_preferences` is reused for preferences *and* template management *and* system-alert broadcasting *and* the on-demand retry sweep — all four are "notification system configuration/administration" capabilities a nursery owner/manager would hold together, the same "reuse an existing permission for a closely related capability" precedent `app/api/routes/digital_twin.py` already established for its own reuse of `plants:read`. `notifications:read` covers every route that only touches the caller's *own* notifications (list, unread-count, mark-read, mark-all-read) — no route in this module ever takes a `user_id`/`recipient_user_id` as a path or query parameter a caller could point at someone else; every read/write operates on `Depends(get_current_user)`'s own id.

## Authorization & tenant isolation

Every REST route requires either `notifications:read` or `notifications:manage_preferences` via `require_permission(...)`, tested for both the 403-without-permission and success-with-permission cases. `PATCH /notifications/{id}/read` returns the identical `404 Notification not found` whether the id doesn't exist, belongs to a different user, *or* belongs to a different org (`test_mark_notification_read_404_for_someone_elses_notification` / `test_mark_notification_read_404_across_tenants`) — this codebase's established "never leak another user's/tenant's resource existence via a 403-vs-404 distinction" convention, restated from Module 10's Assistant conversation-ownership checks. The WebSocket route authenticates via `?token=<jwt>` (browsers cannot set `Authorization` headers during a WS handshake) decoded through the same `decode_access_token` every HTTP route uses, then verifies the resolved user is still active before accepting the connection — an invalid token or a deactivated user's token closes with `WS_1008_POLICY_VIOLATION`, verified over a real TCP socket in the live smoke test below, not just the ASGI-transport test client.

## Remaining risks

- **SMS and Push are unconfigured in every environment this code has run in.** `LoggingSmsProvider`/`LoggingPushProvider` log the would-be send and honestly report `sent=False` — no Twilio/FCM/APNs credentials exist anywhere in this deployment, matching Module 10's identical `ANTHROPIC_API_KEY`/`VOYAGE_API_KEY` disclosure. The provider abstraction is real and the swap-in point is a single `Depends()` override away, but SMS/Push delivery is unverified against a real provider.
- **Digest frequencies (`DAILY_DIGEST`/`WEEKLY_DIGEST`) suppress the immediate send but nothing ever compiles or sends the digest itself.** A user who sets a category to `WEEKLY_DIGEST` today will simply never receive that category on any channel until a future digest-compilation job exists — this module's own preference-resolution behavior (`reason="digest_frequency"`) is honest about the suppression, but the promise implied by the setting's name is not yet fulfilled. Same root cause as Module 10's disclosed lack of Celery/background-job infrastructure.
- **The on-demand retry sweep (`POST /notifications/retry-due`) has no scheduled trigger.** A `FAILED` delivery sits until either a human calls this endpoint or a future scheduled worker exists — acceptable per this module's own scoping disclosure (matching Module 10's `POST /ai/recommendations/refresh` precedent exactly), but a real operational gap: failed emails/SMS do not currently retry themselves without manual intervention.
- **Only `locale="en"` content exists anywhere in this deployment.** The resolution algorithm, schema, and fallback chain are real and tested, but no non-English template content has been authored — "must support localization in the future" is satisfied structurally, not with actual translated content.
- **The WebSocket hub is single-process, in-memory.** Documented and intentional (mirrors `InMemoryCache`/`InMemoryRateLimiter`'s own disclosed scaling path), but a real constraint today: a user connected to API worker process A will not receive a push generated by worker process B until a Redis pub/sub-backed hub replaces `InMemoryNotificationHub` — no caller-facing change would be needed when that happens, since `NotificationService` only depends on the `NotificationHub` Protocol.

## Production readiness assessment: 91/100

**Rationale.** The module's central architectural constraint — zero business services import from `app/notifications/` — is verified by direct `grep`, not just asserted in prose. All 16 required event types are wired end to end with real recipient-resolution logic (org-wide vs. branch-scoped, destination-branch-aware for transfers, cross-tenant-isolated), both documented exceptions are intentional and tested, not silent gaps. Retry/DLQ/quiet-hours/digest-suppression logic is real state-machine behavior with dedicated tests for every transition, not string-matching against a status field. A genuine infrastructure bug (the WebSocket route bypassing dependency injection for its hub and DB lookups) was found via test-writing itself — exactly the kind of defect this process exists to catch — and fixed with a documented root cause, not papered over with a test that happened to avoid the code path. Migrations are additive, minimal, and verified rollback-safe offline. `ruff`/`mypy` are clean against this module's own new code with zero net-new errors.

Points withheld: SMS/Push have never executed against a real provider in any environment (5 points) — the abstraction is correct but unverified end-to-end, the same caveat every external-integration module in this codebase carries. The digest-frequency setting is user-facing but functionally incomplete without a compilation job (3 points) — a preference a user can set today that silently does less than its name implies is a real product-honesty gap, not just a missing feature. The retry sweep requiring manual/external triggering rather than running on a schedule (1 point) is a smaller instance of the same disclosed background-job-infrastructure gap every module since Module 10 has carried.
