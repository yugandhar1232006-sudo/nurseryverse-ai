# Phase 6, Module 14 — Production Readiness: infrastructure, CI/CD, observability, and DR

The final module of Phase 6 (Backend). No new business capability — this module makes the thirteen modules already built (`app/`) deployable, observable, and recoverable: Docker images, Compose orchestration, Nginx, GitHub Actions CI/CD, Prometheus metrics, real Celery worker/beat wiring, backup/restore + a disaster-recovery runbook, and a load/stress test. Scoped from Task #35's one-line description, supplemented by the detailed design already written in `docs/architecture/09-infrastructure.md`/`10-devops.md` during Phase 4 planning — this module implements those documents, not a new design.

## Architecture: what's new, what isn't

No new microservice, message queue, or standalone process beyond what `09-infrastructure.md` already specified. Everything below implements that document's existing topology:

- **`app/core/metrics.py`** — Prometheus `Counter`/`Histogram` on the default global registry, instrumented once inside `app/core/middleware.py`'s existing `RequestContextMiddleware` (not a second middleware layer). Labeled by route *template* (`request.scope["route"].path`), not raw path, so a parameterized route like `/api/v1/employees/{id}` collapses onto one label series regardless of how many distinct employee ids are requested — verified by a dedicated test asserting no UUID ever appears in a `path_template` label.
- **`GET /metrics`** (`app/api/routes/health.py`) — unauthenticated, unprefixed (matches `/healthz`/`/readyz`'s own convention), excluded from the OpenAPI schema. Not proxied through Nginx (see below) — scrape access is a network-layer decision, not an application-layer one.
- **`app/workers.py`** — a real Celery application, not a stub. `retry_due_notifications` (every 5 minutes) and `run_due_scheduled_reports` (every minute) close a gap Modules 11 and 12 each explicitly disclosed in their own architecture docs ("no scheduler exists — needs an external cron trigger"). Each task builds its own repository/service dependency graph directly from a fresh `AsyncSession`, mirroring `app/api/deps.py`'s `get_domain_event_publisher` — a worker process has no request/response cycle to hang a `Depends()` off of.
- **`infra/docker/api.Dockerfile`** / **`infra/docker/worker.Dockerfile`** — multi-stage (`deps` → `runner`), non-root user, build tools discarded in the final layer. `worker.Dockerfile` duplicates rather than `FROM`-references the built `api` image, trading a small amount of layer-cache reuse for independent buildability (documented in that file's own header) — `beat` is not a third image, it reuses the `worker` image with a different Compose `command:`, per `09-infrastructure.md` §1.
- **`docker-compose.yml`** / **`docker-compose.prod.yml`** — dev (bind mounts, hot reload via `uvicorn --reload`, host-published debug ports) and a production overlay (`!override`-tag Compose merge, no bind mounts, resource limits, `restart: unless-stopped`, pre-built image tags). Services: `postgres` (`pgvector/pgvector:pg16`, not stock `postgres` — migration 0001 needs the `vector` extension), `redis`, `api`, `worker`, `beat`, `nginx`.
- **`infra/nginx/`** — TLS termination point (commented-out `listen 443` block, since no certificate exists in this repository), routing (`/api/` → `api`, with WebSocket upgrade headers always forwarded for `/api/v1/notifications/ws`), the security headers deferred here from the application layer during this module's own security audit (Task #156: HSTS, CSP, X-Frame-Options, X-Content-Type-Options, Referrer-Policy, Permissions-Policy), gzip compression, and a `/metrics` deny (defense in depth alongside the metrics endpoint simply not being routed to).
- **`.github/workflows/ci.yml`** — the staged pipeline `10-devops.md` §1 diagrams: lint → typecheck → import-boundaries → unit tests → integration tests (against real ephemeral Postgres/Redis service containers, including a genuine `alembic upgrade head` this sandbox could never run) → security scan (pip-audit + bandit) → build/push (api + worker images, GHCR, SHA + semver tags) → a second migration dry-run from the built image → a `production` GitHub Environment gate for deploy (the manual-approval mechanism the doc calls for).
- **`infra/backup/`** — `backup_database.sh` (daily `pg_dump`, S3-compatible upload, 30-day/12-month daily/monthly retention, webhook alert on failure), `wal_archive.sh` + `postgresql.conf.snippet` (continuous WAL archiving, `archive_timeout=300` to bound RPO), `restore_database.sh` (plain restore or point-in-time recovery, `--confirm`-gated), `DR_RUNBOOK.md` (concrete steps against this repo's own Compose files, mapped to the 4h RTO / 15m RPO targets).
- **`infra/loadtest/load_test.py`** — an async concurrent load generator (httpx-based; no `locust`/`k6`/`wrk` binary was installable in this sandbox), with a real, run result recorded in `RESULTS.md`.

### Scope deviations from `09-infrastructure.md`, disclosed

- **No `web` service, no `web.Dockerfile`.** Phase 7 (Frontend) has not been built in this engagement — there is no Next.js app to containerize. `docker-compose.yml`'s `nginx` service proxies `/api/` only; `location /` returns a deliberate `503` explaining the frontend isn't deployed yet, rather than a broken `proxy_pass` to a nonexistent upstream.
- **No brotli compression** — requires a non-default Nginx module not present in the stock `nginx:1.27-alpine` image this Compose file references; gzip alone is configured.
- **`worker.Dockerfile` duplicates `api.Dockerfile`'s build stages** rather than building `FROM` a pre-built api image tag, for independent buildability (see that file's own header comment) — a deliberate, disclosed implementation choice, not an oversight against the doc's "same base as api.Dockerfile" phrasing.

## Testing

No new business-logic test suite this module (there is no new business logic) — this module's own validation is the full existing regression suite plus new tests specific to what this module added:

- **3 new integration tests** for `GET /metrics` (`tests/integration/test_health.py`): exposition format, route-template cardinality safety (no raw UUID ever appears in a label), and exclusion from the OpenAPI schema.
- **8 new unit tests** for `app/workers.py` (`tests/unit/test_workers.py`): dependency-graph construction correctness (mirrors `app/api/deps.py`'s composition root, both handlers registered), commit-on-success/rollback-on-exception for both scheduled tasks (against a real in-memory SQLite engine, not a mock), and that the Celery-decorated sync entrypoints correctly drive `asyncio.run()`.
- **4 import-linter contracts** (`pyproject.toml`), verified against the real codebase — not aspirational: routes may not import concrete repository implementations (only `app.repositories.interfaces` Protocol types), services may not import from the API layer, repositories may not import services, and domain models stay free of every higher application layer. A deliberate temporary violation was introduced and confirmed to actually fail the check before being reverted, proving the contracts aren't vacuously passing.
- **A real load/stress test** against a live `uvicorn` process (`infra/loadtest/RESULTS.md`): 5,775 requests over 8 seconds at 30 concurrent workers, 100% correct status codes, zero transport errors, p95 ≈ 117ms — scoped honestly to the endpoints that don't require a live database (disclosed in that file).

## Defects found and fixed this session (each with a regression test or equivalent verification)

Running `ruff check .` and `mypy app` fully, for the first time this engagement, across the *entire* `app/` tree (every prior module's own validation pass checked only the files it touched, or a narrower surface) surfaced defects in six earlier modules' files. Per the standing process, each is explained, fixed, and documented here rather than silently patched:

1. **Five SQLAlchemy models used undefined-per-static-analysis forward references.** `Mapped["User"]`/`Mapped["Plant"]`/etc. relationship type hints referenced classes defined in *other* model files, never imported anywhere in the referencing file (not even under `TYPE_CHECKING`). This never broke at runtime — SQLAlchemy's declarative mapper resolves these via its own class registry, not Python's import system, which is why `configure_mappers()` and every prior module's tests passed regardless — but it is a real static-analysis gap: `ruff` (F821) and `mypy` (name-defined) both correctly flagged it once run without a narrower file scope. One occurrence (`app/models/auth.py`) had even been silenced with a bare `# noqa: F821` rather than fixed, which satisfies ruff but not mypy (different tools, different suppression syntax) — that's what surfaced it to mypy specifically. Fixed uniformly across `app/models/catalog.py`, `identity.py`, `organization.py`, `plants.py`, `auth.py`: a `TYPE_CHECKING`-guarded import of the referenced class in each file, costing nothing at runtime and creating no import cycle (both `catalog.py`↔`plants.py` guard imports back to each other safely, since neither is ever evaluated outside `TYPE_CHECKING`). Verified: `ruff check .` clean, `mypy app` clean, `configure_mappers()` still resolves all 81 tables' relationships correctly.
2. **`SystemConfigService`'s `_ERROR_RESPONSES`-shaped dicts in `app/api/routes/auth.py`/`audit.py` had no explicit type annotation**, so mypy inferred a narrower structural type than FastAPI's `responses=` parameter expects, flagging every call site. Fixed with an explicit `dict[int | str, dict[str, Any]]` annotation on each — a pre-existing Module 2/3 gap (the original author never ran a full `mypy app` pass against these files), not something this module introduced.
3. **`Settings.AUTH_REFRESH_COOKIE_SAMESITE` was typed `str`**, but its only consumer (`app/api/routes/auth.py`'s `_set_auth_cookies`, calling Starlette's `Response.set_cookie(samesite=...)`) only accepts `Literal["lax", "strict", "none"] | None`. Fixed by narrowing the field to that same `Literal` — a genuine correctness improvement, not just a type-checker appeasement: pydantic-settings now validates the env var at startup, so a typo'd value fails fast at process boot instead of reaching Starlette deep inside the first cookie-mode login request.
4. **`AuthService._register_failed_attempt` read `user.locked_until.isoformat()` after just having assigned it**, two lines above, inside the same `if locked:` branch — functionally always non-`None` in practice, but mypy cannot narrow an ORM instance attribute re-read after assignment the way it narrows a local variable. Fixed by capturing the value in a local `locked_until: datetime | None` variable at assignment time and reading that instead — zero behavior change, now provable to the type checker rather than relying on the two branches staying in sync by convention.
5. **`app/core/logging.py`'s `_add_request_context` processor had no type annotations**, which widened the `shared_processors`/`renderer` lists structlog's `configure()` call assembles them into down to `list[object]`, failing mypy's structural check against `structlog.typing.Processor`. Fixed with explicit parameter/return annotations on the function (`structlog.typing.EventDict`/`WrappedLogger`) and `list[Any]` annotations on the two list variables — `Any` rather than the precise `Processor` type because structlog's own built-in processors (`TimeStamper`, `ConsoleRenderer`, etc.) still didn't structurally satisfy the stricter alias when tried, a known imprecision in that library's own type stubs, not a bug in this codebase.
6. **`app/reporting/exporters.py`'s `render_excel` had three related openpyxl-stub gaps**, surfaced only after installing `types-openpyxl` (itself a defect-fix — see item 7): `Workbook.active` is stub-typed `Worksheet | Chartsheet | None`, over-approximating a freshly-constructed `Workbook()`'s actual guaranteed-non-None default worksheet; and `Cell | MergedCell` cell-tuple typing meant `.column_letter` (real openpyxl: only `Cell` has it, `MergedCell` does not) was flagged correctly, not a stub false positive. Fixed with an `isinstance(sheet, Worksheet)` runtime guard (both a real safety check and a mypy-narrowing one) and by switching to `.column` (present on both types) + `get_column_letter()` instead of `.column_letter` — zero behavior change for this function's actual, never-merges-cells usage, confirmed by the pre-existing `test_export_format_excel_decodes_via_openpyxl` (Module 12) still passing unchanged.
7. **`mypy` had never been run with a stub-complete environment against `openpyxl`/`reportlab`/`python-jose`/`celery`** — each has been a real dependency since Modules 2/11/12, but no prior module's validation apparently installed the matching `types-*`/`celery-types` stub packages, so every usage was silently `Any`-typed instead of actually checked. Fixed by adding `types-openpyxl`, `types-python-jose`, `types-reportlab`, `celery-types` to `requirements/dev.txt`; `cloudinary` has no stub package on PyPI (confirmed via `pip index versions types-cloudinary`), closed instead via a scoped `ignore_missing_imports` override in `pyproject.toml`'s new `[tool.mypy]` section (no other mypy strictness setting was changed, to avoid silently surfacing a flood of unrelated findings across 13 modules' worth of code well beyond this module's own scope).
8. **`import-linter` had been a declared dev dependency since an earlier module but had no contract configuration anywhere** — the "Import-boundary check" stage `10-devops.md`'s CI pipeline names had nothing to actually run. Fixed by adding `pyproject.toml`'s `[tool.importlinter]` section with four contracts (see Testing above), each verified against the real codebase (not aspirational) before being committed, including a deliberate temporary-violation sanity check.
9. **Three scripts/ files carried genuinely dead code** (`scripts/validate_schema.py`'s unused `in_degree`/`reverse_in_degree` dict and unused `dupes` list; `scripts/generate_seed_migration.py`'s unused `perm_ids`), plus two f-strings with no placeholders (`scripts/generate_data_dictionary.py`, `app/api/routes/auth.py`). None affected runtime behavior (dev tooling / docstring text) — cleaned up as part of the same `ruff check .` pass, since leaving known-dead code in a file this module was already editing for other reasons isn't consistent with the standing quality bar.

None of these nine defects were introduced by this module's own new code (`app/core/metrics.py`, `app/workers.py`, and this module's edits to `app/core/middleware.py`/`app/api/routes/health.py` all passed both tools cleanly on first pass) — every one predates Module 14 and was only surfaced because this module's own validation step was the first to run `ruff`/`mypy` against the complete `app/` tree rather than a per-module subset.

**A tenth, process-level defect**: `apps/api/requirements/base.txt` was accidentally overwritten mid-session by a `Write` call made without first re-reading the file's full current content (only its last 20 lines had been read via a `tail` command beforehand) — a violation of this module's own tool-use discipline (files must be read before being written). The reconstruction was cross-checked against this sandbox's actually-installed package versions (13 of 19 checked packages matched exactly) and left as-is once that gave reasonable confidence it was accurate; flagged here for transparency rather than silently assumed correct. No functional impact was observed (every test/build/lint step against the reconstructed file passed), but a maintainer with access to this repository's real version history should diff this file against its pre-Module-14 state to confirm no pin actually changed.

## Remaining risks / disclosed gaps

- **No live infrastructure exists in this development sandbox**: no `docker` binary, no live PostgreSQL, no live Redis, no `nginx` binary, no `aws`-cli/`pg_dump`/`pg_restore`. Every Docker/Compose/Nginx/backup-restore artifact in this module was validated via syntax/structural checks only (path references, YAML/Nginx-config parsing, `bash -n`) — never an actual build, container run, or database restore. The GitHub Actions pipeline (`ci.yml`) was validated via schema-conformance only; its first genuine execution will be whenever this repository is first pushed to GitHub with Actions enabled. This is the single largest gap in this module's own verification and should be the first thing exercised against a real environment before this repository is trusted for a production deployment.
- **No `web` service / Phase 7 frontend** — disclosed above; `docker-compose.yml`/`nginx.conf` both need extending once Phase 7 exists.
- **The requirements/base.txt reconstruction** (defect 10 above) should be diffed against real version history if this repository has one outside this engagement's own sandbox sessions.
- **Backup/restore/DR runbook scripts have never executed against a real Postgres or object store** — per `DR_RUNBOOK.md`'s own closing section, the first quarterly drill (§5 of that document) is this module's actual validation, not this document's existence.
- **The load test's ~722 req/s / p95 ≈ 117ms figures are not a production capacity claim** — single uvicorn worker, no gunicorn fan-out, no Nginx in front, constrained sandbox hardware, and only non-database-touching endpoints exercised (see `infra/loadtest/RESULTS.md`'s own Interpretation section for the full caveat).
- **`cmdstan` (Prophet's inference backend) install step in both Dockerfiles is unverified** — pinned to a specific version (`2.35.0`) for deterministic multi-stage `COPY --from` behavior, but never actually built in this sandbox; a genuine `docker build` may need adjustment on first real attempt.

## Production readiness assessment

This module makes the application deployable in the infrastructure sense — real Docker images, real orchestration, a real CI/CD pipeline, real metrics, a real background-job scheduler, and a real (if unexercised) backup/DR story — on top of thirteen modules that were already production-ready in the application sense (authenticated, authorized, audited, tenant-isolated, tested). Every artifact traces to an explicit line in `09-infrastructure.md`/`10-devops.md`'s Phase 4 design rather than being invented ad hoc, and every deviation from that design (no `web` image, no brotli, `worker.Dockerfile`'s build-duplication choice) is disclosed inline rather than silent. Nine pre-existing defects across six earlier modules' files were found, fixed, and documented during this module's own full-tree validation pass — none were in this module's own new code. 1,159 of 1,159 tests pass; Ruff and mypy are both fully clean across the entire `app/` tree for the first time this engagement; import boundaries are now enforced, not just conventional; migrations validate offline; the OpenAPI schema and a live server both confirm correct wiring; and a real load test confirms the request-lifecycle middleware holds up under concurrency.

The one honest gap this document cannot close from within this sandbox: nothing Docker/Compose/Nginx/CI-shaped has actually run. That is this module's own clearly-flagged next step, not a claim of completeness this document is making on its behalf.

This is the final module of Phase 6 (Backend) — completing it finishes Phase 6 in its entirety. Per the standing instruction, work stops here for review and approval before Phase 7 (Frontend) begins.
