# Phase 6, Module 12 — Reports & Analytics: API layer + production-readiness review

Real, running FastAPI code in `apps/api/app/`. This document covers the REST API layer built on top of the already-existing repository/service layers (`ReportingRepository`, `DashboardService`, `AnalyticsService`, `ReportGenerationService`, `ScheduledReportService` — all built and reviewed in prior sessions) and records the production-readiness review performed before calling the module complete.

## API surface

`app/api/routes/reports.py` (no router-level prefix, spanning `/dashboards/*`, `/analytics/*`, `/reports/*`) exposes 28 OpenAPI path entries covering all 26 required capabilities: 9 dashboard endpoints, 10 analytics endpoints, the report catalog, report generation/status/download/history, and full scheduled-report CRUD plus pause/resume/run-due. Every route calls exactly one of the four Module 12 services and contains no query or business logic of its own — dashboards/analytics are thin pass-throughs onto `ReportingRepository`'s CQRS read side; generation/scheduling delegate entirely to `ReportGenerationService`/`ScheduledReportService`. `app/schemas/reports.py` supplies every request/response DTO: `ReportFilters` (the one real validation surface — typed optional fields, never an arbitrary client JSON blob, with `date_from <= date_to` enforced once via a `model_validator`), `DateRangeParams`/`get_date_range_params` (shared `?date_from=&date_to=` parsing for the ten analytics trend endpoints), and full request/response models for report generation and scheduled-report CRUD.

## Authorization, tenant isolation, branch isolation

Two permissions exist for this module in migration 0002's seed data — `reports:read` and `reports:export` — and are applied consistently: `reports:read` gates every dashboard/analytics/catalog/status/download/history read; `reports:export` gates report generation and every scheduled-report write (create/update/pause/resume/delete/run-due), since both ultimately produce exportable output. This is the same "reuse an existing permission for a closely related capability" precedent `notifications.py` established for its own permission set.

`nursery_id` is always `tenant.org_id` — no route accepts a `nursery_id` parameter anywhere, so there is nothing for a client to override even maliciously. Two authorization shapes cover every route: `_authorize_branch_or_org` (dashboards/analytics/report-history list/report-and-scheduled-report creation) authorizes against the caller's own org plus an optional query/body `branch_id`; `_authorize_report`/`_authorize_scheduled` (by-id resource routes) fetch the row first and authorize against **its own** `nursery_id`/`branch_id` — a cross-tenant or cross-branch mismatch is a 403, a genuinely nonexistent id is a 404, matching every other by-id resource route in this codebase (`customers.py`'s `_authorize_customer` is the established precedent). An org-wide resource (`branch_id=None`) is visible to a branch-scoped caller regardless of which branch they're scoped to — this is intentional, pre-existing `AuthorizationService` behavior (branch-membership is only checked when `target_branch_id` is actually supplied), not a gap introduced by this module, and is exercised directly by `test_get_report_status_org_wide_report_accessible_to_branch_scoped_user`.

## Report generation: background processing, status tracking, secure download

`POST /reports` returns `202 Accepted` immediately with the freshly-created `Report` row in `PENDING` status, then runs `ReportGenerationService.generate` via FastAPI's `BackgroundTasks` — never blocking the HTTP request for a large report. The client polls `GET /reports/{id}` for `pending → processing → complete`/`failed`. `generate()` never raises back to its caller (there's no caller left awaiting it by the time it runs in a background task); any failure — a bad filter value, a missing dependency — is caught, persisted onto the `Report` row as `FAILED`, and published as `ReportFailed` so Module 11's `NotificationEventHandler` tells the requester, rather than leaving a silently-stuck `PENDING` row forever. `ReportResponse.download_url` is a stable `/reports/{id}/download` API reference, never the raw `Report.file_url` (a Cloudinary URL or local filesystem path) — the download route resolves it server-side, and for the local-storage fallback, `LocalFileStorage.resolve()` validates the resolved path stays inside the storage root before serving it (rejects `..`/path-separator tampering in a malformed filename).

## Scheduled reports: frequency, idempotency, paused/deleted-never-execute

`ScheduledReportCreateRequest`/`ScheduledReportUpdateRequest` validate `frequency` against the `ReportScheduleFrequency` enum and reject a past `next_run_at` at both creation and update time. `POST /reports/scheduled/run-due` calls `ScheduledReportService.run_due_for_org` — a tenant-scoped counterpart to the pre-existing, deliberately global `run_due` (meant for a single external cron trigger, never a tenant-scoped API caller) — added this session specifically so one organization's on-demand run-due call can never execute or advance another organization's due schedules as a side effect; this was caught and fixed during route design, before ever being exercised by a test, and is now covered by `test_run_due_executes_only_the_callers_own_org` at both the service and route layers. A paused schedule is never returned by `list_due` in the first place, and a deleted schedule can't be either (it no longer exists to fetch) — both "never execute" requirements are satisfied one layer down, at the repository query itself, verified by `test_paused_schedule_is_never_selected_by_run_due`/`test_deleted_schedule_cannot_be_executed` (service) and `test_run_due_never_executes_a_paused_schedule` (route). Execution is idempotent per invocation: each due row's `next_run_at` is advanced into the future before `_execute` returns, so an immediate second call against the same `now` will not re-select a row it just processed — verified by `test_run_due_for_org_is_idempotent_within_the_same_now`/`test_run_due_is_idempotent_within_the_same_request` at both layers. Notification delivery on generation completion/failure reuses Module 11's existing `ReportGenerated`/`ReportFailed` → `NotificationEventHandler` path — no new notification wiring was needed.

## Export formats

All four formats (PDF via `reportlab`, Excel via `openpyxl`, CSV via the stdlib `csv` module, JSON) render through one shared `exporters.render()` entry point so every one of the 18 report types produces correct output through the same four functions rather than each growing bespoke per-type export code. `test_export_format_*` (unit) and `test_generate_and_download_every_export_format` (integration, parametrized over all four formats end-to-end through the real route) decode each format back and assert structural correctness: CSV/JSON row content, an `openpyxl`-loadable workbook with the expected header row, and PDF magic-byte verification.

## Defects found and fixed this session (each with a regression test)

1. **Route-ordering bug**: `/reports/{report_id}` (parameterized) was initially registered before the static `/reports/scheduled*` paths, which would have swallowed every scheduled-report request as an invalid-UUID 422 — the same bug class Module 7 already caught once. Fixed by reordering; the file's own module docstring now documents the rule for future routes.
2. **Cross-tenant security bug in `run-due` design**: an early draft would have called the global `run_due()` from the tenant-scoped route, executing and advancing every organization's due schedules on one org's API call. Caught during design, before being exercised by a test. Fixed by adding `run_due_for_org`; regression-tested at both the service and route layer.
3. **FastAPI/pydantic forward-ref resolution bug**: `Depends()` off a bare `DateRangeParams` class (rather than a factory function) raised `PydanticUndefinedAnnotation` at route-registration time in a module using `from __future__ import annotations`, only discoverable by actually constructing the app. Fixed via the `get_date_range_params` factory-function pattern, documented in the schema module for future dependency classes.
4. **204 response-model assertion**: `DELETE /reports/scheduled/{id}` raised `AssertionError: Status code 204 must not have a response body` until `response_model=None` was added, matching `customers.py`'s existing precedent.
5. **mypy `Decimal * Numeric` finding** in `_profit_report` (pre-existing code, newly surfaced by this session's mypy run) — fixed via explicit `Decimal` casts; a dedicated regression test (`test_profit_report_computes_decimal_cogs_correctly`) exercises the exact computation against data shaped the way a real Postgres `Numeric` column round-trip produces it (the in-memory fake repository doesn't coerce types the way a real column does, so the test explicitly re-creates that coercion rather than silently passing against fake-only behavior).
6. **`ScheduledReportRepository.update()` accidentally dropped during an edit**, caught by mypy (`"ScheduledReportRepository" has no attribute "update_after_run"`) before ever reaching a test run.

## Remaining risks / disclosed gaps

- **No background-job scheduler.** `run_due`/`run_due_for_org` are on-demand sweeps (`POST /reports/scheduled/run-due`), the same disclosed gap Module 11's notification retry sweep already established — a real deployment needs an external cron trigger (a k8s CronJob curling the endpoint) to actually run schedules unattended; nothing in this codebase currently does that on a timer.
- **Cloudinary is unconfigured in every environment this code has run in** — `LocalFileStorage` (a fully working, not a no-op, fallback) is what every test and the live smoke test above actually exercised; the real `CloudinaryFileStorage` path is implemented but unverified against live credentials, matching every other "vendor credentials not present in this sandbox" disclosure already made for SMTP/Twilio/FCM/Anthropic in prior modules' reports.
- **Dashboard/analytics numbers are recomputed in pure Python by `FakeReportingRepository`** for every test — this mirrors the real materialized-view SQL closely enough to catch wiring bugs, but a genuine SQL-vs-Python arithmetic drift would only surface against a real Postgres instance, which this sandbox does not have.
