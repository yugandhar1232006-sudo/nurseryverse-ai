# Phase 6, Module 8 — Inventory & Stock Management

Real, running FastAPI code in `apps/api/app/`. This document explains the design decisions the module's requirements forced and records what was actually verified before calling it complete.

## Architecture: a separate bounded context, not a Plant subsystem

The module's spec is explicit: "Inventory is a separate bounded context. Do not duplicate plant data." Module 6 already established the two models as deliberately non-overlapping — individually-tracked Plants (a Digital Twin per plant) versus bulk Inventory (quantity-at-a-location, no per-unit identity). Module 8 keeps that boundary intact rather than eroding it: `InventoryService` never reads from or writes to `plants`, `growth_timeline`, or any other Module 6 table, and `PlantService` has no reference to `InventoryService`, the Inventory repositories, or the Inventory domain events. The two contexts integrate through exactly one narrow, optional channel, described below — everywhere else, they are independent.

This required one interpretive decision. The spec's ARCHITECTURE section lists `PlantRegistered`, `PlantMoved`, `PlantStatusChanged`, `PlantArchived` as example events feeding into "Inventory & Stock Events," which on a literal reading would mean Inventory subscribes to Plant lifecycle events and adjusts bulk quantities in reaction — e.g., registering an individually-tracked plant would decrement some bulk count. Module 6 already tried exactly this (a write-path hook bumping `inventory.quantity` on every Plant registration) and removed it after finding it caused double-counting: a plant that started as bulk stock, got individually tagged, and was later registered would be counted in both places at once, with no principled way to reconcile the two. That removal and its reasoning are recorded in `docs/ux/16-inventory-workflow.md`'s "Relationship to the Digital Twin" section. Module 8 treats the spec's Plant* event list as illustrative real-world triggers for Inventory's *own* vocabulary — a purchase order arriving is what produces `StockReceived`, not `PlantRegistered` — rather than a literal subscription list, and does not add any Plant-event handler to Inventory. `InventoryService` defines and publishes its own ten-type event vocabulary (`StockReceived`, `StockTransferred`, `StockReserved`, `StockReleased`, `StockAdjusted`, `StockDisposed`, `StockDamaged`, `StockSold`, plus `InventoryLocationCreated`/`InventoryArchived`), all with `aggregate_type="Inventory"`, and never subscribes to anything Module 6 publishes.

## The one Digital Twin coupling point

The spec also requires "Inventory Events... update... Digital Twin timelines." Module 7's own documentation claimed the Digital Twin's Inventory Timeline section would "always be empty... structurally inapplicable," reasoning that `inventory_adjustments.inventory_id` (as it was then named) FKs to the bulk `inventory` table, which had no `plant_id` column, so there was no valid join. Module 8 revisits that: it adds a nullable `plant_id` column to the renamed `stock_movements` table, populated only for the rare, already-documented case where a bulk-tracked line item corresponds to a specific plant being demoted out of individual tracking (or, symmetrically, a specific plant's stock movement being recorded against its own identity without duplicating its Digital Twin data). Whenever `StockMovement.plant_id` is non-null, `InventoryService._publish_movement_link()` publishes one additional event, `InventoryMovementRecorded`, with `aggregate_type="Plant"` and `aggregate_id=plant_id` (not `"Inventory"` — this event rides on the Plant's own event stream so the existing dispatcher routes it to the Digital Twin projector without any bulk-inventory-wide fan-out). This event_type was added to `DigitalTwinService.PROJECTED_EVENT_TYPES`, and one new handler, `_on_inventory_movement_recorded`, was added alongside the other thirteen — no new dispatcher registration, no change to `EventDispatcher` or `DomainEventPublisher` was needed, since both already fan out to every registered handler for any event type it declares interest in. This corrects Module 7's prior claim without contradicting Module 6's separation: the join now exists, but only fires for the narrow case where a movement is genuinely about an identified plant, never for ordinary bulk stock.

Every other Inventory event (received, transferred, reserved, released, adjusted, disposed, damaged, sold against bulk stock) has no `plant_id` and never reaches the Digital Twin. This is not a gap; it is the correct behavior for stock that was never associated with an individually-tracked plant in the first place.

## The inventory model (migration `0012`)

- **`inventory_locations`** — the location hierarchy the spec asks for (Nursery/Branch/Zone/Greenhouse/Outdoor/Rack/Bench/Section), modeled as a self-referencing tree: `parent_location_id` (nullable, `SET NULL` on delete) plus a `location_type` enum. Branch and Nursery levels are the existing `BranchScopedMixin`/tenant scoping; everything below Branch (Zone, Greenhouse, Outdoor Area, Rack, Bench, Section) is a row in this table pointing up the tree via `parent_location_id`. A location can be deactivated (`is_active=False`) without being deleted, preserving history for any `StockMovement` that referenced it.
- **`inventory`** (extended, not replaced) — one row per stock line (branch + category/species + optional location), now carrying `reserved_quantity`, `damaged_quantity`, `disposed_quantity` alongside the pre-existing `quantity`, each with a `>= 0` check constraint, plus a `reserved_damaged_le_quantity` constraint (reserved + damaged can never exceed total quantity — the invariant that makes "Available Quantity" a safe derived value rather than a separately-stored, driftable number). `available_quantity` is never stored; it is always computed as `quantity - reserved_quantity - damaged_quantity` at the API layer, so it can never itself drift out of sync. A new `version` column (default 1) is the optimistic-concurrency token, described below.
- **`stock_movements`** (renamed from `inventory_adjustments`) — the immutable ledger. Every stock-affecting action writes exactly one row here: `movement_type` is one of the ten required values (Incoming, Outgoing, Transfer, Adjustment, Waste, Damage, Reservation, Release, Sale, Archive); `from_location_id`/`to_location_id` are both present on every row (nullable individually — e.g., Incoming has no `from_location_id`, Sale has no `to_location_id` — but the pair is always populated where meaningful, satisfying "every movement carries source and destination"). `plant_id` is the optional Digital Twin linkage described above. `reservation_id` and `transfer_group_id` correlate a movement back to the reservation or transfer operation that produced it. Enforced immutable at the database level (REVOKE UPDATE/DELETE plus a rejection trigger, the same technique migrations `0004` and `0011` already established for `audit_logs` and `digital_twin_versions`) — a stock movement is a historical fact, never edited after the fact; corrections are new, offsetting movements (an `Adjustment`), never mutations.
- **`stock_reservations`** — one row per hold against available stock (Reservation → Release or Fulfill). `status` is `ACTIVE`/`RELEASED`/`FULFILLED`/`EXPIRED`. `reference_type`/`reference_id` are a loose, non-FK pointer to whatever business object created the hold (an order, a quote — nothing in this module or before it defines those tables yet, so this is deliberately not a foreign key, matching the same "loose pointer to a not-yet-existing table" pattern already used elsewhere in this schema rather than inventing a stub table).

## Movement ledger design: one write path, always paired

`InventoryService._apply_change()` is the *only* method in this module that ever mutates `Inventory.quantity`/`reserved_quantity`/`damaged_quantity`/`disposed_quantity`, and it always writes exactly one `StockMovement` row in the same call that performs the mutation — there is no code path that changes a quantity without a corresponding immutable ledger entry, and no code path that writes a ledger entry without the mutation it describes actually having happened. Every other service method (`receive_stock`, `transfer_stock`, `adjust_stock`, `mark_damaged`, `dispose_stock`, `sell_stock_direct`, the reservation lifecycle) is a thin, validated wrapper that computes the right delta(s) and location(s) and calls `_apply_change()` — this is what makes "Inventory History" (`GET /inventory/{id}/movements`) a complete, trustworthy audit trail rather than a best-effort log: it is structurally impossible for a quantity change to exist without a matching row explaining it.

`_apply_change()` also owns every quantity invariant: a resulting negative `quantity`/`reserved_quantity`/`damaged_quantity`/`disposed_quantity` is rejected, an Outgoing/Sale/Reservation that would exceed `available_quantity` is rejected as a `ConflictError` with `context={"reason": "insufficient_stock", ...}` (the spec's own named `InsufficientStockError`, satisfied via this codebase's deliberately closed exception hierarchy rather than a new exception class — the same convention that has held since Module 1).

## Reservation lifecycle

`reserve_stock` increments `reserved_quantity`, creates a `StockReservation` (`status=ACTIVE`), and writes a `StockMovement` (`movement_type=RESERVATION`, `quantity_delta=0` — a reservation moves stock from "available" to "reserved," not out of the location, so total `quantity` is unaffected). From there:

- `release_reservation` sets `status=RELEASED` and decrements `reserved_quantity` back — the hold is dropped, stock becomes available again, `quantity` unaffected.
- `fulfill_reservation` sets `status=FULFILLED` and decrements *both* `quantity` and `reserved_quantity` for real — the reserved stock has now actually left, recorded as a `movement_type=SALE` row. `fulfill_reservation` optionally accepts a `plant_id`, which is the one call site that can populate `StockMovement.plant_id` and trigger the Digital Twin linkage described above.

Both transitions reject a reservation that is not `ACTIVE` (a `ConflictError`) — a released or already-fulfilled reservation cannot be acted on again, matching the spec's own Release/Reservation semantics.

## Transfers: one method, two shapes

`transfer_stock` handles both cases the spec describes under Transfers:

- **Same-branch, different location**: a single `Inventory` row has its `location_id` updated in place; one `StockMovement` (`movement_type=TRANSFER`, `quantity_delta=0`, `from_location_id`/`to_location_id` set) records the move.
- **Cross-branch**: the source `Inventory` row is decremented (or archived, if fully transferred); the destination branch's matching line is found via `get_by_branch_and_name` or created if it doesn't yet exist, then incremented. Two `StockMovement` rows are written — one on each side — sharing a single `transfer_group_id` (a UUID) that correlates them as one logical transfer, so a transfer report can reconstruct "this stock left branch A and arrived at branch B" from two otherwise-independent ledger rows without needing a separate transfers table.

## Optimistic concurrency: "minimal locking" as a real constraint, not a slogan

The spec asks for "minimal locking" under concurrent updates. `Inventory.version` (an integer, default 1) is the concurrency-control column: `InventoryRepository.update(inventory, *, expected_version)` issues a conditional `UPDATE ... WHERE id = :id AND version = :expected_version` (incrementing `version` in the same statement) and returns the updated row, or `None` if `rowcount == 0` — meaning someone else's write already moved the version forward. Following this codebase's established convention (repositories are pure data access; only services raise `AppError` subclasses), the repository never raises on a conflict — it returns `None`, and `InventoryService._apply_change()` turns that `None` into a `ConflictError` with `context={"reason": "version_conflict"}`. This is optimistic, not pessimistic, locking: there is no `SELECT ... FOR UPDATE`, no held row lock across the request — a losing writer simply retries against the fresh version, which is the standard technique for keeping high-volume movement writes from serializing behind long-held locks.

## Reporting

Inventory Summary, Movement History, Low Stock, Waste, Transfer, Stock Valuation, and Reservation reports are all built from two pagination helpers, `_all_inventory()`/`_all_movements()`, which page through the same `list_for_nursery` repository methods every other query uses (200 rows/page) and aggregate in Python. This is a deliberate, disclosed tradeoff: it is correct for any dataset size and requires no new SQL, but it is not as efficient as a dedicated `SUM()`/`GROUP BY` query pushed down to Postgres. Given this module's actual data volumes (line items per branch, not per-plant event volume), and consistent with this project's pattern of disclosing performance tradeoffs rather than hiding them (Module 7 made the identical disclosure about its own snapshot-vs-replay design), this was judged the right tradeoff for now; a future optimization pass could replace the aggregation helpers with real SQL aggregates without changing any route or schema.

## Authorization

Inventory reuses the existing `inventory:read`/`inventory:write`/`inventory:adjust` permission codes (already defined from Module 6's original bulk-inventory routes) rather than minting new ones — Inventory Locations and Stock Reservations are both views onto the same bounded context a caller already needs `inventory:read`/`write` for, the same reasoning Module 7 applied reusing `plants:read` for Digital Twin routes. Every by-branch and by-resource route authorizes against the resource's real `nursery_id`/`branch_id` via `AuthorizationService.authorize()` called at the route layer only — never inside `InventoryService` or `InventoryLocationService` — matching the pattern established since Module 5 and re-confirmed against `plant_service.py`/`plants.py` before writing this module's routes. Cross-tenant access is rejected the same way every prior module's is: fetch-then-authorize against the resource's actual tenant, not the caller's claimed one.

## Testing

570 tests total (489 pre-existing Modules 1–7 + 81 new): 52 unit (`test_inventory_service.py`), 29 integration (`test_inventory_routes.py`).

- **Movement workflow tests**: one per movement type (receive, transfer same-branch, transfer cross-branch, reserve, release, fulfill, sell direct, damage, dispose, adjust up/down, archive), each asserting both the resulting `Inventory` quantities and the exact `StockMovement` row written (type, delta, locations).
- **Reservation tests**: full lifecycle (reserve → release, reserve → fulfill), double-release/double-fulfill rejection, fulfill-with-plant_id triggering the Digital Twin linkage (`test_fulfill_reservation_with_plant_id_publishes_digital_twin_linkage`), insufficient-available-stock rejection.
- **Transfer tests**: same-branch in-place move; cross-branch decrement-source/create-destination; cross-branch decrement-source/reuse-existing-destination; `transfer_group_id` correlation asserted across both resulting rows.
- **Concurrency tests**: a stale `Inventory` object (captured `version` before a later write moved it forward) passed directly into `_apply_change()` raises `ConflictError` with `reason=version_conflict` — the version-mismatch *logic* is proven correct at both the fake-repository layer and the service layer, with the disclosed limitation (below) that true concurrent-write races are not reproducible against single-threaded in-memory fakes.
- **Cross-tenant tests**: every by-ID route (inventory line, location, reservation) rejected for `CROSS_TENANT_ORG`, mirroring every prior module's own cross-tenant suite.
- **Inventory projection test**: the one Digital Twin coupling point is proven end-to-end — `fulfill_reservation(..., plant_id=...)` results in a `plant.inventory_movement_recorded` event that the shared dispatcher routes to `DigitalTwinEventHandler`, verified against the live `digital_twin_service` snapshot's new `inventory_movements` count and `latest.inventory_movement` fields.
- **Authorization**: 401 unauthenticated, 403 missing permission, 403 cross-tenant, for every route.
- **Immutability**: `PATCH`/`PUT`/`DELETE` to any stock-movement path return 404/405 (no such route exists — movements are only ever created via the domain actions, never edited directly), the same technique Module 6 and Module 7 used to prove their own immutable tables.

**Coverage**: **100%** on both new core files (`inventory_service.py` — 273 stmts; `routes/inventory.py` — 198 stmts).

### Pre-completion validation checklist (from the module's own spec)

- Inventory is independent of individual plant lifecycle — verified structurally: no Inventory code path reads or writes any Module 6 table; the only coupling is the one optional, outbound `InventoryMovementRecorded` event.
- Every stock change is recorded as an immutable Stock Movement — enforced by `_apply_change()` being the sole write path (always pairs a mutation with a movement row) and by database-level immutability (REVOKE + trigger) on `stock_movements`.
- Every movement carries source and destination — `from_location_id`/`to_location_id` populated on every row where meaningful, tested per movement type.
- Reservations correctly hold and release stock — tested through the full lifecycle, including the reserved+damaged ≤ quantity database constraint.
- Transfers correctly move stock between locations/branches — tested for both same-branch and cross-branch shapes, including destination find-or-create.
- Inventory Events update Digital Twin timelines — tested end-to-end for the one case where they apply (`plant_id`-linked movements); correctly does not fire for ordinary bulk movements, which is the intended behavior, not a gap.
- Reporting is accurate and efficient enough for current volumes — tested for correctness; the pagination-based aggregation tradeoff is disclosed above rather than hidden.
- Authorization is enforced, including branch-level and cross-tenant — tested extensively, reusing `inventory:read`/`write`/`adjust`.
- Concurrent updates are handled safely with minimal locking — optimistic `version` column proven correct at the logic level; true concurrent-write races remain unverified against real infrastructure (see below).
- OpenAPI documentation is complete — confirmed live: 24 new paths, all with `response_model`s and summaries.

## What remains unverified

Same disclosed limitation as every prior module: no live PostgreSQL or Redis instance is reachable in this sandbox. The real `SqlAlchemyInventoryRepository`'s conditional `UPDATE ... WHERE version = :expected_version` (including its actual behavior under genuinely concurrent transactions — whether Postgres's own MVCC guarantees serialize the two writers the way the logic assumes, and whether the `rowcount == 0` signal is reliably observed by the losing writer under real contention), the `stock_movements` immutability trigger's real enforcement, and the four new check constraints' real enforcement under concurrent writes have been validated for correct query construction and exercised end-to-end through the app's HTTP layer against in-memory fakes, but not against real concurrent load. The in-memory fakes' single-threaded execution model cannot reproduce a true write race by construction — this was disclosed rather than papered over, consistent with Module 7's own equivalent disclosure.
