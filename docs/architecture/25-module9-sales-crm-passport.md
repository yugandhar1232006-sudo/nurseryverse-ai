# Phase 6, Module 9 — Sales, CRM, Plant Passport & QR Intelligence

Real, running FastAPI code in `apps/api/app/`. This document explains the design decisions the module's requirements forced and records what was actually verified before calling it complete.

## Architecture: a separate bounded context, reacting to Inventory, never coupled to Plant Lifecycle

The module's spec is explicit: "Sales must remain its own bounded context. Do not couple Sales directly to Plant Lifecycle. Sales must react to lifecycle and inventory events." Concretely, `SalesOrderService`/`CustomerService`/`PaymentService`/`ReturnService`/`RefundService` never read or write `plants`, `growth_timeline`, or any other Module 6 table, and never call `PlantService`. The one place Sales touches inventory is a legitimate, in-request service call — `SalesOrderService.confirm_order()`/`checkout()` call `InventoryService.reserve_stock()`/`fulfill_reservation()`/`sell_stock_direct()` directly for bulk-tracked line items, reusing `StockReservation.reference_type`/`reference_id`, which Module 8 built as a deliberately loose, non-FK pointer for exactly this caller. A direct, transactional, in-request service call ("take a stock hold as part of confirming an order") is a different thing from the forbidden direction the spec actually names: nowhere in this module does Sales call `PlantService` or flip `Plant.status` to `SOLD` — see `PlantSold`'s own docstring in `app/domain_events/events.py` for the reasoning behind that specific, deliberate omission (Plant Lifecycle's own state machine, not Sales, owns that transition; Sales only *publishes* the fact via a domain event).

`Sale`/`SaleItem`/`Invoice`/`InvoiceItem`/`InvoiceSale`/`Payment`/`Passport` are pre-existing Phase 5 tables (migration `0001`) that no prior module built on. `SalesOrder` is this module's own pre-completion lifecycle wrapper: a `Quotation` may convert to a `SalesOrder`, which moves through `DRAFT → CONFIRMED → PROCESSING → FULFILLED`/`CANCELLED`; `checkout()` is the one method that, on success, creates exactly one `Sale` row (+ one `Invoice`, if requested) from the order — `SalesOrder` and `Sale` are not the same concept renamed twice: `SalesOrder` is the negotiable, mutable pipeline object; `Sale` is the immutable transaction record it produces.

## Plant Passport as this module's own bounded context, not a Sales→Plant coupling

`SalesOrderService.checkout()` also generates a Plant Passport for every plant-tracked line item, synchronously, in the same request — calling `PassportService.generate_passport()` directly, not just publishing an event for some other module to react to later. This is deliberate, and it is not the forbidden Sales→Plant-Lifecycle coupling: this module's own name is "Sales, CRM, **Plant Passport** & QR Intelligence" — Passport is Sales' sibling bounded context within the *same* module, not Plant Lifecycle's. `PassportService` itself never calls `PlantService` and never writes to `plants`; it only *reads* an already-registered `Plant` row (passed in by the caller) to build the frozen `content_snapshot`, exactly the same read-only relationship `app/api/routes/passport.py`'s internal `generate_passport` route already has to `PlantRepository`.

## Digital Twin Integration: Sales/Ownership/Revenue timelines, and the one architectural tension this module surfaced

The spec asks for Sales events to update three things: "Sales Timeline," "Ownership Timeline," "Revenue Timeline," via domain events only. `DigitalTwinService.project(event)` uses `event.aggregate_id` directly as the twin's `plant_id` lookup key — so only events whose `aggregate_type == "Plant"` can feed the *per-plant* twin at all. Of this module's ten published event types (`OrderCreated`, `ReservationCreated`, `ReservationReleased`, `InvoiceGenerated`, `PaymentReceived`, `PlantSold`, `PlantReturned`, `RefundProcessed`, `PassportGenerated`, `QRGenerated`), only four — `PlantSold`, `PlantReturned`, `PassportGenerated`, `QRGenerated` — carry `aggregate_type="Plant"`; the rest (`OrderCreated`, `ReservationCreated`/`Released`, `InvoiceGenerated`, `PaymentReceived`, `RefundProcessed`) carry `aggregate_type="Invoice"`/`"Refund"`/`"SalesOrder"`, because they are facts about an order/invoice/refund, not about one specific plant, and most have no single `plant_id` to attribute them to at all (an order can span many line items).

This is resolved, not worked around, as follows:

- **Ownership Timeline** and the plant-scoped slice of **Sales/Revenue Timeline** are served by the per-plant twin: `_on_plant_sold` flips the new `snapshot["ownership"]` field from `{"owner_type": "nursery", ...}` to `{"owner_type": "customer", "customer_id": ..., "since": ...}` and records `snapshot["latest"]["sale"]`; `_on_plant_returned` flips ownership back and records `snapshot["latest"]["return"]` (including an enrichment read via the new `ReturnItemRepository.get_by_id` for `line_refund_amount`, the same "payload carries only an id, service fetches the row" pattern `_on_growth_recorded` and others already use). Four new snapshot count keys (`plant_sold`, `plant_returned`, `passports_generated`, `qr_generated`) and four new `latest.*` keys (`sale`, `return`, `passport`, `qr`) were added, following the identical shape every prior event type already uses.
- **Full historical Sales Timeline** (every order/invoice/payment/refund event, not just the two plant-scoped ones) is served by the *existing*, already-general `get_timeline`/`get_event_history` query methods, filtered client-side by `event_type` — exactly how Growth/Health Timeline already work. `DigitalTwin.snapshot` only ever stores latest-value summaries and counts, never growing lists (per the model's own docstring), so this was never going to be a snapshot-field concern regardless of aggregate type.
- **Nursery-wide Revenue Reports** (the module's own Reports section, distinct from a single plant's Digital Twin) are correctly served by `SalesReportingService.revenue_report`/`sales_report`, which aggregate real `Sale` rows — not routed through the per-plant Digital Twin projector at all, which was never the right mechanism for a nursery-wide rollup in the first place.

This is disclosed here rather than left as a silent gap: `PaymentReceived`/`InvoiceGenerated`/`RefundProcessed` genuinely cannot and do not reach the per-plant twin's snapshot, by the projector's own `aggregate_id`-as-`plant_id` design (a Module 7 decision, not something this module could or should change) — and they don't need to, since both alternative paths above already correctly serve what those events would have shown.

## Live-smoke-test-only bugs: two real gaps the unit/integration suite could not catch

Both were found by booting the app with real `uvicorn` and hitting it with `curl` — a step the test suite's own dependency-override mechanism structurally cannot exercise, since it replaces every service factory with a direct harness reference rather than resolving `app/api/deps.py`'s real dependency graph.

**Bug 1 — public passport/QR routes silently required a bearer token.** `app/api/routes/passport.py`'s `public_router` (`GET /public/passport/{token}`, `GET /public/qr/{token}`) takes no `User`/`TenantContext`/`get_current_user` parameter at the route level — by inspection, this looked correct. But `get_passport_service`'s `audit_repo` parameter resolved via `get_audit_log_repository` → `get_scoped_db` → `get_tenant_context` → `get_current_user`, and `get_qr_service` depended on `get_passport_service`. A recursive walk of the real FastAPI dependency tree (not just the route's own direct parameters) showed the actual chain; a live `curl` with no `Authorization` header confirmed it: both public endpoints returned `401 {"message": "Missing bearer token."}` instead of reaching the token-verification logic at all. This directly violated the module's own hard requirement ("Customers must NOT authenticate... access controlled by secure public tokens only") and would have been shipped, since neither the unit tests (construct `PassportService`/`QRService` directly, no DI graph involved) nor the integration tests (override `get_passport_service`/`get_qr_service` themselves, short-circuiting the graph one level above the bug) ever resolved the real chain.

  Fix: `app/api/deps.py` gained `get_unscoped_audit_log_repository` (same repository class, built off plain `get_db` instead of `get_scoped_db` — safe because `PassportService.get_passport_by_token`/`QRService.scan` never call `self._audit` at all; only `generate_passport`, reachable exclusively from the authenticated internal route, does) and `get_public_passport_service` (identical to `get_passport_service` except for that one substitution). `get_qr_service` and the public `get_public_passport` route now depend on `get_public_passport_service`, not `get_passport_service`. The internal, authenticated `router`'s three passport routes are untouched and still use the original `get_passport_service`. Verified by re-walking the dependency tree (zero `get_current_user` node reachable from either public route) and by a live `curl` with no `Authorization` header returning `404` (correct — token not found) instead of `401`.

**Bug 2 — QR scan's live health/growth/fertilizer reads would have returned nothing under real RLS.** `QRService.scan()` reads `plants`/`growth_timeline`/`health_history`/`fertilizer_logs` for the "live data, not just the frozen snapshot" half of a QR scan (see that method's own docstring on the deliberate frozen-vs-live asymmetry). All four are RLS-protected (migration `0003`'s `DIRECT_TENANT_TABLES`/`JOIN_TENANT_TABLES`), and the public QR path has no `app.current_org_id` to scope with — by design, per migration `0003`'s own documented exemption for `passports`: "the public tokenized read path... is intentionally unauthenticated and has no org context at all; access control is the signed, time-scoped token itself." Under real Postgres, RLS doesn't error on a missing session variable — it silently filters every row, so `health_status`/`growth_timeline`/`fertilizer_schedule` would have come back null on every public scan, forever, with no exception ever raised to reveal why. This sandbox has no live Postgres, so it could not be observed directly; it was found by reasoning through migration `0003`'s own table list against what `QRService.scan` actually reads, while investigating Bug 1.

  Fix: migration `0014` adds one additional, narrow, SELECT-only RLS policy per table (`plants.id`, `growth_timeline.plant_id`, `health_history.plant_id`, `fertilizer_logs.plant_id`), keyed against a new session variable, `app.qr_scan_plant_id`. `QRService` now optionally carries the raw `AsyncSession` (`db: AsyncSession | None = None` — unused by the Fake-repository test harness, which passes none) and, immediately after `PassportService.get_passport_by_token` succeeds, calls `_scope_to_verified_plant(passport.plant_id)`, which issues `SELECT set_config('app.qr_scan_plant_id', :val, true)` on that same session. This is not a blanket RLS bypass: no INSERT/UPDATE/DELETE policy is added, the variable is set to exactly one plant id per request — the one a cryptographically verified, unguessable, HMAC-signed token already unlocked — and it is never set anywhere on the internal authenticated request path, so the existing `app.current_org_id` tenant-isolation policies from migration `0003` are untouched and still fully enforced for staff. Migration `0014`'s own docstring records the full reasoning. Unverifiable end-to-end without a live Postgres instance (disclosed below), but the policy SQL and dependency wiring were validated via `scripts/validate_migrations_offline.sh`'s full offline chain generation (`base → 0014`, 3,130 lines, zero errors, RLS policy count 55 → 59 as expected for four new tables).

## The Plant Passport token (unchanged from the session that built it, re-verified this session)

`Passport.public_token` is a compact, self-contained, HMAC-SHA256-signed opaque token — not a JWT (whose base64 claims are human-readable once decoded) and not a bare random string relying only on database uniqueness. Binary layout, base64url-encoded: `[passport_id (16B) | nonce (12B) | expires_at epoch (8B, 0 = never) | HMAC-SHA256 truncated to 16B]`. The signature is verified with `hmac.compare_digest` (constant-time) before the payload is trusted; `get_passport_by_token` raises the identical generic `NotFoundError` for "no such token," "forged/tampered," and "expired" — deliberately undifferentiated, so a public caller can never learn *why* a guess failed. The token payload never carries `plant_id`/`nursery_id`/`branch_id`; the public response schemas (`PublicPassportResponse`/`QRScanResponse`) never include any database id, and `passport_number` is a one-way SHA-256 digest of the passport's own UUID (`NVA-PP-XXXXXXXX`), never a truncation of the raw id's own characters.

## Testing

**628 tests total** (570 pre-existing Modules 1–8 + 58 new): 36 new unit tests across `test_sales_service.py` (17), `test_passport_service.py` (13), `test_customer_service.py` (6); 22 new integration tests across `test_sales_routes.py` (6), `test_passport_routes.py` (10), `test_customer_routes.py` (6).

- **Sales workflow tests**: quotation → conversion → order → confirm/reserve → checkout → sale + invoice + passport generation, in one continuous flow, asserting every intermediate status transition.
- **Reservation tests**: create, release, fulfill, double-fulfill rejection, insufficient-stock rejection (delegated to and re-verified against Module 8's `InventoryService`).
- **Payment tests**: cash/UPI/card/bank-transfer methods, multiple partial payments summing toward `PAID`, payment history retrieval.
- **Passport tests**: version-1 generation, append-only re-generation (version N+1, never an overwrite), token round-trip, forged-token rejection, tampered-middle-byte rejection, wrong-signing-secret rejection, expired-token rejection, unexpired-with-configured-expiry success, public-response-never-leaks-internal-ids.
- **QR validation tests**: all seven required response sections present, a scan event is recorded, live health data (not the frozen snapshot) is what's returned, invalid token raises the same generic not-found.
- **Public token security tests** (integration): `GET /public/passport/{token}`/`GET /public/qr/{token}` reachable with literally no `Authorization` header sent; forged and tampered tokens both return `404` with the *identical* error body as a straightforwardly nonexistent token (no oracle).
- **Cross-tenant tests**: passport generation against a foreign-org plant rejected with `cross_tenant_org`, matching every prior module's own suite.
- **Customer/CRM tests**: profile CRUD, contacts/addresses/tags/notes/communications as child collections, purchase history aggregation, analytics (total orders/spend/average order value), customer report (top-N by spend).

Two real, production-affecting bugs were caught and fixed by this suite during development (both in the initial implementation, before the live smoke test found the two DI/RLS bugs above): a `_money()` quantization bug where `Decimal` arithmetic between two already-2-place values could still produce 3 decimal places (`total_amount` persisting as `"55.000"` instead of `"55.00"`), and a `Quotation → SalesOrder` conversion silently dropping the effective tax rate (the `Quotation` model persists only the resulting `tax_amount`, not the `tax_rate` fraction that produced it), both caught by `test_full_sales_workflow` asserting exact totals and fixed by, respectively, always-quantize semantics in `_money()` and re-deriving `effective_tax_rate` algebraically from the quotation's own stored subtotal/discount/tax at conversion time.

## Authorization

Quotations and Sales Orders reuse the pre-seeded `sales:read`/`sales:write`/`sales:void` permission codes (they are Sales' own pre-completion pipeline); Payments reuse `invoices:read`/`invoices:write`/`invoices:void` (a payment is recorded against an Invoice); Returns reuse `sales:*` (`sales:void` for the reversal-finalizing `complete` action); Refunds reuse `invoices:*` (same money-movement ledger family as Payments); Passport/QR internal routes use the new `passport:generate`/`passport:read` codes. Every internal route authorizes via `AuthorizationService.authorize()` called at the route layer only, fetch-then-authorize against the resource's real `nursery_id`/`branch_id`, matching the pattern held since Module 3. The public passport/QR surface uses no `AuthorizationService` call at all — by design, per the module's own instruction ("Public Plant Passport APIs use signed tokens only") — access control is entirely the cryptographic token verification described above, never bypassed, never weakened by a fallback authorization path.

### Pre-completion validation checklist (from the module's own spec)

- Orders complete correctly — verified end-to-end: quotation → order → confirm (reserve stock) → checkout (fulfill reservation, create Sale + Invoice + Passport-per-plant, publish `PlantSold`).
- Inventory updates correctly — checkout calls Module 8's real `InventoryService.fulfill_reservation`/`sell_stock_direct`; stock quantities and the `StockMovement` ledger are asserted in the workflow test.
- Digital Twin updates through events — verified for the two plant-scoped events (`PlantSold`/`PlantReturned` flip `ownership`, populate `latest.sale`/`latest.return`) and for `PassportGenerated`/`QRGenerated` (new count fields); the "full Sales/Revenue Timeline" resolution via `get_timeline`/`SalesReportingService` (not the per-plant snapshot) is architecturally explained above, not a gap.
- Passport generation works — version-1 and append-only-versioned re-generation both tested; snapshot content (origin, care guide, growth/health timeline, purchase information) verified field-by-field.
- QR scanning works — all seven required response sections present; live-data-not-frozen-snapshot asymmetry tested; now correctly reachable with zero authentication (Bug 1) and, at the schema level, correctly able to read the RLS-protected live tables it needs once a token verifies (Bug 2, migration `0014`).
- Public tokens cannot be forged — HMAC signature verification tested against forged, tampered, wrong-secret, and expired tokens, all rejected with the identical generic error.
- Authorization works — every internal route tested for `401`/`403 (missing permission)`/`403 (cross-tenant)`; the public surface tested for reachability with zero auth (not a gap, the spec's own requirement) and for RLS narrowness (migration `0014`'s policies are SELECT-only, single-plant-scoped, and provably don't weaken the existing tenant-isolation policies).
- Reports are correct — Sales/Revenue/Customer/Passport reports each have a dedicated test asserting exact aggregated figures; QR Scan Analytics counts scan events per passport.
- OpenAPI documentation is complete — confirmed live: 46 new paths, all with `response_model`s, summaries, and error-response schemas.

## What remains unverified

Same disclosed limitation as every prior module: no live PostgreSQL or Redis instance is reachable in this sandbox. Three things specifically could not be exercised end-to-end as a result: (1) migration `0014`'s new RLS policies' real enforcement — the policy SQL was validated for correctness via Alembic's offline SQL generation and reasoned through against migration `0003`'s existing, already-proven pattern, but was never run against a real Postgres instance to confirm Postgres actually OR-combines the new permissive policy with the existing tenant-isolation one the way this design assumes; (2) the invoice-numbering scheme (`INV-<year>-<sequence>`, a simple count-based-per-nursery approach, not a dedicated database sequence) is correct in the single-writer path this module is verified against but not proven race-safe under two genuinely concurrent checkouts for the same nursery — disclosed rather than silently assumed safe, matching Module 8's identical disclosure about its own optimistic-concurrency column; (3) `PASSPORT_TOKEN_SECRET` resolution's production fail-fast behavior (`resolve_passport_token_secret` refuses to start in production without an explicit secret) was verified by code inspection and the ephemeral-dev-secret fallback was exercised throughout testing, but the fail-fast path itself was not triggered against a `settings.is_production=True` live process in this sandbox.
