# Phase 6, Module 3 — Authorization & RBAC

Real, running FastAPI code in `apps/api/app/`. This document explains the design decisions the module's requirements forced and records what was actually verified before calling it complete.

## Schema change: migration 0008

Phase 5/Module 2's schema had nowhere to record *why* a request was denied — `security_events` (Module 2) covers the authentication lifecycle (login/logout/lockout), and `audit_logs` (Phase 5) requires a non-null `nursery_id` and only records successful, completed actions. Neither fits "user X tried to do Y and was refused." Per this module's explicit rule, migrations 0001-0007 were never touched; everything new is `migrations/versions/0008_authorization_denials.py`:

- `authorization_denials` — one row per denied `AuthorizationService.authorize()` call: `user_id`, `permission_code`, `resource_type`/`resource_id`, `nursery_id`/`branch_id` (nullable — a denial can happen before either is known, e.g. `NO_ORG_CONTEXT`), `reason` (the new `authorization_denial_reason` enum), `explanation`, `request_id`, `ip_address`, `created_at`. Three composite indexes (`user_id, created_at`; `nursery_id, created_at`; `reason, created_at`) for the investigation queries this table exists to answer ("what has this user been denied", "what's been denied in this org", "how often is X reason firing").

Generated the same mechanical way as 0001/0007 (`scripts/generate_migration_0008.py`), re-validated with the full offline chain (`scripts/validate_migrations_offline.sh`): 56 tables, 22 enums, 40 RLS policies, 18 triggers, 291 seed rows, zero errors across 2,252 lines of generated SQL.

## The single choke point: `AuthorizationService.authorize()`

Every permission/tenant/ownership decision in the system — today's `require_permission`/`require_org_match`/`require_branch_match`/`require_ownership_or_permission` FastAPI dependencies (`app/api/deps.py`), and every future module's route protection — funnels through one method: `app/services/authorization_service.py`'s `AuthorizationService.authorize()`. It never raises; it returns an `AuthorizationDecision` (`allowed`, `explanation`, `reason`, plus everything that went into the decision), which is what makes "every authorization decision must be explainable" concretely true rather than just a design goal — the decision object itself *is* the explanation, inspectable in a debugger, a test assertion, or the denial audit row. The FastAPI dependency layer is a thin wrapper that turns `allowed=False` into a raised `PermissionDeniedError` and persists the denial; there is no second, looser code path a route could accidentally use instead.

The check order is fixed and deliberate — **Nursery → Branch → Resource**, matching the module's required enforcement chain: account-active, then org match (if a target org was given), then branch match (if a target branch was given, and only when the caller's role is branch-scoped — see below), then permission membership or ownership. Org mismatch is checked and denied *before* branch is even considered, so a branch ID that happens to belong to a different org can never be compared against the caller's branch scope in the first place (`tests/unit/test_cross_tenant_isolation.py::test_branch_manager_of_org_a_branch_cannot_reach_org_bs_matching_branch_id` covers exactly this ordering).

## RBAC stays fully database-driven

Nothing new changes Module 2's core RBAC design: `app/services/permission_service.py` still resolves a user's role and permissions only from Phase 5's `role_assignments → roles → role_permissions → permissions` tables, seeded from `docs/ux/07-role-permission-matrix.md`. Module 3's addition is `ResolvedAccess`, a small frozen dataclass wrapping that resolution (`org_id`, `role_id`, `role_code`, `branch_ids`, `permissions`) with one piece of interpretation centralized in exactly one place: `is_org_wide()`. Per `RoleAssignmentBranchScope`'s own Phase-5 docstring, an *absent* set of branch-scope rows means "every branch" (how Owner/Org Admin are modeled — org-wide roles never get branch_scopes rows at all), not "no branches." Every caller — `AuthorizationService`, and every future module's route dependencies — reads that interpretation off `ResolvedAccess.is_org_wide()` instead of each re-deriving "empty list means what, again?" independently. No role name or permission code is hardcoded into any `if role == "owner"`-style branch anywhere in this module; the only place a role code is compared is `explanation` strings (for human readability) and test fixtures (which are simulating the seed data, not replacing it).

Inheritance was **not** modeled — the module's requirement was "support inheritance only if explicitly modeled," and nothing in the approved role/permission matrix (Phases 1-4) defines a parent/child role relationship. Adding one now would be speculative; if a future module's requirements introduce it, it's a data-model change to `roles` (e.g. a `parent_role_id` column) plus a migration, not a shortcut taken here.

## Multi-role future-readiness

`PermissionRepository.list_role_assignments_for_user` and `PermissionService.resolve_all_for_user` already resolve *every* `RoleAssignment` a user holds into a list of `ResolvedAccess`, not just the first. v1's application-layer constraint (one org per user — `RoleAssignment`'s own docstring) means this returns 0 or 1 entries today; if that constraint is ever lifted by a future module, no code here needs to change, only the underlying data. `resolve_for_user` (the one used by `AuthorizationService` and route dependencies today) is unaffected — it still resolves the single "primary" assignment, per v1's actual product behavior.

## Permission caching

`app/core/cache.py` defines a generic `Cache` protocol (`get`/`set`/`delete`/`delete_prefix`) with two implementations, mirroring the exact pattern Module 2 already established for the rate limiter: `InMemoryCache` (dict + monotonic expiry, always available) and `RedisCache` (real `redis.asyncio`, `SCAN`-based `delete_prefix` rather than `KEYS` — `KEYS` blocks the whole Redis instance on a large keyspace, `SCAN` is the production-safe iteration primitive). `app/main.py`'s `create_app` sets `app.state.cache = InMemoryCache()` immediately (so ASGI test transports that skip lifespan events still get a working cache), and `_try_upgrade_to_redis_cache` attempts a real Redis connection during `lifespan`, swapping in `RedisCache` if reachable and logging a warning (not crashing) if not — verified live: booting under real `uvicorn` with no Redis reachable logged `redis_unreachable_using_in_memory_cache` and kept serving requests normally.

`PermissionService.resolve_for_user` checks the cache first, falls back to the database on a miss, and populates the cache with a 5-minute safety-net TTL. The primary invalidation path is explicit, not time-based: `invalidate_user(user_id)` deletes the cache entry immediately, and any future code path that changes a user's role, branch scope, or a role's permission set (Module 4's RBAC management endpoints, Module 5's employee role changes) is required to call it. Without an explicit call, a revoked permission remains effective for up to the TTL — a real, bounded, and honestly documented exposure window, not a silent gap (`tests/unit/test_privilege_escalation.py::test_stale_cache_without_invalidation_would_still_be_closed_by_ttl` asserts the window exists and is bounded; `test_revoked_role_stops_granting_access_immediately_after_invalidation` asserts the explicit path closes it immediately).

## Authorization middleware: four dependency factories, not four bespoke checks

`app/api/deps.py` adds four FastAPI dependency *factories* (each call returns a fresh closure, so two routes needing different permissions never collide):

- **`require_permission(permission)`** — the common case: "this route requires `<module>:<action>`," no path-scoped tenant, no ownership fallback. Used by `GET /api/v1/audit-log`.
- **`require_org_match(permission, nursery_id_param="nursery_id")`** — for routes shaped like `/nurseries/{nursery_id}/...`: requires the permission *and* that the path's org matches the caller's own. Not yet used by a route (Module 3 owns no org-scoped resource routes of its own beyond the audit log, which is org-implicit rather than path-scoped) — built and unit-tested now (`tests/unit/test_authz_dependencies.py`) so Module 6+ (Nursery Management) can depend on it directly instead of re-deriving the same path-param-to-`authorize()`-call wiring.
- **`require_branch_match(permission, ...)`** — adds branch-path-param matching on top of org match, honoring `ResolvedAccess.is_org_wide()`'s scoping.
- **`require_ownership_or_permission(permission, resolve_owner_id=None)`** — allowed via the permission *or* via a caller-supplied async resource-owner lookup (e.g. "is this the customer's own order"). `resolve_owner_id` is intentionally a parameter, not a fixed path-param convention: "who owns this resource" is a per-resource-type question this module — which owns no business resources itself — can't answer generically; Module 6+ pass their own resolver when they wire this up for a real resource.

All four raise `PermissionDeniedError` (403, the standard error envelope) on denial and return the `AuthorizationDecision` on success, so a route can inspect *why* it was allowed (e.g. via ownership vs. via the blanket permission) if it needs to.

## Multi-tenancy: two independent enforcement layers

**Application layer**: `get_tenant_context` resolves the caller's `TenantContext` (org id, branch ids, role, permissions) once per request — cheap, since `PermissionService` caches it — and every `require_*` dependency checks against it via `AuthorizationService`. **Database layer**: `get_scoped_db` wraps `get_db` and issues `SELECT set_config('app.current_org_id', :val, true)` at the start of the request's transaction — the session variable Phase 5's RLS policies (`migrations/versions/0003_row_level_security.py`) key against via `current_setting('app.current_org_id', true)::uuid`. Deliberately `set_config` with a bound parameter, not a raw `SET LOCAL app.current_org_id = '<value>'` string — Postgres's `SET` doesn't accept bind parameters, and string-formatting a session variable is an injection risk even for a server-computed UUID; `set_config`'s third argument (`true`) makes it transaction-local, matching `SET LOCAL` semantics so the value never leaks to a pooled connection's next transaction. This is defense in depth on purpose: even a bug in a route's own application-layer filter (an accidentally-omitted `WHERE nursery_id = ...`) still can't leak cross-tenant rows, because Postgres itself is filtering them. `GET /api/v1/audit-log` (see below) applies both layers, not just one, and its own docstring explains why the application-level filter isn't redundant with RLS: it's what makes pagination *counts* correct in contexts (like the in-memory fake-backed unit tests) where there is no real RLS to fall back on.

## Auditing: every denial, with full context

`_deny()` (the single internal path every denial branch in `authorize()` routes through) writes an `AuthorizationDenial` row via `AuthorizationDenialRepository.log()` with exactly the fields the module requires: `user_id`, `permission_code`, `resource_type`/`resource_id`, `nursery_id`/`branch_id`, `reason` (one of `MISSING_PERMISSION`, `CROSS_TENANT_ORG`, `CROSS_TENANT_BRANCH`, `NOT_OWNER`, `ACCOUNT_INACTIVE`, `NO_ORG_CONTEXT`), a human-readable `explanation`, and `request_id`/`ip_address` from the request's `RequestContext`. Allowed decisions never write a row — only failures are audited here, by design (successful actions belong in `audit_logs`, Phase 5, once a module actually performs one). `persist_denial=False` exists for the rare case a caller wants a dry-run decision without an audit side effect (not used by any route today, but available to a future "preview my permissions" endpoint).

## The worked example: `GET /api/v1/audit-log`

The module's requirements point at a real, useful endpoint protected end-to-end, not a synthetic test route — `audit:read` is a genuine seeded permission (`docs/ux/07-role-permission-matrix.md` line 78: Full for Owner/Org Admin, no access for anyone else), and the audit log itself (Phase 5's `audit_logs` table) is exactly the kind of sensitive, org-scoped data multi-tenancy and permission enforcement exist to protect. The route depends on `get_audit_log_repository` (an injectable Protocol-typed dependency, following the same pattern every other module-2/3 repository dependency uses) rather than constructing `SqlAlchemyAuditLogRepository` inline, specifically so `tests/integration/test_audit_routes.py` can override it with `FakeAuditLogRepository` and integration-test the route's permission/tenant-scoping/pagination wiring without a live database.

## Testing

All from `apps/api/` unless noted. 79 new tests across six files, all passing alongside the 88 pre-existing Module 1/2 tests (167 total):

- `tests/unit/test_authorization_service.py` (15 tests) — every branch of `authorize()`: permission grant/deny, no-role-assignment default-deny, account-inactive, cross-tenant org (both directions), cross-tenant branch (org-wide bypass vs. branch-scoped denial/allow), ownership fallback (grant and deny), and the denial audit trail's full field set.
- `tests/unit/test_permission_service_cache.py` (10 tests) — `ResolvedAccess.is_org_wide()`/JSON round-trip, cache hit avoiding a second repository call, `invalidate_user` forcing fresh resolution, unassigned-user default access, `resolve_all_for_user`'s multi-role-ready shape.
- `tests/unit/test_authz_dependencies.py` (9 tests) — `require_permission`/`require_org_match`/`require_branch_match`/`require_ownership_or_permission` called directly with a minimal duck-typed fake `Request`, covering both the allow and `PermissionDeniedError`-raising paths, including the renamed-path-param option.
- `tests/unit/test_tenant_context.py` (4 tests) — `get_tenant_context` resolving `TenantContext` and populating `app/core/context.py`'s contextvars; `get_scoped_db` issuing (or correctly not issuing) the `set_config` RLS statement, verified with a fake `AsyncSession` that records what it was asked to execute.
- `tests/unit/test_authorization_matrix.py` (25 parametrized tests) — a representative slice of the role/permission matrix (`org:read`, `org:write`, `branch:read`, `employees:read` × all five customer-facing roles), plus dedicated branch-scoped-roles-blocked-from-a-foreign-branch and org-wide-roles-reach-every-branch checks.
- `tests/unit/test_cross_tenant_isolation.py` (5 tests) — two independent orgs, verifying neither's Owner can read the other's org or branch data, that permission sets never leak across org context, and that denials from two different orgs are each correctly attributed to the right user.
- `tests/unit/test_privilege_escalation.py` (6 tests) — a caller cannot claim an ungranted permission or a foreign org by asserting it; a revoked role loses access immediately once invalidated (and the *un*-invalidated case is explicitly bounded by TTL, not open-ended); the ownership fallback cannot be used to claim a resource by passing someone else's ID as the "owner"; a deactivated account can't ride a still-warm permission cache entry.
- `tests/integration/test_audit_routes.py` (5 tests) — the full HTTP stack: 401 unauthenticated, 403 without `audit:read`, 200 scoped correctly to the caller's own org (a second org's row is verified absent from the response), pagination params respected, and the (currently unreachable under v1's role model, but defensively handled) no-org-membership case.

**Coverage**: `app/services/authorization_service.py` and `app/services/permission_service.py` — the module's actual authorization engine — are at **100%** line coverage. `app/api/deps.py`'s Module-3-specific additions (`get_tenant_context`, `get_scoped_db`, `require_permission`, `require_org_match`, `require_branch_match`, `require_ownership_or_permission`) are fully exercised; the file's aggregate coverage (85%) is pulled down by Module 2's thin DI-construction functions (`get_auth_service`, `get_email_sender`, etc.), which were already untested at that granularity before this module and are out of this module's scope. `app/core/cache.py`'s `RedisCache` implementation is untested against a live Redis, for the same disclosed reason `RedisRateLimiter` (Module 2) is — no Redis is reachable in this sandbox; both classes were validated for correct call construction and exercised end-to-end via the graceful-fallback path (verified live, see below).

## Validation performed

- `bash scripts/validate_migrations_offline.sh` — 56 tables, 22 enums (including the new `authorization_denial_reason`), 40 RLS policies, 18 triggers, 291 seed rows, zero errors across the full 0001→0008 chain.
- `python3 -m pytest` — 167 tests passing (88 pre-existing + 79 new).
- Every route is protected: `GET /api/v1/audit-log` requires `audit:read` via `require_permission`; every future module's routes have `require_org_match`/`require_branch_match`/`require_ownership_or_permission` available and unit-verified now rather than built ad hoc per module.
- Every permission resolves correctly and every role behaves correctly: the authorization matrix tests directly verify F/B/R/- from the role-permission-matrix document against `AuthorizationService`'s actual behavior, not just against `PermissionService`'s resolution.
- Cross-tenant access is blocked: at the application layer (`AuthorizationService`, unit-tested) and the database layer (`get_scoped_db`'s RLS wiring — mechanically verified via `scripts/validate_migrations_offline.sh`'s RLS policy count; genuine query-time enforcement remains unverified against a live database, same disclosed limitation as every prior module).
- Cache invalidation works: `invalidate_user` closes the revocation window immediately; the bounded TTL-only fallback window is explicitly tested, not just assumed.
- Audit logs are generated: every denial branch writes an `AuthorizationDenial` row with the complete required field set, unit-verified directly and integration-verified through the audit-log route's 403 case.
- OpenAPI documentation is updated: booted the real app under `uvicorn` and fetched `/openapi.json` live — `/api/v1/audit-log` appears with its summary/description and 200/401/403/422 response models documented.
- Booted the real app under actual `uvicorn` (not the test client) against a genuinely unreachable database and Redis: `/healthz` stays up, `/readyz` reports 503 informatively, an invalid bearer token on `/api/v1/audit-log` is rejected at JWT decode (never touches the unreachable database), both the rate limiter and the new permission cache log a warning and fall back to their in-memory implementations rather than crashing the process, and the server keeps serving subsequent requests throughout.

## What remains unverified

Same disclosed limitation as every prior module: no live PostgreSQL or Redis instance is reachable in this sandbox. `SqlAlchemyAuthorizationDenialRepository`/`SqlAlchemyAuditLogRepository` (the real production repository implementations) and `RedisCache` have been validated for correct query/call construction and exercised end-to-end through the app's HTTP layer against in-memory fakes, and the graceful-degradation path against unreachable Redis/Postgres has been verified live, but true row-level-security enforcement (does Postgres actually filter a cross-tenant row at query time) and real Redis cache coherency across multiple processes remain unverified against real infrastructure. This should be among the first things exercised once an environment with database and Redis access is available — the "Module 9: Integration & Testing" pass this project's own phase plan already schedules, or sooner if practical.
