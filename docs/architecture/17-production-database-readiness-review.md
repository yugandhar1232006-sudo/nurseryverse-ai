# Production Database Readiness Review

Gate review between Phase 5 (Database) and Phase 6 (Backend). Scope: everything in `apps/api/app/models/` and `apps/api/migrations/`. Three real issues were found and fixed during this review (not just noted) — see the "Fixed During This Review" box in each relevant section — before Phase 6 begins, per the instruction that anything incomplete gets fixed first.

**Fixed during this review, in order found:**

1. **Every timestamp column was `TIMESTAMP WITHOUT TIME ZONE`.** `Mapped[datetime]` had no explicit type override, so SQLAlchemy fell back to its default (naive) `DateTime`. Fixed by registering `type_annotation_map = {datetime: DateTime(timezone=True)}` once on `Base` (`app/db/base.py`) — all 74 affected columns across every table now compile to `TIMESTAMPTZ` without touching each column individually.
2. **40 of 40 standalone composite/tenant-scoping indexes were silently missing from migration 0001.** `ops.CreateTableOp.from_table(table)` — the technique used to mechanically generate the migration — captures columns, PK, FK, and inline constraints, but does not capture `Index(...)` objects declared in `__table_args__`. `scripts/generate_initial_migration.py` now also renders a `CreateIndexOp` per index; migration 0001 was regenerated and now contains all 40 `CREATE INDEX` statements.
3. **The AI Assistant's RAG knowledge base had no table.** `pgvector` was enabled as an extension since migration 0001 but nothing used it. Added `knowledge_base_chunks` (`app/models/ai.py`) with a 1024-dim `Vector` column and an HNSW cosine-distance index — see §5.

All three are re-validated below; `scripts/validate_migrations_offline.sh` passes clean after the fixes (50 tables, 20 enums, 40 RLS policies, 18 triggers, 40 standalone indexes + 2 materialized-view unique indexes, 291 system-metadata seed rows, zero orphan FKs, zero circular dependencies, zero duplicate constraint names).

## 1. Schema Validation

**Every table documented, every column documented.** `docs/architecture/16-data-dictionary.md` — all 50 tables, all 423 columns, generated mechanically by `apps/api/scripts/generate_data_dictionary.py` directly from `Base.metadata` (types compiled against the real PostgreSQL dialect, not SQLAlchemy's generic repr), so it cannot drift the way a hand-written data dictionary would. Regenerate it after any model change; the command is in that file's header.

**PK/FK validation.** Every table has a single-column UUID primary key (`UUIDPKMixin`, `gen_random_uuid()` server-side default — chosen over sequential integers specifically so record counts/creation order never leak across tenants, per `docs/architecture/05-database-architecture.md` §4). 104 foreign keys total, all confirmed to resolve to a real table and column by `scripts/validate_schema.py`'s `check_orphan_foreign_keys()` (walks every FK in `Base.metadata` and asserts the referenced table/column exists) — zero orphans. The FK graph was also confirmed acyclic via a topological sort (Kahn's algorithm) — a real requirement, since a circular FK dependency would make `CREATE TABLE` ordering impossible and would have blocked migration generation entirely; it didn't, because the schema doesn't have one.

**Cascade rules.** Three deliberate patterns, chosen per-relationship rather than defaulted:
- `CASCADE` — child rows that have no independent meaning once the parent is gone: `plant_images`, `growth_timeline`, `health_history`, `watering_logs`, `fertilizer_logs`, `environmental_readings`, `disease_reports`→`treatments`, `ai_predictions`, `ai_assistant_conversations`→`messages`, `invoice_items`, `role_permissions`, `role_assignment_branch_scopes`, `knowledge_base_chunks` (deleting a nursery removes its own knowledge chunks, but not the platform-wide `nursery_id IS NULL` ones, since the FK is nullable and only fires for non-null rows).
- `RESTRICT` — reference data and financially/operationally significant entities that must never silently vanish: `branches`, `species`, `plant_varieties`, `suppliers`, `customers`, `plants`, `sales`, `invoices`, `purchase_orders`, `inventory`, `org_settings`, `subscriptions`, `usage_counters`. Deleting a branch with sales history, or a species with plants still assigned to it, fails loudly at the database rather than cascading into silent data loss — the application layer (Phase 6) is expected to catch this and surface a friendly "this is still referenced" error ahead of the raw constraint violation, exactly as `docs/architecture/13-consistency-validation.md` reasoned when the `plants:delete` permission was removed in the Phase 4→5 gate.
- `SET NULL` — optional cross-references where the child record still makes sense without the parent: `ai_predictions.branch_id`→plant-level predictions, `disease_reports.source_ai_prediction_id`, `ai_recommendations.source_prediction_id`, `inventory.species_id`, `sales.customer_id`, `inventory_adjustments.reference_sale_id`/`reference_purchase_order_id`.

**Constraints.** 22 composite unique constraints (e.g., one species per botanical name per org, one QR token globally, one invoice number per org, one idempotency key per branch, one role code per org) and 4 check constraints (inventory quantity ≥ 0, sale total ≥ 0, PO received-quantity ≤ ordered-quantity, and sale-line-item references exactly one of `plant_id`/`inventory_id`) — all listed per-table in the data dictionary and confirmed to compile against the PostgreSQL dialect with zero duplicate names across all 220 named constraints/indexes.

**Index review.** See §2 — this is where the missing-index bug was caught and fixed.

## 2. Performance Review

**Missing indexes (found and fixed — see box above).** Beyond the structural bug, the actual index *design* was already sound going into this review: every tenant-scoped table is covered by a `(nursery_id, branch_id)` or `nursery_id`-leading composite (part of `TenantMixin`/`BranchScopedMixin` — every table that mixes these in gets its FK columns, but the composite index itself is declared per-table where it matters for a real query, not blanket-applied where it wouldn't be used). Purpose-built composites exist for the highest-traffic access patterns: `ai_predictions(plant_id, prediction_type, created_at)` for "latest prediction per module" (the single most-repeated query shape in the product — Plant Twin, AI Predictions Dashboard, Branch Dashboard all hit it), `sales(branch_id, created_at)` for the default Sales History sort, `disease_reports(status, severity)` for triage queues, `audit_logs(nursery_id, created_at)` for the Audit Log Viewer's default filter+sort, `ai_recommendations(branch_id, status)` for the active-recommendations feed.

**Over-indexing.** None found. Every index was checked against a real, named query pattern in the UX/architecture docs rather than added speculatively — there is no index in this schema that isn't traceable to a specific screen or report. `plant_categories` and `units` (small, rarely-filtered reference tables) deliberately have no indexes beyond their PK/unique-code, since a sequential scan over ~12 rows is faster than an index lookup would be.

**Query optimization.** The recurring "latest row per group" pattern (predictions, and implicitly health/growth history for a plant's current state) uses `DISTINCT ON` backed by the matching composite index, centralized in `v_plant_latest_predictions` (migration 0005) rather than reimplemented per repository — one indexed, reviewed query instead of five ad hoc ones that could drift out of sync with each other.

**Join optimization.** RLS policies for one-hop and two-hop tenant tables (`plant_images`→`plants`, `treatments`→`disease_reports`→`plants`) rely on the parent's `nursery_id` already being indexed, so the isolation check doesn't add a full scan on top of the query's own joins — confirmed by inspecting each policy's `USING` clause in migration 0003, all of which subquery through an indexed FK, never an unindexed column.

**Expected query patterns / recommendations for Phase 6:**
- The repository layer should always filter tenant-scoped tables by `nursery_id` (and `branch_id` where applicable) explicitly, even though RLS enforces it as a backstop — an explicit filter lets the query planner use the composite index directly instead of relying on the RLS policy's subquery to do the narrowing.
- `pg_trgm` (enabled since migration 0001) is provisioned but no `GIN` trigram index exists yet on any searchable text column (`customers.name`, `plants.common_label`, `species.common_name`/`botanical_name`). This is deliberately deferred, not forgotten: those indexes are only worth their write-amplification cost once the global-search and duplicate-customer-detection features (Phase 6, User/Plant/Customer modules) are actually built and their exact query shape is known. Recommendation: add them in the migration that ships global search, not speculatively now.
- Materialized view refresh (§ Views, Phase 5 doc) should be monitored once real data exists — `mv_branch_dashboard_summary`'s `at_risk_counts` CTE does a `DISTINCT ON` over all of `ai_predictions`, which is fine at launch scale but is the first query worth re-examining under the 100K/1M-plant projections in §4.

## 3. Security Review

**RLS policies.** 40 policies confirmed present across three query shapes (direct `nursery_id` equality — 23 tables; one-hop join through a parent — 13 tables; one two-hop join — `treatments`), all with `FORCE ROW LEVEL SECURITY` so even the table owner is subject to them (not just non-owner roles, which is the common RLS misconfiguration). Seven tables are deliberately RLS-exempt, and each exemption is a considered decision, not an oversight — documented in migration 0003's module docstring: `users`/`invites` (looked up pre-authentication, before any org context exists to filter on), `passports` (the one intentionally-public unauthenticated endpoint), `roles`/`permissions`/`role_permissions` (system roles must be visible platform-wide; org-custom roles are filtered at the application layer instead), `plant_categories`/`units` (global reference data). `knowledge_base_chunks` (new, §5) is a deliberate eighth exemption for the same reason as `plant_categories` — its `knowledge_article` rows are global by design — with the `org_data` rows' tenant isolation enforced by the retrieval service always querying `nursery_id = :current_org OR source_type = 'knowledge_article'` explicitly rather than relying on RLS. This is the one place in the schema where tenant isolation is application-enforced rather than database-enforced, and it's called out explicitly here so Phase 6's AI Services module (task list item 11) does not treat it as covered by the RLS backstop the way every other table is.

**Role permissions.** 58 permissions × 6 system roles, mechanically parsed from the approved `docs/ux/07-role-permission-matrix.md` (not hand-transcribed) into migration 0002's seed data — the same regex parser (`scripts/generate_seed_migration.py`) that produced it is re-runnable if the matrix doc ever changes, guaranteeing the two stay in sync.

**Sensitive columns.** `users.password_hash` — confirmed there is no plaintext password column anywhere in the schema; `passlib[bcrypt]` is pinned in `requirements/base.txt` for Phase 6 to hash against. `invites.token` and `passports.public_token` are both long random strings used as unauthenticated bearer credentials (invite acceptance, public passport view) — both are unique-indexed and `passports.token_expires_at` gives the public path a bounded lifetime; invites should get the same expiry enforcement in the Phase 6 Authentication module (currently `invites.expires_at` exists and is `NOT NULL`, so the column is ready — the expiry check itself is application logic, not yet written). One item flagged for Phase 6, not the schema: `org_settings.sms_provider_config` is a raw `JSON` column that will hold an SMS provider's credentials once populated. The schema doesn't prevent storing that in plaintext. Recommendation: the service layer that writes to this column should encrypt the payload (e.g., via `pgcrypto`'s `pgp_sym_encrypt`, already available since `pgcrypto` is enabled) or, preferably, store only a reference to a secret held in the deployment platform's secrets manager — not raw credentials in a row a `SELECT *` could expose. This is a Phase 6/9 implementation task, not a Phase 5 schema gap, since the column's *shape* (JSON, nullable) is correct either way.

**Audit logging.** `audit_logs` is genuinely immutable (migration 0004): both `REVOKE UPDATE, DELETE` from the app's runtime role and, as the real guarantee since table owners bypass grants, a `BEFORE UPDATE OR DELETE` trigger that unconditionally raises. FR-19.3 is enforced below the ORM and below the API.

**Encryption strategy.** At-rest: deferred to the managed PostgreSQL provider's disk-level encryption (standard on RDS/Cloud SQL/etc. — not a schema concern) per `docs/architecture/09-infrastructure.md`. In-transit: `asyncpg`/`psycopg` both support `sslmode=require`, to be set via `DATABASE_URL` at deploy time (Phase 10). Application-level: `pgcrypto` is enabled precisely so column-level encryption is available where warranted (the `sms_provider_config` recommendation above is the first concrete case for it). No column in the current schema stores a credential or secret in plaintext by design — `password_hash` is a hash, not a secret; `qr_code_token`/`public_token`/`invite.token` are unauthenticated bearer identifiers, not secrets protecting something else, and are treated as such (unique-indexed, and for passports, expiring).

**SQL injection resistance.** Every migration's parameterized DDL and every model's ORM-mapped column goes through SQLAlchemy's query construction, which parameterizes by default. The two places raw SQL appears — RLS policy definitions (migration 0003) and trigger function bodies (migrations 0004/0006) — are static, string-literal `op.execute()` calls with no runtime user input concatenated into them; they're schema DDL, not data-path queries, so they carry no injection surface. This must remain true in Phase 6: recommendation is that any raw-SQL escape hatch in a repository (e.g. a materialized-view refresh trigger or a full-text-search query) go through SQLAlchemy's `text()` with bound parameters, never f-string interpolation of user input — a rule worth stating explicitly now since it's cheap to enforce in code review and expensive to catch after the fact.

## 4. Scalability Review

Estimates below use the schema's actual row-growth shape: `plants` is the anchor entity, and its child tables (`growth_timeline`, `health_history`, `environmental_readings`, `watering_logs`, `fertilizer_logs`, `ai_predictions`, `plant_images`) grow as a multiple of plant count over time, not a fixed ratio — a plant with a 2-year production cycle accumulates far more history rows than one sold in a month.

**10,000 plants.** No changes needed. At this scale (roughly what a handful of mid-size nursery orgs would produce in their first 1–2 years), even an unindexed table would perform acceptably; with the composite indexes in place (§2), every dashboard/detail query stays well under NFR-1.3's 2-second budget. `mv_branch_dashboard_summary`'s 15-minute refresh cadence is more than sufficient.

**100,000 plants.** Still no structural changes required, but this is the point where the deferred `pg_trgm` GIN indexes (§2) stop being optional — fuzzy plant/customer search over 100K+ rows without a trigram index would start showing up in slow-query logs. Connection pooling (PgBouncer, already planned in `docs/architecture/09-infrastructure.md`) becomes operationally necessary rather than just good practice, since concurrent branch-level POS/inventory writes multiply with org count. History tables (growth/health/environmental/watering/fertilizer logs) at this scale, assuming ~50 records/plant/lifecycle, put the largest single table around 5 million rows — comfortably within a single unpartitioned PostgreSQL table's capabilities, but the point at which partitioning should be actively monitored, not yet acted on.

**1,000,000 plants.** This is where the partitioning plan documented in `docs/architecture/14-phase5-database-implementation.md` §19 should actually be executed, not just planned: range-partition `audit_logs`, `ai_predictions`, `notifications`, and the four Digital Twin history tables by month on `created_at`/`recorded_at`. At 1M plants with realistic history depth, the largest of these tables would be in the hundreds of millions of rows — unpartitioned, index maintenance and vacuum times would start to noticeably affect write latency. This is also the scale at which `mv_branch_dashboard_summary`'s refresh query (which scans recent `sales`/`ai_predictions`/`inventory` per branch) should be re-benchmarked; if the 15-minute cadence starts taking longer than 15 minutes to compute, the CTEs need to move to incrementally-maintained rollup tables instead of a full materialized-view recompute.

**Archiving.** Not yet implemented (correctly deferred, matching the "don't build for scale you don't have" reasoning already used for partitioning). The natural archive boundary is plant lifecycle completion: once a plant reaches `sold`/`deceased` and its retention window (a business policy, not yet specified) elapses, its history rows are candidates for cold storage. The schema doesn't block this — nothing references `growth_timeline`/`health_history`/etc. rows from elsewhere, so archiving them (e.g., to cheaper storage, or a `_archive` schema) is a pure data-movement operation whenever it's needed, not a schema migration.

**Read replicas.** Not needed at any of the three estimated scales for OLTP traffic, but materialized-view refresh and reporting queries (Phase 6 Reports/Analytics modules) are natural candidates to route to a read replica once one exists, since they're read-only and tolerate the replication lag that pre-aggregated dashboards already tolerate by design (§2's 15-minute refresh cadence already assumes non-real-time reads). This is an infrastructure decision for Phase 10, not a schema change.

**Future sharding strategy.** Every tenant-scoped table's leading index column is `nursery_id` specifically so that if sharding ever becomes necessary (well beyond the 1M-plant estimate — likely only relevant at hundreds of orgs each near the 1M-plant mark, not the launch target of 50 orgs), the natural shard key is already the schema's own primary access pattern: shard by `nursery_id` range or hash, and every existing composite index remains useful within a shard unchanged. This isn't implemented (would be premature at any realistic near-term scale) but the schema doesn't foreclose it either — no cross-tenant JOIN in any repository query would need to change.

## 6. Data Lifecycle

**Plant creation.** `INSERT INTO plants` (status defaults to `in_production`) with a mandatory `species_id` (optionally `variety_id`) and a system-generated unique `qr_code_token`. No plant is ever created via seed data, per the Phase 5 seed-data rule — every plant row is a real business event from Phase 6 onward.

**Growth updates.** Append-only `INSERT INTO growth_timeline` per observation (height/spread/growth_stage/photo), attributed to `recorded_by_user_id`. Never updated or deleted — the timeline's value is the complete history, not just the latest point (the latest point is derived via `v_plant_latest_predictions`-style `DISTINCT ON` queries when needed, not by mutating a "current" row).

**Health reports.** Two paths converge on the same lifecycle: a human logs a `health_history` observation directly, or an AI disease-detection prediction (`ai_predictions`) triggers a `disease_reports` row (`source_ai_prediction_id` set, `is_ai_sourced=true`), which a horticulturist then confirms/dismisses (`status` transitions `draft`→`confirmed`/`dismissed`) and optionally treats (`treatments`, append-only, `outcome` tracks `ongoing`/`recovered`/`plant_lost`). A confirmed severe disease report is the one path that can move `plants.status` to `under_treatment`.

**Inventory movement.** Every quantity change to `inventory` goes through `inventory_adjustments` (append-only, `reason` enum: `damage`/`correction`/`internal_use`/`purchase_order_receipt`/`sale`/`other`, with `quantity_delta` and `quantity_after` both recorded so the adjustment log is independently reconstructable without replaying the whole history). `inventory.quantity` itself is the current-state column the adjustment log maintains — this is the one place in the schema where a service-layer transaction (§17 of the Phase 5 doc) is load-bearing: the adjustment insert and the `inventory.quantity` update must commit together.

**Sales.** `sales` (status `completed`/`voided`) + `sale_items` (exactly one of `plant_id`/`inventory_id` per line, enforced by check constraint) created in one transaction alongside the corresponding `inventory_adjustments` (reason=`sale`) and, for plant sales, a `plants.status` transition to `sold`. Voiding a sale (`status='voided'`, `void_reason` set) does not delete the row — sales are never hard-deleted, matching the audit-first design of the rest of the schema.

**Archiving.** Not yet triggered by any lifecycle event (§4) — a future policy decision, not a current gap, since nothing in today's launch-scale operation needs it.

**Deletion.** Deliberately rare in this schema by design, not by omission: `plants` are never deleted (only transitioned to `sold`/`deceased`), digital-twin history tables have no delete path at any layer, `audit_logs` is trigger-enforced immutable, and every reference entity (`branches`, `species`, `suppliers`, `customers`) uses `ON DELETE RESTRICT` so a delete attempt against a referenced row fails loudly rather than cascading data loss. The only true hard-deletes in the product are pre-business-data cleanup cases (e.g., an unaccepted, expired `invites` row) — everything with real business weight is soft-stated (`status` enum) or append-only.

**Audit history.** Every mutating action that matters (per FR-19.x, `docs/architecture/08-security-architecture.md`) writes an `audit_logs` row (`action`, `entity_type`, `entity_id`, `diff` JSON, `actor_user_id`) — this is a Phase 6 application-layer responsibility (the schema provides the immutable sink; nothing populates it automatically via trigger, since capturing a meaningful diff requires application context a database trigger doesn't have).

## 7. Backup & Recovery

Restated and made concrete from `docs/architecture/05-database-architecture.md` §8 and `docs/architecture/14-phase5-database-implementation.md` §18/19 for this final schema:

**Backup policy.** Daily logical backup (`pg_dump --format=custom`, enables selective table restore) plus continuous WAL archiving for point-in-time recovery between daily snapshots. Retention: 30 days rolling daily, 12 months monthly (first-of-month snapshot retained past the 30-day rolling window). Materialized views (`mv_branch_dashboard_summary`, `mv_org_revenue_rollup`) are derived data and do not need independent backup — a restore only needs `REFRESH MATERIALIZED VIEW` once the base tables (`sales`, `inventory`, `ai_predictions`, etc.) are back.

**Restore strategy.** Two tiers matching two real failure modes: (1) point-in-time recovery via WAL replay for "bad deploy/bad migration/accidental bulk update" — restore to the timestamp immediately before the bad write; (2) full logical restore from the most recent daily `pg_dump` for total-loss scenarios (region failure, corrupted volume). `audit_logs`' trigger-enforced immutability (migration 0004) means a restored audit log is provably identical to pre-incident state — there is no scenario where a "restore" could have included a tampered row, since tampering was never possible at any point in the row's life.

**Disaster recovery.** RPO target: ≤15 minutes (bounded by WAL archive frequency, not the daily snapshot). RTO target: bounded by restore-and-replay time for the WAL volume since the last snapshot — for the launch-scale data volumes in §4 (10K–100K plants), this is a low-minutes operation; the 1M-plant estimate is the point at which restore time itself should be re-benchmarked, since a from-scratch restore of a partitioned table set can parallelize by partition where an unpartitioned restore cannot.

**Retention policy.** Backups: 30 days rolling + 12 months monthly, as above. This is independent of any future business-data retention/archiving policy (§4/§6) — backup retention protects against operational failure, data archiving is a business decision about how long *active* history should stay queryable, and the two should not be conflated when Phase 6/9 implements either.

## 9. Implementation Validation

**Migrations are deterministic.** Every migration is either pure DDL (`CREATE TABLE`/`CREATE INDEX`/`CREATE TYPE`, generated mechanically from `Base.metadata` — same input always produces the same output) or `op.execute()` of static, parameter-free SQL (RLS policies, triggers, views). Nothing in the migration chain depends on wall-clock time, random values at migration-authorship-time, or external state — the two `gen_random_uuid()`/`now()` calls that appear are database-side `server_default`s evaluated at row-insert time, not baked into the migration itself.

**Idempotent where appropriate.** `CREATE EXTENSION IF NOT EXISTS` (migration 0001) and the role-existence-checked `DO $$ ... IF EXISTS ...` block around the audit-log grant revocation (migration 0004) are both written to be safe to re-run or to run against an environment that doesn't perfectly match assumptions (e.g., local dev connecting as superuser, where the `nurseryverse_api` role doesn't exist). Table/type/index creation is intentionally *not* idempotent (`CREATE TABLE` without `IF NOT EXISTS`) — this is correct for a migration chain, where Alembic's own `alembic_version` tracking is what prevents re-application, not defensive SQL; adding `IF NOT EXISTS` everywhere would mask a real problem (re-running an already-applied migration) instead of surfacing it.

**Version history is complete.** Six migrations, single linear chain, no forks: `<base> → 0001 → 0002 → 0003 → 0004 → 0005 → 0006`, confirmed by `alembic history` during this review's re-validation run (§ top of this document).

**Rollback strategy exists.** Every migration has a real `downgrade()`, not a `pass` stub: 0001 drops all 50 tables in reverse dependency order and drops the three extensions; 0002 deletes the seeded rows; 0003 drops all 40 RLS policies and disables RLS per table; 0004 drops the immutability trigger/function and restores grants; 0005 drops both materialized views and both plain views; 0006 drops all 17 `updated_at` triggers and the shared trigger function. None of these were exercised against a live database in this sandbox (§ "What this does not prove" in `docs/architecture/14-phase5-database-implementation.md`), which remains the one outstanding verification step before this is unconditionally production-ready.

## 10. Final Sign-off

**Schema:** complete, documented, internally consistent — 50 tables, 423 columns, 104 FKs (zero orphans, zero cycles), 220 named constraints/indexes (zero duplicates), 20 native enums, all confirmed via both Python-level static validation and full offline `alembic upgrade head --sql` generation (2,138 lines of real PostgreSQL DDL/DML across all six migrations, zero errors).

**Fixed during this gate, not deferred:** naive timestamps → `TIMESTAMPTZ` schema-wide; 40 missing composite/tenant indexes → present and confirmed in generated SQL; RAG knowledge base table → added with a real pgvector column and HNSW index. The generator script itself (`scripts/generate_initial_migration.py`) was also fixed, so the index-rendering gap cannot silently recur on the next model change.

**Recommended, not blocking:** `pg_trgm` GIN indexes for fuzzy search (defer to the Phase 6 module that actually ships search — building them now would be speculative); encrypt or externalize `org_settings.sms_provider_config` when the service layer that writes it is built (Phase 6 Notifications module); re-benchmark materialized-view refresh cost and consider partitioning once the org actually approaches the 1M-plant range (§4) — none of these block Phase 6 from starting.

**Outstanding, honestly disclosed:** no live PostgreSQL 16 instance has executed this migration chain. This sandbox has no reachable database and no root/apt access broad enough to provision one (documented exhaustively in `docs/architecture/14-phase5-database-implementation.md`). Everything checkable without a live database has been checked — DDL dialect compilation, FK/index/constraint structural validation, and full offline SQL generation for the entire chain — but a live `docker compose up -d postgres && alembic upgrade head` run, followed by exercising the RLS policies and triggers under an actual session, has not happened and should be the first thing done in whatever environment eventually has database access, ideally before or alongside Phase 6's first database-touching integration test.

**Assessment: production-ready at the schema/migration level, conditional on the live-execution step above.** Given how much of this chain is mechanically generated directly from validated, introspectable metadata rather than hand-typed, the risk of a live-only failure is low — but it is not zero, and this review does not claim otherwise. Proceeding to Phase 6 is appropriate; the live-DB run should happen at the first opportunity an environment provides one, not be treated as satisfied by this review.
