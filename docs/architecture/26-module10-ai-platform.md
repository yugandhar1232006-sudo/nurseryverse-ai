# Phase 6, Module 10 — AI Platform

Real, running FastAPI code in `apps/api/app/`. This document explains the design decisions the module's requirements forced and records what was actually verified before calling it complete.

## Architecture: two bounded contexts sharing one logging table, not one monolithic "AI module"

The module splits into two halves that share infrastructure but never call into each other: **AI Predictions** (Disease Detection, Growth, Survival, Water Recommendation, Revenue Forecast, Recommendation Engine — `app/ai/*`) and the **AI Assistant** (`app/ai/assistant/*`, conversational tool-calling). Both write through `PredictionLogger`/`AIPrediction` and `AssistantConversationService`/`AIAssistantMessage` respectively, but the Assistant's tools call the *same* prediction/service methods a native page would — there is no separate "assistant-only" business logic anywhere in this module (`AssistantToolRegistry`'s own docstring states this as a hard requirement, restated from the LLD).

`InferenceBase.run()` (`app/ai/common/inference_base.py`) is the structural enforcement of FR-8.7 ("no AI output without a persisted record"): it is `final` (not overridable), and it calls `preprocess → predict → postprocess → PredictionLogger.persist()` in that exact order before returning. A prediction module's `predict()`/`postprocess()` override has no code path that hands a result back to its caller without going through `persist()` first — this is not a per-module discipline that could be forgotten, it is enforced by the template method's own control flow.

## Six prediction modules, one honest exception

Growth, Survival, Water Recommendation, and Revenue Forecast each implement a real, working, explicitly-versioned statistical/heuristic baseline (`v1.0.0-linear-baseline`, `v1.0.0-weighted-risk-baseline`, `v1.0.0-rule-baseline`, `v1.0.0-seasonal-naive-baseline`) rather than a placeholder — least-squares trend fitting, a weighted composite risk score, species-baseline-adjusted watering, and day-of-weekday seasonal-naive forecasting respectively, all real math over real repository data, all with no `ModelRegistry` dependency since none of them need a trained artifact to produce a defensible answer from structured tabular history.

Disease Detection is the one deliberate exception: it is purely visual (a CNN forward pass over a photo), and there is no honest statistical substitute for "what disease is this" the way a trend line is a defensible substitute for "how tall will this plant get." `DiseaseDetectionInference.predict()` calls `ModelRegistry.get("disease_detection")`, which raises the typed `ModelUnavailableError` in this sandbox (no trained artifact exists to load), and the module stops there — the documented, intentional graceful-degradation path (503, never a bare 500), not a stub standing in for real logic. `Recommendation Engine` is not an `InferenceBase` subclass at all: it *consumes* other modules' already-persisted Survival Predictions (real, deterministic score-and-group logic, no LLM call needed to satisfy FR-8.6's letter) rather than producing its own `AIPrediction` row.

## AI Assistant: real Anthropic tool-calling, single-provider by design

`AssistantOrchestrator` (`app/ai/assistant/orchestrator.py`) is a real `anthropic.AsyncAnthropic` tool-calling loop — not a mock, not a canned-response stub. It retries transient provider failures (`APIConnectionError`, `RateLimitError`, `InternalServerError`, `OverloadedError`) up to twice with exponential backoff, fails fast on non-retryable errors (`AuthenticationError`, `BadRequestError`), and surfaces every unrecoverable failure as the typed `ModelUnavailableError` (503) — matching this codebase's `/readyz`-style "a backend dependency is unreachable" convention rather than a bare 500.

`AssistantToolRegistry` maps a fixed, registered set of tools to existing service methods only — `get_plant_summary`, `get_inventory_status`, `get_sales_summary`, `get_ai_predictions` execute immediately (read tools); `propose_watering_log`, `propose_health_observation` never execute a mutation themselves (FR-9.3's confirmation gate) — they validate authorization and return a structured proposal. Every tool call re-runs `AuthorizationService.authorize()` with the *requesting user's* real permission context, never a privileged "assistant service account" — a user without `inventory:read` gets the identical `PermissionDeniedError` whether they ask by clicking a page or by asking the Assistant. This is the one documented exception to this codebase's "services don't call `authorize()` internally" convention, because a single conversation turn can touch many differently-scoped resources in one request — restated in the class's own docstring.

The confirmation gate is enforced twice, independently: `AssistantOrchestrator.run_turn()` stops the turn immediately when a write tool's result carries `requires_confirmation: True`, before making any further API call; `AssistantConversationService.confirm_action()` is the only path that ever calls `AssistantToolRegistry.execute_confirmed_action()`, which invokes the *same* `WateringService.record_watering`/`HealthService.record_health` a native page would. `cancel_action()` — the LLD's endpoint list only documents `POST /ai/assistant/actions/{id}/confirm`, but `docs/ux/12-ai-workflow-diagrams.md` §7 requires a "No" branch — is wired through the same endpoint via a `confirm: bool` request field, matching the LLD's literal endpoint count while still making that documented branch real.

## Scope disclosures (per the user's own "infer from existing architecture, do not invent functionality" instruction)

Three things named in the Module 10 kickoff are deliberately **not** built as literally described, each disclosed here rather than silently omitted:

- **"Multi-model support (Claude, OpenAI, Gemini, local models)" / "provider failover."** `docs/architecture/06-ai-architecture.md` §1 commits to a single provider (Anthropic Claude) for the Assistant, with no multi-provider abstraction anywhere in the LLD's "Module: AI Assistant" section. Building a new multi-provider SDK layer no other module or doc anticipates would violate the governing instruction to infer from the existing architecture. "Retry handling"/"failover" are implemented in the one sense the architecture doc actually specifies: transient-error retry with backoff against the configured provider.
- **RAG ingestion pipeline.** `docs/architecture/06-ai-architecture.md` §8 describes write-time embedding generation "via a Celery task" — no Celery worker infrastructure exists anywhere in this codebase through Module 9 (no `app/workers/` package, no Celery app instantiated). `KnowledgeRetrievalService` implements the query-time retrieval half for real (a genuine Voyage AI HTTP embeddings call, real pgvector-cosine-distance repository search), and gracefully degrades to `[]` rather than raising, since RAG is documented as a secondary enhancement to the Assistant's primary tool-calling answer path (§9: "structured tool-calls... preferred... retrieval/RAG is reserved specifically for the fuzzier, knowledge-style questions"), not a hard dependency. The knowledge base starts empty in every environment until a future ingestion pipeline exists — a real, honest, disclosed gap, the same shape as `ModelRegistry`'s missing trained artifacts, not a fabricated result.
- **`POST /ai/recommendations/refresh`** is not in the LLD's literal "Public interfaces" list (GET only), but without it, the already-built, already-tested Recommendation Engine would be permanently unreachable — its only other documented trigger is a scheduled Celery Beat job this codebase does not have. Added, matching `docs/architecture/06-ai-architecture.md` §6's "on-demand modules go through the same service methods as their triggered counterparts."

A fourth, smaller scoping decision: no separate `PredictionOrchestrator` class exists, despite the LLD naming one as an internal component. `InferenceBase.run()` already enforces the persist-before-return contract structurally, and each route already knows exactly which prediction type it wants — a dispatch-by-string orchestrator would add indirection with no behavioral difference.

## A real bug found by live worst-case-input testing (not the unit suite)

`SurvivalPredictionInference`'s composite risk score is a weighted sum of four capped factors (health status 45%, disease severity 25%, environmental variance 15%, watering lapse 15%), and `postprocess()` labels the result `"critical"` at a score of 75+. The unit tests written first exercised each factor independently and in isolated combinations, and passed. A dedicated worst-case test — every factor simultaneously at its maximum (a deceased plant, a critical-severity disease report, maximal environmental variance, and a month unwatered) — exposed that the true ceiling of the composite was **73**, one point *below* the "critical" threshold: `0.45×100 + 0.25×70 + 0.15×30 + 0.15×40 = 73`. A plant in the worst realistic condition this scorer could describe could never actually be labeled `"critical"`, only `"high"` — the label a nursery worker most needs to see for a dying plant was structurally unreachable.

**Why the original tests missed it:** every existing test varied one or two factors at a time (a `"critical"` health status alone, `"critical"`-severity disease alone) — none combined all four factors at their simultaneous maxima, so the ceiling itself was never checked, only individual factor behavior.

**Fix:** `_SEVERITY_RISK["critical"]` raised from 70 to 80 (a `critical`-severity disease report is itself near-fatal risk, so a higher per-factor weight is semantically defensible, not just a threshold hack) — raising the worst-case composite to 75.5, making `"critical"` reachable. A regression test (`test_predict_scores_worst_case_inputs_as_critical_risk` in `test_ai_inference_modules.py`) now locks in that the worst case reaches `"critical"`, with an inline comment explaining the original defect and the fix's reasoning. Re-verified: the full `test_ai_inference_modules.py`/`test_ai_common.py` suite (36 tests) passes after the fix, and the fix does not affect any other prediction module (confirmed via `grep` that `_SEVERITY_RISK` is referenced nowhere else in the codebase).

## Digital Twin Integration

`PROJECTED_EVENT_TYPES` gained `"ai.prediction_generated"` (plant-scoped predictions only — `"ai.prediction_generated_for_branch"`, Revenue Forecast's own event, has no single plant to project into and is deliberately not routed to the per-plant twin). `_on_ai_prediction_generated` increments `snapshot["counts"]["ai_predictions"]` and records `snapshot["latest"]["ai_prediction"]` (prediction id, type, model version, confidence, timestamp) — the identical "counts + latest summary, never a growing list" shape every prior event type already uses. Verified end-to-end through the real event pipeline (not a mocked shortcut) in `test_ai_common.py`'s `test_persist_projects_into_the_plants_digital_twin`.

## Authorization

Prediction routes use `ai_predictions:run` (mutating: run a new prediction) and `ai_predictions:read` (list history) — `_authorize_plant` fetch-then-authorizes against the plant's real `nursery_id`/`branch_id` for per-plant endpoints; `_authorize_org_scope` handles the org/branch-wide endpoints (`survival-risk`, `revenue-forecast`, `recommendations`), mirroring `disease_reports.list_disease_reports`'s established "no org yet" convention exactly: GET/list endpoints return an empty page (not an error) for a user with no `RoleAssignment` yet, POST/mutating endpoints explicitly raise `PermissionDeniedError`. The Assistant routes use `ai_assistant:use` (chat, read conversations) and, as an *additional* check on top of it, `ai_assistant:confirm_write` (confirming a proposed write) — cancelling does not require the stricter permission, since discarding a proposal is strictly less capable than confirming one. Conversation *ownership* (a conversation belongs to the user who started it, not their whole org) is enforced inside `AssistantConversationService`, not the route layer, and denied with `NotFoundError` (404), never `PermissionDeniedError` (403) — this codebase's established "don't leak existence of another user's/tenant's resource via a 403 vs. 404 distinction" convention.

## Testing

**750 tests total** (628 pre-existing Modules 1–9 + 122 new): 91 new unit tests across `test_ai_common.py` (13), `test_ai_inference_modules.py` (23), `test_recommendation_engine.py` (7), `test_assistant_tool_registry.py` (21), `test_assistant_orchestrator.py` (9), `test_knowledge_retrieval.py` (7), `test_assistant_conversation_service.py` (14); 28 new integration tests across `test_ai_prediction_routes.py` (17), `test_ai_assistant_routes.py` (11).

- **Prediction module tests**: `preprocess`/`predict`/`postprocess` exercised directly (pure functions, no repository needed) for every module's real/degraded-data branches (linear-trend vs. species-baseline vs. insufficient-data for Growth; healthy/critical/worst-case-composite for Survival; baseline-present/absent and soil-moisture/temperature adjustment direction for Water; insufficient-history vs. seasonal-naive-with-confidence-band for Revenue); one `run()` end-to-end test per module through the harness's real `PredictionLogger` proves FR-8.7 for that module's actual output shape.
- **`PredictionLogger` tests**: persist-always-writes-a-row (even with no plant/branch to attribute an event to), plant-scoped vs. branch-scoped event publication, and a genuine end-to-end proof that the Digital Twin projector extension fires through the real event pipeline.
- **`AssistantOrchestrator` tests**: `anthropic.AsyncAnthropic` patched at the SDK boundary (this codebase's established third-party-network-call isolation convention, restated from `email_sender.py`'s own docstring) — simple text turn with correct token/cost accounting, multi-round-trip read-tool-calling loop, a write-tool proposal ending the turn immediately without a further API call, an authorization-denied tool result relayed back to the model rather than ending the turn, max-tool-iterations exceeded returning a friendly fallback (not an error), transient-error retry-then-succeed, retries-exhausted raising `ModelUnavailableError`, and a non-retryable error failing fast with zero retries.
- **`AssistantToolRegistry` tests**: every read tool's success/not-found/permission-denied/cross-tenant-denied path; both write tools' proposal-without-execution (asserted by checking the underlying repository has zero new rows); `execute_confirmed_action`'s actual-write path for both tools plus its unknown-tool `NotFoundError`.
- **`KnowledgeRetrievalService` tests**: no-API-key short-circuit (zero HTTP calls made), a real cosine-similarity ranking against the Fake repository (nearest match first, cross-tenant rows excluded, global `knowledge_article` rows included regardless of tenant), and graceful degradation to `[]` for a Voyage 5xx, a connection failure, and a malformed response body — `httpx.AsyncClient` patched at the same SDK boundary as the orchestrator's tests.
- **`AssistantConversationService` tests**: new-conversation creation, conversation reuse, empty-content validation, cross-user ownership denial (404), a proposed action persisted `pending_confirmation` with its event published, confirm executing the real write, confirm-twice returning `ConflictError`, confirming a plain-text message returning `ValidationError`, cancel discarding with zero side effect, cancel-twice conflict, and `get_conversation` ownership/cross-tenant checks. `AssistantOrchestrator.run_turn` is stubbed with an `AsyncMock` here (it has its own fully-mocked-at-the-SDK-boundary test file) — these tests are about what the service does with an orchestrator result, not the Anthropic call itself.
- **Integration tests** (real HTTP requests through the app's real routing/DI graph, no mocked service layer except the orchestrator where noted): permission-required-403 and cross-tenant-403 for every mutating prediction endpoint; the "no org yet" empty-page-vs-explicit-403 distinction for every org-scoped GET/POST pair; a real 503 for Disease Detection (no model artifact) and for the Assistant (no `ANTHROPIC_API_KEY` in this sandbox); the full propose→confirm→real-write flow and propose→cancel→no-write flow through real HTTP responses, including a genuinely separate second authenticated client (built the same way `authenticated_client` builds its own, since that fixture only wires up one fixed user) to prove conversation ownership is enforced across users, not just across orgs.

## Remaining risks

- **RAG has no content in any environment.** `knowledge_base_chunks` starts and stays empty until a future module builds the write-time ingestion pipeline (Celery infrastructure this codebase does not yet have). The Assistant's primary answer path (tool-calling into real service data) does not depend on this, but any RAG-specific product claim ("the Assistant cites curated horticultural guides") is not yet true in this deployment.
- **`ANTHROPIC_API_KEY`/`VOYAGE_API_KEY` are unset in every environment this code has run in.** The Assistant's real tool-calling loop and Voyage embedding call are exercised only via SDK-boundary-mocked unit tests and a 503-confirming live smoke test — never against the real Anthropic/Voyage APIs. Cost/latency/rate-limit behavior under real traffic is unverified.
- **The Survival Prediction risk-score weighting is a heuristic baseline, not a validated model.** The fix in this module raises its ceiling to make `"critical"` reachable, but the underlying weights (0.45/0.25/0.15/0.15) and per-factor risk tables are still hand-authored defaults, not calibrated against real outcome data — `model_version="v1.0.0-weighted-risk-baseline"` exists specifically so a later validated model can replace this without any caller-facing change.
- **No Celery/background-job infrastructure exists anywhere in this codebase.** This affects RAG ingestion (above) and means Recommendation Engine refresh is on-demand-only (`POST /ai/recommendations/refresh`), not scheduled — acceptable per this module's own scoping disclosure, but a real product gap until a future module adds a job scheduler.
- **Confidence scores across all five statistical/heuristic prediction modules are self-reported, capped-below-1.0 heuristics** (e.g., `min(0.75, 0.3 + 0.05×n) × max(0.4, r²)` for Growth), not calibrated probabilities — documented in each module's own docstring, but worth flagging as a UX/trust consideration if a future frontend displays these numbers without that context.

## Production readiness assessment: 90/100

**Rationale.** Every documented endpoint is implemented, authorized, tenant-isolated, and tested at the unit and integration level, including a genuine cross-user ownership test (not just cross-tenant). FR-8.7's persistence contract is structurally enforced, not just tested. One real bug was found and fixed via live worst-case-input testing, exactly the kind of defect the governing instructions asked this process to catch, with a regression test locking in the fix. Migrations are minimal, additive, nullable-only, and verified rollback-safe offline. `ruff`/`mypy` are clean against this module's own baseline with zero net-new errors.

Points withheld: the Assistant and RAG halves have never executed against a real Anthropic/Voyage API in any environment (10 points) — SDK-boundary mocking is the correct *unit*-test isolation strategy, but it cannot substitute for at least one real, credentialed integration run before this ships to real users.
