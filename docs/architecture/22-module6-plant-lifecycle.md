# Phase 6, Module 6 — Plant Lifecycle Management

Real, running FastAPI code in `apps/api/app/`. This document explains the design decisions the module's requirements forced and records what was actually verified before calling it complete.

## Migration: `0010_plant_lifecycle`

Adds columns only — no new tables, no new enum types, no new `PlantStatus` values. To `plants`: `batch_number`, `supplier_id` (FK `suppliers.id`, `ON DELETE SET NULL`), `purchase_price`, `purchase_date`, `registered_by_user_id` (FK `users.id`, `ON DELETE SET NULL`), `archived_at`, `archived_reason`, plus `ix_plants_batch_number`/`ix_plants_supplier_id`. To `plant_transfers`: `from_zone`/`to_zone` (unifies branch, zone, greenhouse, and outdoor moves into the one existing movement table — see below). To `growth_timeline`: `leaf_count`, `flower_count`, `fruit_count`, `photo_urls` (JSON). To `health_history`: `health_score` (Numeric(5,2)), `is_ai_observation` (Boolean, `server_default false`). To `watering_logs`: `method`. To `fertilizer_logs`: `method`, `schedule`, `next_application_date`. To `environmental_readings`: `ph_level` (Numeric(4,2)), `weather_snapshot` (JSON). Full `downgrade()` provided. Two pre-existing model bugs (`Plant.price`, and four `Numeric`-typed columns across the digital-twin-record models) were also corrected to `float`, the same `Mapped[Numeric]` → `Mapped[float]` class of fix Module 5's doc already flagged — annotation-only, no schema impact.

## The plant-status vocabulary: mapped onto the existing enum, not replaced

The module's own spec lists ten status words (Seedling, Growing, Mature, Ready for Sale, Reserved, Sold, Quarantine, Diseased, Disposed, Archived). The already-approved `PlantStatus` enum from `docs/ux/13-digital-twin-lifecycle.md` has five values (`IN_PRODUCTION`, `READY_FOR_SALE`, `UNDER_TREATMENT`, `SOLD`, `DECEASED`) with its own full transition-rules table. Rather than take the spec's list at face value and add a sixth-through-tenth enum member, each word was mapped onto the existing model:

- **Seedling / Growing / Mature** — these describe growth stage, not lifecycle status. They live in `growth_timeline.growth_stage` (free text, one row per observation), not as `PlantStatus` values. A plant is `IN_PRODUCTION` throughout all three stages.
- **Ready for Sale / Sold** — exact matches to `PlantStatus.READY_FOR_SALE` / `PlantStatus.SOLD`. No change needed.
- **Quarantine / Diseased** — both map to `PlantStatus.UNDER_TREATMENT`. The existing enum already treats "removed from normal production for a health reason" as one state; adding two more states that mean the same thing to a buyer or a branch manager would be the "unjustified scope creep" `BranchStatus`'s own docstring already warns against elsewhere in this codebase.
- **Disposed** — maps to `PlantStatus.DECEASED`. "Deceased" already covers "no longer a saleable, living plant," which is what "disposed" means operationally.
- **Archived** — modeled as `Plant.archived_at`/`archived_reason`, a nullable timestamp pair, **not** a sixth `PlantStatus` enum value. This mirrors how `sold_at`/`deceased_at` already record *when* a terminal status was reached without being separate status values themselves, and mirrors `NurseryStatus.ARCHIVED`/`BranchStatus.INACTIVE`'s "hide from default listings, keep forever" concept while keeping `PlantStatus` itself unchanged. Archiving requires the plant to already be in a terminal status (`SOLD` or `DECEASED`) — it's a record-keeping action on a plant whose commercial lifecycle is already over, not a lifecycle transition in its own right.
- **Reserved** — deferred. This is a sales/order concept ("a customer has committed to buy this specific plant"), and Module 6's spec is Plant Lifecycle Management, not Sales. No `Sale`/`Order`/`Reservation` model exists yet in this codebase. Implementing it here would mean guessing at a future Sales module's data model. Out of scope, flagged for that module.

## Inventory and Plant are deliberately separate models

An early version of this module wired `PlantService.register_plant` to also increment the bulk `inventory` table's quantity, following the LLD's mention of `InventoryService.apply_change()`. Reading `docs/ux/16-inventory-workflow.md`'s "Relationship to the Digital Twin" section caught this before it shipped: bulk `inventory` (undifferentiated stock counts, e.g. "40 units of 4-inch basil") and individually-tracked `Plant` (one Digital Twin per specimen) are explicitly separate, non-overlapping models in this product — a plant that has its own QR code and lifecycle timeline is never also counted in the bulk inventory total for its SKU, or every report double-counts. The spec's "initial inventory assignment" requirement is satisfied by `Plant.branch_id` + `Plant.status` alone; no write to the `inventory` table happens anywhere in this module. No `InventoryRepository` was added.

## Plant movement: one table, not four

The spec lists branch, zone, greenhouse, and outdoor transfers as separate concerns. Rather than four movement-history tables, the existing `PlantTransfer` table was extended with nullable `from_zone`/`to_zone` columns. A branch-to-branch move populates `from_branch_id`/`to_branch_id` with `from_zone`/`to_zone` null; a same-branch zone-only move sets `from_branch_id == to_branch_id` with the zone columns populated; greenhouse/outdoor is just a `to_zone` value like any other zone label. One table, one repository, one `PlantService.move_plant` method, one movement-history read path — a plant's full movement history is always `list_movement_history`, regardless of what kind of move each entry represents.

## Plant Timeline is a pure read-model

`PlantTimelineService` has exactly one public method, `get_timeline`. It writes nothing and owns no table — every entry is reconstructed by reading across the append-only tables that already exist (`PlantTransfer`, `GrowthTimeline`, `HealthHistory`, `WateringLog`, `FertilizerLog`, `DiseaseReport`, `Treatment`) plus `Plant.sold_at`/`deceased_at`/`archived_at` for the terminal events. This makes "timeline events are immutable" true by construction rather than by convention: there is no `update_timeline_entry` or `delete_timeline_entry` method to accidentally call, because the timeline isn't a table a caller could mutate — it's a merge-and-sort view over tables that are themselves append-only. Two items from the spec's event list are deliberately absent from the feed: "Inventory Updated" (no inventory writes happen in this module — see above) and environmental readings (not in the spec's own example event list, and a temperature/humidity reading isn't really a lifecycle *event* in the same sense as the others). Both omissions are noted in the service's module docstring rather than silently dropped.

## Branch-scoped authorization: a first for this codebase

Every prior module's resources (Species, PlantVariety, PlantCategory) are org-scoped only. `Plant` is genuinely branch-scoped — a single `branch_id`, via `BranchScopedMixin` — so every Plant route passes `target_branch_id` into `AuthorizationService.authorize()`, which was already built (in Module 3) to check `access.branch_ids` membership for non-org-wide grants; this module is simply the first caller to actually exercise that path for a flat, single-branch-scoped resource. `POST /plants` is the one exception that needs a different shape: there's no existing plant row to fetch-then-authorize against, so `_authorize_branch_write` authorizes against the branch ID from the request body instead of a fetched resource — same authorization call, different source for `target_branch_id`.

## Fertilizer routes reuse `watering:*` permissions

No `fertilizer:read`/`fertilizer:write` permission codes were ever seeded in `migrations/versions/0002_seed_system_metadata.py`. Rather than add new permission codes unilaterally (which would need its own migration and role-matrix update, out of scope for this module), Fertilizer routes are gated on `watering:read`/`watering:write` — consistent with `FertilizerLog`'s own pre-existing model docstring, which already describes fertilizing as folded under general "care" alongside watering, and consistent with Module 5's own precedent of reusing `species:read` for `GET /plant-categories` rather than inventing a new permission code for a closely-related read.

## Disease severity thresholds drive automatic status transitions

`DiseaseReportService.confirm_report` calls `PlantService.transition_status(UNDER_TREATMENT)` automatically, but only for `MEDIUM`/`HIGH`/`CRITICAL` severity confirmed reports on a plant currently `IN_PRODUCTION` or `READY_FOR_SALE` — a `LOW`-severity confirmed report doesn't pull a plant out of production. `TreatmentService.apply_treatment` calls `PlantService.transition_status` back to `IN_PRODUCTION` (outcome `RECOVERED`) or to `DECEASED` (outcome `PLANT_LOST`), and only when the plant is currently `UNDER_TREATMENT` — both outcomes also resolve the disease report. `TreatmentOutcome.ONGOING` moves a `CONFIRMED` report to `TREATED` without closing it or touching plant status, so a plant can accumulate several `ongoing` treatment attempts before a final `recovered`/`plant_lost` outcome is recorded.

## QR codes

`QRCodeService.generate_unique_token()` produces an `NVA-` prefix plus 12 random characters from a 33-character alphabet that excludes visually ambiguous characters (`0`/`O`, `1`/`I`), checks the candidate against `PlantRepository.get_by_qr_token` for collisions, and retries up to 5 times before raising. Every registered plant gets one at creation time — `GET /plants/qr/{token}` is the lookup route a physical QR scan resolves to.

## Digital Twin creation is automatic because the Plant row *is* the Digital Twin

The spec asks for "initial Digital Twin creation" as part of registration. There is no separate `DigitalTwin` table to insert into — per the existing schema, `Plant` plus its related record tables (growth/health/watering/fertilizer/environmental/transfers/images) together *are* the Digital Twin. `PlantService.register_plant` creating the `Plant` row, generating its QR token, and returning it is the Digital Twin's creation; there's no second write path to keep in sync.

## Bulk registration: all-or-nothing in intent, not rollback-tested in fakes

`bulk_register_plants` loops calling `register_plant` per item and lets any exception propagate, aborting the batch. Against the real SQLAlchemy repositories this is atomic (all inserts share one session transaction, so a mid-batch failure rolls back everything already added). The in-memory fakes used by this module's own tests can't exercise that rollback guarantee — a failure partway through leaves already-`register_plant`-ed items in the fake's dict — so this limitation is disclosed directly in the service's docstring rather than asserted as tested when it isn't.

## What remains unverified

Same disclosed limitation as every prior module: no live PostgreSQL or Redis instance is reachable in this sandbox. The real `SqlAlchemy*Repository` implementations (including the unified `PlantTransfer` movement query, the QR-token collision check under real concurrent inserts, and the `plants` referential-count query Module 5's `SpeciesService`/`PlantVarietyService` delete guards depend on) have been validated for correct query construction and exercised end-to-end through the app's HTTP layer against in-memory fakes, but true behavior against real data volume and real concurrent writes remains unverified against real infrastructure. Bulk registration's transactional rollback guarantee specifically falls into this category — see "Bulk registration" above.
