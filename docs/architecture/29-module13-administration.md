# Phase 6, Module 13 — Administration & System Management: architecture, security model, and production-readiness review

Real, running FastAPI code in `apps/api/app/`. This is the final functional module before production readiness (Module 14). It covers Role & Permission Administration, User Administration, System Configuration, Feature Flags, Audit & Security Administration, System Health, AI Administration, and Data Management — plus the one genuinely new capability added to an earlier module (`EmployeeService.reactivate_employee`, Section 3's "Employee Administration," since Sections 3/4/5 are otherwise fully covered by Module 4's existing `EmployeeService`/`OrganizationService`/`BranchService`).

## Architecture: eight services, two permission shapes, no new microservices

`app/services/admin_service.py` holds eight service classes in one file — the same "several related, individually small service classes share a module" precedent Module 9's `sales_service.py` already established, rather than eight near-empty files: `RoleAdminService`, `UserAdminService`, `FeatureFlagService`, `SystemConfigService`, `AuditAdminService`, `HealthCheckService`, `AIAdminService`, `DataManagementService`. No new microservice, message queue, or standalone process was introduced — every capability is a route → service → repository call inside the existing modular monolith, per the standing "do not add unnecessary microservices" constraint.

Two permission shapes coexist in `app/api/routes/admin.py` (33 routes total, mounted at `/admin`):

- **Org-scoped routes reuse existing permission codes** from earlier modules — `employees:read`/`employees:write` (Role & Permission Administration, User Administration — mechanically staff-management operations on top of the same Employee/User records Module 4 already protects), `audit:read` (Audit & Security Administration), `feature_flags:read`/`feature_flags:manage` (Feature Flags' org tier). No new permission code was minted where an existing one already fit.
- **Platform-wide routes** (System Configuration, System Health, AI Administration, Data Management, and Feature Flags' platform-default tier) require the two genuinely new permissions this module adds — `admin:read`/`admin:manage` (migration 0018) — checked with `require_permission(...)` and no path-scoped nursery id, the same org-agnostic shape Module 12's report-catalog route already established. Only the seeded `platform_admin` system role is ever granted these two permissions.

## Section-by-section summary

**1. Role & Permission Administration** — `RoleAdminService`: list system + org roles, list the permission catalog, inspect a role's granted permissions, inspect a user's *effective* (resolved) permissions (delegates straight to `PermissionService.resolve_for_user`, the Module 3 resolver that is already the single source of truth), and change a staff member's role. Two protections satisfy "system-level roles must be protected from unauthorized modification": neither the current nor the new role may be `owner` (ownership moves exclusively through `EmployeeService.transfer_ownership`), and the target must already hold a `RoleAssignment` in exactly the caller's org (a cross-tenant target is a 403, never a 404).

**2. User Administration** — `UserAdminService`: search/detail, activate/deactivate, lock/unlock (with a fixed-duration lockout and a security-event log entry per action), session listing/revocation/force-logout, and password-reset/email-verification triggers — all delegating token issuance to the existing `AuthService` (Module 2) rather than reimplementing it. Every method is org-scoped through `Employee` (the only tenant-scoping join point `users` has); a target with no Employee row in the caller's org is a 403, never a 404. The organization owner's account cannot be administered by anyone but the owner themself.

**3. Employee Administration** — served by Module 4's existing `EmployeeService`, plus one new method this module adds directly to it: `reactivate_employee`. Deactivation (`remove_employee`) deletes the `RoleAssignment` entirely rather than disabling it, so reactivation provisions a brand-new assignment and therefore requires the caller to supply an explicit `role_code` — the old role is not recoverable from a deleted row. Exposed as `POST /employees/{id}/reactivate` on the existing `employees.py` router, mirroring the `deactivate` route's fetch-then-authorize pattern.

**4/5. Nursery & Branch Settings** — fully covered by Module 4's existing `OrganizationService`/`BranchService` and their routes; nothing new was needed.

**6. System Configuration** — `SystemConfigService`, platform-wide (`admin:read`/`admin:manage`). Validates `category` and `value_type` against fixed sets before writing, and never accepts or exposes a secret (`SystemConfig.value` is a plain JSON value, never a credential field).

**7. Feature Flags** — `FeatureFlagService`. Three-tier resolution (branch override → org override → platform default) with a fail-safe contract: a key with no row at any tier resolves to `False`, never raises. Org-tier writes need `feature_flags:manage`; the platform-default tier needs `admin:manage` — verified as genuinely separate gates by `test_platform_feature_flag_write_denied_with_only_org_manage_permission`.

**8. Audit & Security Administration** — `AuditAdminService`. Adds the filterable search layer (date range, actor, action, entity type, result, branch) over `audit_logs`/`security_events`/`authorization_denials` that Module 3's original filterless viewer didn't have, plus a CSV/Excel/PDF/JSON export reusing Module 12's `exporters.render()`. `platform_security_events` is the one deliberately cross-tenant view in this module (every organization's security events, `admin:read`-gated) — authorization for it is enforced at the route layer, not inside the service, mirroring how every other platform-wide route in this module works.

**9. System Health** — `HealthCheckService`/`HealthReport`. Every field is a boolean or a short label — never a secret, credential, or internal token — satisfied structurally: nothing on `HealthReport` is capable of holding one, since every check reduces to either a live round-trip (database: `SELECT 1`; cache: a real `set`/`get` round-trip through the existing `Cache` abstraction, working identically regardless of Redis-vs-in-memory backend) or a `bool(setting)` presence check (storage/AI/notifications/background). Both liveness checks fail closed (`False`) on any exception rather than raising or leaking a stack trace into the response.

**10. AI Administration** — `AIAdminService`. Model configuration status per capability is read via `ModelRegistry.is_configured()` (an environment-variable presence check) with **no write path anywhere in the application layer** — Section 10's "do not allow arbitrary model configuration changes" requirement is satisfied by the capability not existing at all, not merely by being gated. Usage stats, inference failures, and RAG knowledge-base status are all read-only aggregations, gated by an explicit `nursery_id` query parameter (not implicit tenant scoping) since these are `platform_admin` routes meant to inspect any org.

**11. Data Management** — `DataManagementService`. Deliberately read-only: `retention_summary()` returns a dry-run count of rows older than a caller-supplied threshold. There is no deletion path anywhere in this service or its route — "never provide unrestricted destructive database operations through the application" is satisfied structurally, the same pattern AI Administration's model-status uses.

**12. Security Controls** — privilege-escalation prevention is the "owner role/account is untouchable" invariant enforced independently in two places (`RoleAdminService.change_user_role`, `UserAdminService._assert_not_owner`); every sensitive operation records actor, organization, action, target, timestamp, request ID, and result via `audit_logs` (two columns — `branch_id`/`result` — were added by migration 0018 specifically to complete that list, rather than splitting a parallel "admin actions" table off from the existing, immutable-at-the-database-grant-level `audit_logs` table).

## AI inference latency/failure tracking (a cross-cutting Module 10 extension)

`InferenceBase.run()` (Module 10's shared inference pipeline) now measures wall-clock latency around `preprocess → predict → postprocess` and passes it to `PredictionLogger.persist()` on success; on any exception, it best-effort-logs one `AIInferenceFailure` row (wrapped in its own try/except so a failure-logging failure can never mask the original exception) and then re-raises unchanged — every one of the six prediction modules' existing typed-error-to-graceful-degradation contracts is completely unchanged. This is additive and optional (`failure_repo: AIInferenceFailureRepository | None = None`, default `None`); four of the six inference modules needed zero code changes since they don't override `__init__`.

## Defects found and fixed this session (each with a regression test)

1. **`SystemConfigService.set_config`'s before/after audit diff silently recorded "before" as "after"**: both `FakeSystemConfigRepository.upsert` and the real `SqlAlchemySystemConfigRepository.upsert` mutate the existing row's `.value` attribute in place on an update rather than returning a new object, and the real repository additionally relies on SQLAlchemy's identity map, which guarantees `get(key)` and the object `upsert` mutates are the exact same Python object. Capturing `before.value` by reference before calling `upsert` meant that by diff-construction time, `before.value` and `config.value` were already the same (post-update) dict — every "before" ever logged for a config update silently equaled "after," making the audit trail useless for exactly the changes it exists to record. Fixed by snapshotting `before.value` into a separate variable immediately after fetching, before `upsert` runs. Regression: `test_set_config_round_trips_value_and_audits_before_after`.
2. **`export_audit_logs` passed the wrong `ReportFormat` attribute to the shared exporter**: `exporters.render()` keys its dispatch table by enum *member name* (`"CSV"`), not `.value` (`"csv"`) — `ReportGenerationService.generate` (Module 12) already established `.name` as the correct call shape, but this route's first draft passed `.value`, raising `ValueError: Unsupported report format: csv` on every export. Fixed to match the existing Module 12 precedent. Regression: `test_audit_log_search_and_export_are_org_scoped`.
3. **Three DB-`server_default`-only fields never populated in the in-memory test fakes**, discovered while exercising Module 13's routes against data written the way earlier modules actually write it: `SecurityEvent.id`/`created_at` (`FakeSecurityEventRepository.log`), `AuditLog.result` (`FakeAuditLogRepository.log`), and `RefreshToken.issued_at` (`FakeRefreshTokenRepository.add`) are all populated by Postgres itself at INSERT time in production and were never set explicitly by any pre-Module-13 caller (`AuthService._log_event`/`_issue_token_pair`, every earlier module's own `_log_audit` helper) — a gap that went unnoticed because no route before Module 13 ever serialized these fields back out through a Pydantic model that required them. Fixed by backfilling all three in the fakes, matching the precedent `FakeAuditLogRepository.log`'s existing `id`/`created_at` backfill already established. Regressions: `test_session_list_revoke_and_force_logout`, `test_security_events_org_scoped_vs_platform_wide`, `test_audit_log_search_and_export_are_org_scoped`.
4. **FastAPI 204-status assertion errors**: `revoke_user_session`/`force_logout_user` set `status_code=204` without `response_model=None`, raising `AssertionError: Status code 204 must not have a response body` at app-construction time — the same bug class Module 12's `DELETE /reports/scheduled/{id}` already hit once. Fixed by adding `response_model=None`, matching that precedent.
5. **`Depends(request_context)` misuse**: `request_context` (`app/api/deps.py`) is a plain function taking `Request` directly, always called inline elsewhere in this codebase — not a bare-`Depends()`-compatible dependency. Fixed with a local `_req_ctx` wrapper, caught before any test ran (via a live `create_app()` construction check).
6. **Forward-reference ordering bug in `deps.py`**: `get_ai_inference_failure_repository`, originally placed in the new Module 13 section at the end of the file, is referenced via `Depends(...)` as a default argument by the six Module 10 AI-inference getter functions defined much earlier — Python evaluates default-argument values at `def` time, so this would have raised `NameError` at import. Fixed by relocating the function's definition into the Module 10 section, immediately after `get_ai_prediction_repository`.

## Remaining risks / disclosed gaps

- **`platform_admin` is the only role ever granted `admin:read`/`admin:manage`** in the seed data — this module assumes that assignment is managed correctly outside the application (it is not itself self-service-grantable, by design: `RoleAdminService.change_user_role` explicitly cannot grant `owner`, and there is no route anywhere that grants `platform_admin` to an arbitrary user). A real deployment's operational runbook needs to document how a `platform_admin` account is provisioned.
- **`HealthCheckService` needs a real `AsyncSession`/`Cache`/`Settings`**, so it's the one Module 13 service deliberately not part of the shared fake-backed test harness — verified instead by constructing a full app per-test with a small stub session (working and broken), the same "override the one DB-touching dependency per-test" pattern `test_health.py`'s own `/readyz` tests already use for Module 1's `get_db`.
- **Feature flags and system config have no bulk-import/export tooling** — each key is set one at a time via its own `PUT`; acceptable for the current scale (a handful of flags/configs per deployment) but would need a batch endpoint if the catalog grows significantly.
- **Data retention visibility, not enforcement** — `DataManagementService.retention_summary()` reports counts only; there is no automated purge job. This is a deliberate scope boundary (Section 11 explicitly rules out "unrestricted destructive database operations through the application"), not an oversight, but it means retention policy enforcement is currently a manual/external process.
- **No live PostgreSQL instance in this sandbox** — migration 0018 is validated offline (SQL generation, structural sanity counts) exactly as every prior module's migration was; the `docker compose up -d postgres && alembic upgrade head` step against a real database remains the one verification this environment cannot perform.

## Production readiness assessment

Module 13 is architecturally consistent with every prior module: no new microservices, the same repository/service/route layering, the same fetch-then-authorize and org-scoped-cross-tenant-403 patterns established since Module 3, and the same test-harness conventions. All 33 routes are authenticated, authorized (against either a reused org-scoped permission code or the two new platform-wide ones), and audited where they mutate state. The three privilege-escalation-relevant invariants (owner role untouchable, owner account untouchable by others, platform-wide permissions ungrantable through this module) are each independently enforced and independently tested. Six genuine defects were found and fixed during this module's own test-writing — three in Module 13's own new code, three latent gaps in shared test infrastructure exposed for the first time by Module 13's routes — each with a named regression test, per the standing defect-handling process. 1,148 tests pass; Ruff and the Module-13-relevant mypy surface are clean; migrations validate offline; the OpenAPI schema and a live server both confirm the full route surface is correctly wired.

This is the final functional module before Module 14 (Production Readiness). Per the standing instruction, work stops here for review and approval before Module 14 begins.
